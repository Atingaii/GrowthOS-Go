# 第 17 节第一性原理设计手记：先证明“什么可以被抽”，再决定“怎样抽”

> 本文记录第 17 节“最简单随机抽奖需要什么对象”在实现提交 `0b59217` 所处时间切片中的架构推导。它不是概率算法教程、数据库设计、API 契约、验收报告或面试背诵稿。本文中的“已实现”只指 `internal/lottery/domain` 内的纯内存领域对象及其单元测试；真实执行结果以[第 17 节 QA](../../qa/lessons/lesson-17.md)为准。数据库表、Repository、随机选择、HTTP API、真实 React 抽奖页、规则引擎和 Redis 都尚未出现，尤其不能从 `AwardOutcome` 的存在推导出“一次抽奖已有唯一最终结果”或 NFR `INV-03` 已满足。

## 1. 决策命题与时间切片：这一节只决定合法配置，不决定抽奖事实

“随机抽奖”看起来像一个算法题：生成随机数，再根据概率返回奖品。

如果直接从算法开始，代码很容易先写成这样：

```go
if rand.Intn(100) < 10 {
	return "优惠券"
}
return "谢谢参与"
```

它能演示一次分支，却没有回答决定系统能否继续演进的问题：

- “10”是百分比、万分比、权重还是运营误填的字符串？
- “优惠券”是可选结果、已中奖事实、库存、待发权益还是已经到账的权益？
- “谢谢参与”是一次正常完成的未中奖，还是算法没有找到结果？
- 同一组奖项属于哪个可复用配置？它是否就是营销活动？
- 两个同名奖项如何区分？
- 输入切片在对象创建后被调用方修改，策略是否会悄悄变化？
- 权重求和溢出后，随机区间是否会回绕？
- 数据库返回顺序变化，是否会改变同一随机值对应的奖项？
- 一个奖项或全部都是 `no_reward` 的策略是非法，还是一种允许但需要上层治理的配置？
- 这个对象怎样在后续表、Repository、算法、API 和缓存之间保持同一个含义？

因此，本节真正要决定的不是随机数生成器，而是：

> 在还没有持久化、用例、传输和缓存的前提下，怎样建立 Lottery 上下文最小但完整的领域词汇，使任何后续抽奖算法只能接收合法、稳定、可区分且不会因调用方别名修改而变化的策略配置；同时不把 Activity、User、库存、Benefit 或最终 DrawResult 错装进这个模型？

### 1.1 本节完成的时间切片

本节已经实现：

- `StrategyID` 与 `AwardID` 两个基于 `uint64` 的领域标识类型；
- `Weight` 正整数相对权重，不把权重伪装成百分比；
- `AwardOutcomeReward` 与 `AwardOutcomeNoReward` 两种封闭结果候选语义；
- `Award` 实体及其构造器、只读访问器和局部不变量；
- `Strategy` 聚合根及其构造器、只读访问器、奖项查找和总权重；
- Strategy/Award 名称的 trim、UTF-8、控制字符和 128 rune 上限约束；
- 聚合内 Award ID 唯一、至少一个 Award、每个权重大于零、总权重不溢出的约束；
- 构造输入和 `Awards()` 输出两侧的切片防御复制；
- 按 Award ID 升序规范化聚合内部顺序；
- 对合法、边界、零值、重复、溢出、别名修改和查找行为的单元测试。

### 1.2 本节尚未发生的时间切片

本节没有实现：

- MySQL 业务表或任何 Migration；
- Repository、SQL、事务或领域对象重建；
- 随机源、随机数区间、加权选择或统计分布验证；
- “一次请求只能得到一个最终结果”的幂等与持久化语义；
- HTTP route、DTO、错误码、JSON ID 表示或鉴权；
- 真实 React 抽奖页面；现有业务页仍不能作为本模型的运行证据；
- Redis 缓存、缓存键、TTL、失效或穿透保护；
- 用户资格、次数、活动状态、库存、预算、奖品发放或补偿；
- Strategy 版本、审核、发布、灰度、历史快照或审计；
- 生产公平性、密码学随机性、监管合规或业务 SLO 结论。

这个时间边界非常重要：当前对象回答的是“什么配置可以交给未来算法”，不是“某次抽奖已经发生了什么”。

### 1.3 可重放的决策摘要

如果后来者只想快速重放本节推理，可以沿着下面这条链路检查：

```text
Lottery 拥有结果选择规则
→ 先需要一个可复用的决策配置，而不是 Activity 或 User
→ 配置必须把多个可选结果作为一个整体保持合法
→ Strategy 成为聚合根，Award 成为聚合内实体
→ 选择强度需要精确、可累加且不依赖固定分母
→ 使用正整数相对 Weight，并显式检查总和溢出
→ “未中奖”也是正常完成结果候选，不能用 nil 或概率空洞表达
→ 用 reward / no_reward 封闭词汇区分候选语义
→ 构造完成后配置不能被调用方切片别名悄悄修改
→ 私有字段、构造校验、输入复制、输出复制和规范排序
→ 只用单元测试证伪对象不变量
→ 把表、Repository、算法、API、前端与缓存留给第 18～24 节逐层建立证据
```

## 2. 不可争辩的事实、约束与仍待验证的假设

设计开始时必须先把代码事实、业务事实、平台事实和希望如此的假设分开，否则“未来计划”会被误写成“已经完成”。

### 2.1 当前代码事实

| 代码事实 | 直接含义 | 它明确不能证明什么 |
| --- | --- | --- |
| `Strategy` 与 `Award` 位于 `internal/lottery/domain` | 它们属于仓库内部 Lottery 领域模块，不是公共 SDK | 模块已经可以独立部署或拥有独立数据库 |
| 字段私有，只能由构造器生成合法公开值 | 包外调用方不能直接改写字段绕过校验 | 同包未来代码永远不会误改私有字段 |
| ID 与 Weight 的底层类型是 `uint64` | 零值可作为非法哨兵，正值范围大且可精确表示 | JSON/JavaScript 能无损表示所有值 |
| Weight 必须大于零 | 每个保留在策略中的 Award 都具有非零选择质量 | 未来算法一定公平或不存在 modulo bias |
| 总权重使用显式溢出检查 | 构造时不会把 `uint64` 求和静默回绕 | 第 20 节会安全处理 `MaxUint64` 随机区间 |
| Outcome 只接受 `reward`、`no_reward` | 未知字符串与零值不能成为合法 Award | `reward` 已经发放，或 `no_reward` 等于失败 |
| 名称先验证 UTF-8，再 trim，再按 rune 限长并拒绝控制字符 | 已构造名称具有最小展示与存储可用性 | 名称已做 Unicode 规范化、反欺骗或 HTML 安全处理 |
| Strategy 至少包含一个 Award | 合法配置不会产生空选择集合 | 多 Award 才有随机性；单 Award 被明确允许 |
| Strategy 内 Award ID 不重复 | 可在聚合内按 ID 唯一查找一个 Award | Award ID 已被证明全局唯一 |
| Award 名称可以重复 | 展示标签不是身份 | 运营界面已经能避免同名误操作 |
| 构造器按 Award ID 排序 | 调用方输入顺序不是当前领域状态 | 前端展示顺序应该按 ID，或未来永远不需要运营排序 |
| 输入与输出切片均复制 | 包外调用方不能通过原切片或返回切片替换聚合元素 | 未来 Award 若加入 map/slice/pointer 后浅复制仍然足够 |
| `Award(id)` 当前线性扫描 | 少量奖项下实现简单，且不保留第二份索引状态 | 大规模配置下查找复杂度一定可接受 |
| 构造器不读时钟、随机数、数据库、网络或环境变量 | 同一输入产生同一对象或同一类错误 | 整个 Lottery 用例是确定性或无外部依赖 |

### 2.2 已有业务语言事实

已有[限界上下文地图](../../product/bounded-context-map-v1.md)规定：

- Lottery 拥有 Strategy、Award、概率、抽奖规则与结果选择；
- Marketing 拥有 Activity 的目标、时间窗、预算、渠道和生命周期；
- Participation 拥有用户资格、次数、参与订单和幂等；
- Benefit 拥有积分、优惠券等权益的发放、余额、流水、使用和补偿；
- 其他上下文可以引用 Lottery 的结果，但不能复制一份可独立修改的权威事实。

这些事实决定对象边界，但没有决定表结构、进程拆分或同步协议。

### 2.3 平台与语言约束

| 约束 | 对设计的影响 |
| --- | --- |
| Go 结构体有可用零值，但业务 ID、Weight 和 Outcome 的零值没有合法含义 | 构造器与嵌套校验必须显式拒绝零值，不能依赖调用方自律 |
| slice 是指向底层数组的描述符，赋值不会深复制元素 | 聚合如果直接保存调用方 slice，就会暴露可变别名 |
| Go string 是不可变字节序列，但不保证内容一定是合法 UTF-8 | 名称构造前必须校验编码 |
| `uint64` 加法会按无符号整数规则回绕 | 总权重必须在加法前检查剩余空间 |
| JavaScript number 只对至多 `2^53-1` 的整数保证精确 | 第 21 节必须决定 JSON ID 使用字符串还是限制数值范围 |
| Unicode rune 是代码点，不是用户感知字素 | 128 rune 不是 128 个“肉眼字符”，组合字符和 emoji 可能产生差异 |
| 模块化单体共享进程 | 包边界和事实所有权仍需明确，不能用“同进程”作为跨上下文混模理由 |
| 当前没有业务表 | 任何字段、索引、排序、字符集和外键设计都还是第 18 节问题 |

### 2.4 不可跨越的设计约束

1. Strategy 不能等同于 Activity；前者是可复用选择配置，后者有营销生命周期。
2. Award 不能等同于 Benefit；前者是被选中的奖励描述，后者有发放和持有生命周期。
3. `no_reward` 必须表达正常未中奖，不能吞掉服务失败或未知结果。
4. 仅有候选 Award 不能被描述成已保存 DrawResult。
5. 当前没有用户输入，因此模型不能嵌入 User、资格或次数规则。
6. 当前没有库存事实，因此 Weight 不能同时承担库存含义。
7. 当前没有算法，因此 Weight 不能被宣传为已经验证的真实命中率。
8. 当前没有 API，因此领域错误不能提前绑定 HTTP status 或公开错误文案。
9. 当前没有持久化，因此不能宣称跨进程、重启或版本升级后对象仍然可恢复。
10. 当前没有缓存，因此不能把任何内存对象行为写成 Redis 契约。

### 2.5 仍待验证的业务假设

下列内容是当前有意允许的建模假设，不是经过产品或生产数据证明的规则：

- 单 Award Strategy 合法，可表达确定性结果或开发/回退配置；
- 全部 Award 都是 `no_reward` 的 Strategy 合法，可表达暂停奖励但仍返回正常未中奖语义的配置；
- Award 名称不承担身份，因此允许重名；
- Award ID 在一个 Strategy 内必须唯一，但是否全局唯一留给持久化设计决定；
- 输入顺序不是业务含义，使用 ID 排序作为当前规范顺序；
- 128 rune 足以覆盖当前运营名称；
- Strategy/Award 名称不应该承载个人敏感信息，但代码尚未强制这一业务政策；
- 当前常见策略的 Award 数量较小，暂不设置最大数量；
- 相对权重比固定百分比更符合后续演进，但真实运营是否需要固定精度尚无证据。

这些假设全部进入第 13 节的风险账本，必须有失效信号和重新决策条件。

## 3. 为什么现在做、为什么不多做

### 3.1 为什么第 17 节先做对象

第 18～24 节会依次增加表、Repository、算法、API、前端、规则与缓存。每一层都会倾向于用自己的便利反向定义领域：

- 数据库倾向于把表行当对象；
- Repository 倾向于暴露查询结果结构；
- 算法倾向于只保留计算所需的数组；
- HTTP 倾向于把 JSON DTO 当领域模型；
- React 倾向于按展示卡片字段定义 Award；
- Redis 倾向于按序列化和命中率定义对象形状。

如果没有一个先于这些技术适配器的合法模型，最终会出现多个互不相同的“Strategy”：一份表结构、一份缓存 JSON、一份 API DTO、一份前端类型和一份算法数组。每一份都能运行，但没有任何地方能回答哪个是权威业务含义。

现在建立领域对象，价值在于给后续层设置验收条件：

- 第 18 节的表必须能无损保存合法对象，也必须阻止或识别不合法数据；
- 第 19 节的 Repository 必须通过构造器重建对象，而不是绕过不变量；
- 第 20 节的算法只消费 Strategy，不重新解释 Weight；
- 第 21 节的 API 映射 DTO，不把 DTO 直接塞进领域；
- 第 22 节的前端展示是投影，不成为领域事实源；
- 第 24 节的缓存只是 Strategy 的派生副本，不拥有真相。

### 3.2 为什么不在本节实现随机算法

对象与算法有不同的失败问题：

- 对象负责“输入是否合法且稳定”；
- 算法负责“在合法输入上如何无偏、可测试地选择”；
- 用例负责“何时允许抽、如何记录和处理未知结果”；
- Repository 负责“如何恢复同一个领域含义”；
- API 负责“如何把外部输入变成受信任命令”。

若本节同时写算法，单元测试绿色很容易把两种证据混在一起：构造器用例可能掩盖分布偏差，分布测试又可能让人误以为数据模型已经稳定。第 20 节单独引入算法，才能明确讨论随机源注入、区间边界、`MaxUint64`、modulo bias、确定性测试和统计证据。

### 3.3 为什么不在本节设计数据库

领域约束与数据库约束相关但不等价：

- `128 rune` 如何映射 MySQL `utf8mb4` 字符长度和索引字节预算，需要第 18 节验证；
- Award ID 是全局主键还是 `(strategy_id, award_id)` 复合身份，尚需表与查询场景决定；
- Outcome 使用字符串、枚举、检查约束还是字典表，需要考虑迁移兼容性；
- Weight 与 total 是否冗余存储，需要事实源和校验策略；
- 规范排序按 ID 已定义，但运营展示顺序尚未定义，不能提前加 `position` 假装有需求；
- Strategy 更新、版本和并发控制尚未进入本节。

现在写表会让 SQL 便利反向塑造对象，也会把第 18 节本应独立学习的权衡吞掉。

### 3.4 为什么不是 Activity

Activity 回答：

- 何时开始和结束；
- 对哪个人群、渠道或预算投放；
- 当前是草稿、待审、运行还是结束；
- 使用哪个抽奖 Strategy。

Strategy 回答：

- 有哪些可选择 Award；
- 每个 Award 的相对选择权重；
- 哪个候选表示 reward，哪个表示正常 no_reward。

一个 Strategy 可以被多个 Activity 引用，一个 Activity 也可能在版本演进中切换 Strategy。若把 Activity 时间窗、预算或状态放进 Strategy，抽奖算法会被迫知道营销生命周期；若把 Awards 直接嵌进 Activity，配置就无法独立复用、审计和缓存。第 30 节会专门复盘这个边界，本节只守住最小分离。

### 3.5 为什么不是 User 或 Participation

User 是否有资格、剩余几次、是否重复请求，是 Participation 的事实。Strategy 对任何合法调用者都表示相同的配置。把 User ID 或剩余次数放入 Strategy 会导致：

- 配置对象失去复用性；
- 缓存键被用户维度放大；
- 资格规则与概率配置一起变化；
- Lottery 开始复制用户和参与账户事实；
- 后续幂等与额度事务难以确定所有者。

因此当前模型没有 User，不代表系统忽略资格，而是资格尚未进入第 25 节之后的对应边界。

### 3.6 为什么不是库存

Weight 表示相对选择质量，不表示库存数量：

- Weight 为 100 不等于还剩 100 份；
- 库存减少不必然意味着 Weight 同步减少；
- no_reward 也可以有 Weight，但没有可扣减库存；
- 库存需要原子扣减、超卖约束、对账和恢复；Weight 只需要被算法读取。

把二者合并会让概率更新和库存扣减互相污染，并诱导用“随机没抽中”掩盖“库存扣减失败”。库存从第 38 节起才有独立事实和证据。

### 3.7 为什么不是 Benefit

`AwardOutcomeReward` 只说明“选中后存在一项需要后续解释或交付的奖励描述”，不说明：

- 它是积分、优惠券还是其他权益；
- 库存是否足够；
- 发放请求是否已受理；
- 用户是否已经到账；
- 发放是否失败、重试或补偿；
- 权益是否被使用或过期。

这些生命周期属于 Benefit。当前 Award 甚至没有 `benefit_id` 或具体 reward payload，这是有意不越界，而不是遗漏一个字段。

### 3.8 为什么不是 DrawResult

一个候选 Award 与一次最终抽奖结果至少缺少这些信息：

- 唯一 draw/request/participation 标识；
- 使用的 Strategy 与版本；
- 被选中的 Award 快照；
- 请求开始、确认和结果持久化时间；
- 幂等键与重复请求行为；
- 超时、崩溃和结果未知时的查询语义；
- 后续 Benefit 交付关联；
- 审计与对账信息。

因此 `AwardOutcome` 不能承担 DrawResult。当前代码只定义“结果候选类型”，还没有“一次抽奖事实”。NFR `INV-03` 必须等待有结果持久化、唯一性约束、崩溃恢复和重复请求测试后才能验收。

## 4. 从第一性维度推导需求

本节按“事实 → 风险 → 必须建立的机制 → 当前证据 → 证据边界”推导，而不是从喜欢的模式名称倒推代码。

### 4.1 事实源：谁有权定义合法 Strategy

**事实：** Strategy 是 Lottery 的可复用决策配置；表、JSON、前端卡片和缓存都尚未存在或尚未真实接入。

**风险：** 如果公开字段允许任意组装，任何 adapter 都能制造不同的合法标准；后续数据库或 HTTP 会成为偶然事实源。

**需求：** 合法性必须集中在领域构造边界，包外不能跳过。

**机制：** 私有字段、`NewAward`、`NewStrategy`、sentinel error、嵌套重新校验。

**证据：** 单元测试覆盖有效与无效构造；包外代码在语言层不能直接设置私有字段。

**不能证明：** 同包未来代码不会增加绕过构造器的路径；第 19 节 Repository 是否确实调用构造器尚未实现。

### 4.2 身份：展示名称不能承担唯一性

**事实：** 两个奖项可能显示相同名称，但仍代表不同配置项；名称也可能被运营修改。

**风险：** 用名称查找或去重会把展示文案变化误认为身份变化，也会错误拒绝合法同名奖项。

**需求：** Strategy 和 Award 都要有独立、非零、稳定的 ID；聚合内 Award ID 唯一。

**机制：** `StrategyID`、`AwardID` 的领域类型和重复 ID 检查；名称不参与身份比较。

**证据：** 测试证明同名不同 ID 合法、重复 ID 被拒绝、零 ID 被拒绝。

**不能证明：** ID 如何生成、是否全局唯一、是否可猜测、数据库约束和跨环境迁移策略。

### 4.3 选择质量：概率首先是比例，不是格式

**事实：** 对离散候选进行加权选择，只需要每项具有正质量及一个有限总和；`1:3` 和 `100:300` 描述同一分布。

**风险：** 固定要求总和等于 100 或 10000 会把展示精度混入领域；浮点会引入表示与累加误差；零权重会让“存在但永远不可选”的状态混入策略。

**需求：** 使用正整数相对 Weight，不固定分母；构造时安全计算总和。

**机制：** `Weight uint64`、零值拒绝、加法前溢出检查、`TotalWeight()`。

**证据：** 测试覆盖 2:5、单项 `MaxUint64` 合法以及 `MaxUint64 + 1` 被拒绝。

**不能证明：** 第 20 节如何生成 `[0,total)` 上的无偏随机数、真实分布是否符合配置、配置是否符合业务预算或监管要求。

### 4.4 结果语义：未中奖是数据，不是空洞

**事实：** 一次合法抽奖可以正常完成但没有奖励。

**风险：** 用 `nil`、找不到 Award 或概率和小于固定分母的“空区间”表达未中奖，会把正常业务结果与算法 bug、脏数据、超时或依赖失败混在一起。

**需求：** 未中奖必须成为显式、可命名、可加权的候选；失败继续由 error 表达。

**机制：** `AwardOutcomeNoReward` 与 `AwardOutcomeReward` 封闭枚举；`HasReward()` 只解释候选类型。

**证据：** 测试证明两种 Outcome 合法、未知或零 Outcome 非法。

**不能证明：** 某次抽奖已经返回 no_reward、失败是否正确映射、reward 是否成功交付。

### 4.5 聚合一致性：奖项集合必须一次成形

**事实：** 每个 Award 单独合法，并不自动意味着集合合法；重复 ID 和总权重溢出只在集合层可见。

**风险：** 如果 Strategy 先创建再逐项 append，中间态可能为空、重复或溢出，并被其他代码观察。

**需求：** Strategy 必须在构造时原子验证整个集合；失败时不返回部分合法对象。

**机制：** 构造器先校验所有 Award、唯一性和总和，最后复制、排序并返回完整值；任一错误返回 Strategy 零值与 error。

**证据：** 负向测试覆盖空集合、零值 Award、重复 ID、溢出。

**不能证明：** 持久化多行写入或读取具有相同原子性；那属于第 18～19 节。

### 4.6 可变别名：聚合所有权必须真实，而不是注释

**事实：** Go slice 与调用方共享底层数组；返回内部 slice 也会暴露相同数组。

**风险：** 调用方在构造后修改输入，或修改 `Awards()` 返回值，会绕过不变量并造成并发数据竞争。

**需求：** Strategy 接管一份自己的集合表示，且读取不暴露内部集合。

**机制：** 构造时 `append([]Award(nil), awards...)`，访问时再次复制。

**证据：** 测试分别修改输入切片和返回切片，内部首项保持不变。

**不能证明：** 将来 Award 若包含引用型字段时，元素内部不会共享别名；当前只是足够的浅复制。

### 4.7 顺序：无业务含义的偶然顺序必须消除

**事实：** 当前没有 `position` 或运营排序需求；数据库在没有 `ORDER BY` 时也不保证行顺序。

**风险：** 保留调用方顺序会让同一集合因 SQL 计划、map 遍历或输入来源不同产生不同序列；若第 20 节算法依赖遍历顺序，同一个随机值可能映射到不同 Award。

**需求：** 为当前无序集合建立稳定规范表示。

**机制：** Strategy 构造时按 Award ID 升序排序。

**证据：** 测试以 30、10、20 输入，读取结果为 10、20、30。

**不能证明：** ID 顺序符合运营展示期望；一旦出现人工排序需求，需要新增显式领域属性并重评算法兼容性。

### 4.8 名称：进入领域后至少要可编码、可显示、可存储

**事实：** Go string 可以包含非法 UTF-8、首尾空白和控制字符；下游会进入日志、数据库、JSON 与 UI。

**风险：** 空名称无法识别；非法编码造成序列化和存储差异；换行等控制字符可能破坏日志或界面；无上限文本造成字段和资源预算漂移。

**需求：** 构造时统一最小规范，且将长度变成跨 adapter 必须保留的领域契约。

**机制：** 验证 UTF-8、`TrimSpace`、非空、最多 128 rune、拒绝 `unicode.IsControl`。

**证据：** 测试覆盖首尾空白、空白名、非法 UTF-8、换行、恰好 128 个中文 rune 和超限。

**不能证明：** Unicode NFC/NFKC、字素数、双向控制、零宽格式字符、混淆字符、HTML escaping、数据库 collation 和索引预算都正确。

### 4.9 权限：纯领域包不应该自行授权

**事实：** 当前对象不知道操作者、用户或请求来源。

**风险：** 在实体构造器中嵌入角色或 HTTP context，会把 Governance/Participation 逻辑与配置合法性耦合；相反，公开字段又会让未授权输入绕过合法性。

**需求：** 本节只验证“内容合法”，不判断“谁有权创建或使用”；授权必须在未来应用边界先完成，再调用构造器。

**机制：** 构造器只接收领域值，不接收身份、token、Gin context 或数据库连接。

**证据：** 包依赖仅为标准库，领域对象没有技术 context。

**不能证明：** 后续 API 已鉴权、运营配置已审批、普通用户不能创建策略。

### 4.10 发布与可逆性：先发布无外部状态的语言

**事实：** 本节新增包没有 route、表、配置、进程和数据迁移。

**风险：** 若领域决策与不可逆数据变更同批发布，发现边界错误时要同时迁移存量数据和外部契约。

**需求：** 先让对象与测试形成可审阅提交，再让第 18 节映射持久化。

**机制：** 独立课程分支和提交；本节代码为 additive，当前回退不会留下外部状态。

**证据：** Git diff 与测试能检查本节文件边界。

**不能证明：** 一旦第 18 节存入数据或第 21 节公开 API 后，语义仍可无成本回退。

### 4.11 可观测性：领域返回事实，不自行记录上下文

**事实：** 构造器没有 request ID、logger、metrics registry 或操作者信息。

**风险：** 领域层直接打日志会泄漏名称、重复记录并依赖平台；完全没有可分类错误又让上层无法统计失败原因。

**需求：** 返回稳定、可用 `errors.Is` 分类的 error，日志和指标由掌握请求上下文的 adapter 负责。

**机制：** sentinel errors；重复 ID 使用 `%w` 包装并携带非敏感 ID。

**证据：** 测试使用 `errors.Is` 匹配错误类别。

**不能证明：** 第 21 节会如何映射 HTTP 状态、公开文案和指标标签；也不能证明错误基数受控。

### 4.12 学习成本：让限制在类型和构造器里可见

**事实：** 课程分支要让学习者逐节比较设计演进。

**风险：** 过度抽象成通用 Entity、Aggregate、Probability 框架，会让两个对象被模式噪声淹没；裸 `uint64` 和 string 又会让术语混用。

**需求：** 只引入能防止当前真实错误的类型与方法，不建立通用 DDD 框架。

**机制：** 小型具体类型、明确命名、标准库依赖、独立文件和表驱动测试。

**证据：** 代码可以从 Award 局部不变量到 Strategy 集合不变量顺序阅读。

**不能证明：** 当前结构对所有未来复杂度仍是最佳；触发条件出现时可以演进。

### 4.13 一条完整的事实到证据链

以下链路用于检查本文是否真正从事实推导，而不是给代码补理由：

```text
事实：slice 赋值共享底层数组
→ 风险：调用方构造后修改输入，Strategy 在没有重新校验时变化
→ 需求：聚合必须拥有自己的 Award 集合
→ 机制：构造输入复制 + 返回输出复制 + 私有字段
→ 证据：分别修改输入和返回切片，Strategy 内部 ID 不变
→ 证据边界：Award 当前全是值字段，所以浅复制足够；未来加入引用字段必须重评
```

第二条链路解释为什么本节没有算法：

```text
事实：相对整数权重只定义目标比例，没有定义随机源和映射算法
→ 风险：把对象测试绿色误认为概率公平
→ 需求：配置合法性证据与分布证据分节建立
→ 机制：第 17 节只保存 Weight/TotalWeight；第 20 节再实现可注入随机选择
→ 当前证据：零权重和溢出被拒绝
→ 尚缺证据：无偏区间、边界随机值、统计分布、并发与基准测试
```

## 5. 备选方案矩阵

本节不是“因为 DDD 所以写聚合”。下面比较的方案都真实可用，只是在当前目标、风险和学习顺序下结论不同。

### 5.1 对象边界：贫血公开结构体、Activity 内嵌还是 Strategy 聚合

| 方案 | 优点 | 当前代价与风险 | 当前结论 | 重新评估触发器 |
| --- | --- | --- | --- | --- |
| 公开 `struct`，由 service 自行校验 | 代码最少；JSON/SQL 映射方便 | 每个入口可能形成不同校验；别名可变；非法零值可四处传播 | 不采用为领域模型；DTO/row 可以是公开结构，但必须映射 | 如果对象只剩无规则数据投影且不再进入决策链，可降低封装 |
| 把 Awards 直接放入 Marketing Activity | 初期一次查询可拿到全部活动和奖项 | Strategy 不可复用；生命周期、预算、资格与概率耦合；跨上下文所有权混乱 | 不采用 | 只有产品证明确实不存在独立策略生命周期、复用或所有权时重评 |
| Strategy 聚合根持有 Award 实体 | 集合不变量集中；技术 adapter 有统一目标；边界与上下文地图一致 | 多一层构造和映射；未来更新要设计聚合持久化 | 采用 | 聚合规模大到无法整体加载、写冲突显著或 Award 获得独立生命周期时重评 |
| Strategy 与 Award 都做独立聚合 | 可独立加载和更新 Award | 当前缺少独立生命周期；跨聚合无法原子保证空集合、唯一性与总权重 | 暂不采用 | Award 被大量策略共享、独立发布或独立权限管理时重评 |

### 5.2 权重表示：浮点概率、固定基数、相对整数或精确分数

| 方案 | 表达示例 | 优点 | 当前代价与风险 | 当前结论 |
| --- | --- | --- | --- | --- |
| `float64` 概率 | `0.1`, `0.9` | 对产品描述直观；标准库支持 | 二进制表示误差；求和与相等边界复杂；JSON/DB 精度协商困难 | 不采用 |
| 固定基数整数 | 万分之 1000、9000 | 精度固定；校验总和直观 | 把展示/运营精度写死；调整一个奖项常需同步所有项；“和必须等于基数”增加配置耦合 | 暂不采用 |
| 正整数相对权重 | `1:9` 或 `100:900` | 精确、简单、无固定分母；适合累计区间 | 需要安全求和；API/UI 需计算展示百分比；极端值影响算法实现 | 采用 |
| 有理数分子/分母 | `1/10`, `9/10` | 数学语义精确；可表达不同分母 | 约分、最小公倍数、溢出和序列化更复杂；当前无需求 | 不采用 |
| 预构建 alias table / 区间表作为领域状态 | 保存算法派生结构 | 高吞吐选择更快 | 派生状态可能与原权重漂移；本节尚无性能证据；提前锁算法 | 不采用；如第 24/95 节测量证明需要再考虑 |

选择相对整数不意味着 API 应直接接受任意 `uint64`，也不意味着运营界面不显示百分比。DTO 可以接收受控文本或数值，展示层可以计算比例，但领域事实仍是相对 Weight。

### 5.3 未中奖表示：nil、概率空洞、特殊 ID 还是显式 Outcome

| 方案 | 优点 | 关键问题 | 当前结论 |
| --- | --- | --- | --- |
| 算法返回 `nil` 表示未中奖 | 调用方写起来短 | 无法区分正常未中奖、未找到配置、算法 bug、超时和未知结果 | 不采用 |
| 固定基数剩余区间表示未中奖 | 配置项更少 | 未中奖没有 ID/名称/审计对象；改基数会改变语义；总和错误可能被静默吞掉 | 不采用 |
| 约定 Award ID 0 为未中奖 | 不新增字段 | 与 ID 零值非法冲突；魔法值跨系统易漂移；不能表达多个未中奖文案 | 不采用 |
| 每个 Award 携带 `reward/no_reward` | 语义显式；未中奖可命名、加权和追踪；失败仍走 error | 需要上层阻止错误配置；未来增加 outcome 类型要迁移 | 采用 |
| Award 内直接嵌入 Coupon/Points payload | 选中后信息完整 | Lottery 复制 Benefit 规则；库存与发放生命周期耦合 | 不采用 |

### 5.4 集合顺序：保留输入顺序、显式 position 或 ID 规范排序

| 方案 | 优点 | 当前问题 | 当前结论 | 重评条件 |
| --- | --- | --- | --- | --- |
| 保留输入顺序 | 无排序成本；可以顺便用于展示 | 顺序来源偶然；数据库无 `ORDER BY` 不稳定；算法映射可能变化 | 不采用 |
| 增加 `position` 作为领域字段 | 运营排序明确；算法可使用稳定顺序 | 当前没有排序需求；新增字段会提前影响表、更新和唯一约束 | 暂不采用 | 第 22/31 节出现明确展示或运营排序需求 |
| 按 Award ID 升序规范化 | 确定、简单；不需要额外状态；便于快照比较 | ID 顺序不等于业务展示顺序；构造 O(n log n) | 采用 | 奖项规模、运营排序或兼容旧随机映射要求变化 |
| 用 map 作为内部集合 | 查找 O(1) | 遍历顺序不稳定；返回和序列化仍需排序；保留第二份索引可能漂移 | 暂不采用 | Award 数量和 lookup profile 证明线性扫描成为瓶颈 |

### 5.5 可变性：指针实体、可变方法或不可变值

| 方案 | 优点 | 风险 | 当前结论 |
| --- | --- | --- | --- |
| `[]*Award` + setter | 更新方便；对象身份直观 | 共享指针、nil、并发竞争和绕过聚合校验 | 不采用 |
| Strategy 提供 `AddAward/ChangeWeight` | 支持增量编辑 | 需要定义中间态、并发版本、复制语义和失败回滚；当前无写用例 | 暂不采用 |
| 构造后只读值对象/实体 | 推理简单；适合并发读取和缓存；失败原子 | 每次更新需要重建；集合访问有复制成本 | 采用 |
| Copy-on-write 专用集合 | 可更新且降低复制 | 实现与学习成本高；无规模证据 | 不采用 |

### 5.6 ID 类型：自增整数、UUID/ULID 或业务字符串

| 方案 | 优点 | 风险/代价 | 当前结论 |
| --- | --- | --- | --- |
| `uint64` | 紧凑、排序和索引友好；零值可拒绝；Go/MySQL 常见 | JSON 大整数风险；可枚举；跨库生成与合并需策略 | 领域层采用，外部表示待第 21 节决定 |
| UUID | 分布式生成、难猜、跨库合并方便 | 16 字节索引、更长日志/JSON；当前单体无分布式生成需求 | 暂不采用 |
| ULID | 可排序、分布式生成、文本友好 | 需要额外库/规范；时间信息泄漏；大小写与排序契约 | 暂不采用 |
| 业务字符串 code | 人可读、跨环境稳定 | 改名与格式规则复杂；容易混用展示名称；索引更大 | 可作为未来额外 code，不替代当前 ID |

`uint64` 的采用只解决领域内部精确身份，不等于 HTTP 应输出 JSON number。第 21 节必须单独处理 JavaScript 安全整数问题。

### 5.7 名称策略：原样保存、字节上限、rune 上限或字素上限

| 方案 | 优点 | 风险/代价 | 当前结论 |
| --- | --- | --- | --- |
| 原样保存任意 string | 最少限制 | 非法 UTF-8、控制字符、空白和无界资源问题 | 不采用 |
| 固定 128 bytes | 与某些存储预算直接 | 中文/emoji 可用长度明显更短；用户语义不直观 | 不采用为领域规则 |
| 固定 128 runes | 标准库可实现；中英文相对公平；可映射字符列 | rune 不等于字素；未做规范化与反欺骗 | 采用为当前最小契约 |
| 固定 128 grapheme clusters | 最接近用户感知字符 | 需额外 Unicode 分割实现/依赖；版本兼容与成本更高 | 当前不采用；国际化证据触发时重评 |

## 6. 不变量与信任边界

### 6.1 Strategy 聚合不变量

任何未来实现、表、Repository、API 或缓存都必须保持以下性质：

| 编号 | 不变量 | 当前机制 | 未来 adapter 的责任 |
| --- | --- | --- | --- |
| S-01 | Strategy ID 非零 | 构造器拒绝零值 | 数据库/DTO 不得把缺失 ID 静默补成零 |
| S-02 | Strategy 名称为 trim 后非空、合法 UTF-8、无控制字符、至多 128 rune | `normalizeName` | DB charset/列长和 API 校验必须无损保持 |
| S-03 | 至少包含一个 Award | 构造器拒绝空集合 | Repository 不得返回半个聚合；事务写入要维持集合原子性 |
| S-04 | 每个内含 Award 自身合法 | Strategy 再次调用 `award.validate()` | 读取脏数据时不能绕过构造器 |
| S-05 | 聚合内 Award ID 唯一 | 临时 map 检查 | 表上必须有对应唯一约束或重建失败策略 |
| S-06 | totalWeight 等于所有 Weight 的精确和且不溢出 | 构造时受检累加 | 若持久化冗余 total，必须验证或明确事实源 |
| S-07 | 内部 Award 顺序按 ID 升序 | 构造后排序 | Repository/缓存顺序不能变成另一套业务语义 |
| S-08 | 构造后包外不能改变集合 | 私有字段与双向复制 | DTO、缓存对象不得共享可变引用 |
| S-09 | Strategy 零值不是合法配置 | 无公开构造字段、嵌套校验 | 调用方必须处理 error，不能把零值当 fallback |

### 6.2 Award 实体不变量

| 编号 | 不变量 | 当前机制 | 尚未包含的含义 |
| --- | --- | --- | --- |
| A-01 | Award ID 非零 | 构造器/validate 拒绝 | 不保证全局唯一或不可枚举 |
| A-02 | 名称满足与 Strategy 相同类别的最小文本约束 | 共享规范函数，各自错误类型 | 不保证名称唯一、已本地化或无混淆字符 |
| A-03 | Weight 为正整数 | 拒绝零值 | 不保证配置在预算/监管上合理 |
| A-04 | Outcome 只能为 reward/no_reward | 封闭常量与 validate | 不代表发放状态、失败状态或最终 DrawResult |
| A-05 | `HasReward()` 只由 Outcome 推导 | 纯函数 | 不查询库存、Benefit 或用户账户 |
| A-06 | Award 可以重名 | 不以名称去重 | UI 仍需显示 ID/code 以防运营误选 |

### 6.3 当前信任边界

```text
不受信任/未校验输入
  HTTP DTO（尚未实现）
  SQL rows（尚未实现）
  Cache bytes（尚未实现）
  测试或同包构造值
          │
          ▼
 NewAward / NewStrategy
  UTF-8、名称、ID、Weight、Outcome、集合、重复、溢出验证
          │
          ▼
 受信任的只读领域值
          │
          ├── 第 20 节算法只能读取
          ├── 第 21 节 DTO 只能投影
          └── 第 24 节缓存只能派生
```

这里的“受信任”只表示对象内部不变量成立，不表示：

- 调用者已授权；
- 配置已审批或发布；
- 概率符合商业规则；
- 随机选择公平；
- 奖励有库存；
- 数据不含个人信息；
- 一次抽奖结果已经持久化。

### 6.4 数据跨边界时必须重新验证的内容

- **HTTP → application：** 类型、大小、ID 编码、认证、授权、幂等和公开错误映射；
- **application → domain：** 调用构造器，不信任 DTO 已校验；
- **SQL → domain：** 数据类型、字符集、Outcome 值、重复行、空集合和总和溢出；
- **Redis → domain：** schema/version、完整性、过期与反序列化，再通过构造器；
- **domain → JSON：** ID 精度、名称 escaping、Outcome 兼容和信息最小化；
- **Lottery → Benefit：** 奖励描述与交付命令分离，接收方确认最终事实；
- **Lottery → logs/metrics：** 禁止高基数名称标签，避免未脱敏自由文本。

## 7. 资源所有权、并发与时间预算

本节没有数据库连接、goroutine、锁、timer、HTTP client 或容器，但“没有运行时资源”不等于不需要讨论所有权。

### 7.1 内存所有权

| 资源 | 创建者 | Strategy 是否接管 | 暴露方式 | 回收者 |
| --- | --- | --- | --- | --- |
| 调用方输入 `[]Award` | 调用方 | 不接管原数组；复制成自有 slice | 原 slice 仍归调用方 | Go GC |
| Strategy 内部 `[]Award` | `NewStrategy` | 是 | `Awards()` 返回新副本 | Go GC |
| 重复 ID 检查 map | `NewStrategy` | 构造期间临时拥有 | 不暴露、不保存 | 构造返回后由 GC 回收 |
| 名称 string | 调用方传入，trim 可能生成子串/值 | 保存规范字符串值 | 只读返回 | Go GC |
| sentinel errors | package 初始化 | package 全局只读 | 通过 error 返回 | 进程生命周期 |

“接管”不是把调用方 slice 清空，而是创建独立表示。调用方在构造后修改原 slice 不会改变 Strategy；反过来，调用方修改 `Awards()` 的结果也不会改变 Strategy。

### 7.2 并发语义

当前对象设计为构造完成后只读：

- 所有导出方法只读取标量、string 或内部 slice；
- `Awards()` 在每次调用时分配并复制，不共享可修改 slice；
- `Award(id)` 返回 Award 值而不是内部指针；
- 构造器只使用局部 map/slice，没有包级可变状态；
- 不读取时钟或随机源，因此并行构造不会互相影响。

在当前字段均为值或不可变 string 的前提下，同一个合法 Strategy 可被多个 goroutine 并发读取而无需锁。这是由结构推导出的设计属性，不是对未来字段的永久承诺。现有测试包含 `t.Parallel()`，但这不等于专门对同一对象进行高强度并发读取证明，也不覆盖未来对象修改方法。

以下变化必须重评并发安全：

- Award 加入 slice、map、pointer 或可变缓存；
- Strategy 保存惰性索引或 memoized alias table；
- 增加 `ChangeWeight`、`AddAward` 等原地修改方法；
- 缓存层返回共享对象并允许调用方修改；
- Repository 使用对象跟踪或 identity map。

### 7.3 复杂度与容量预算

| 操作 | 当前复杂度 | 分配 | 当前理由 | 触发优化的证据 |
| --- | --- | --- | --- | --- |
| `NewAward` | O(name runes) | 可能因 trim 产生字符串视图/值 | 名称上限小 | 构造吞吐画像证明文本检查成为瓶颈 |
| `NewStrategy` 校验 | O(n) | ID map O(n) | 一次检查集合不变量 | 大策略造成显著内存峰值 |
| `NewStrategy` 排序 | O(n log n) | 自有 slice O(n) | 稳定规范顺序 | 奖项数大或构造频繁且排序占比显著 |
| `Awards()` | O(n) | 每次 O(n) 副本 | 优先封装正确性 | profile 证明热路径复制影响 SLO |
| `Award(id)` | O(n) | 无额外长期索引 | 当前预期少量奖项 | lookup P95/P99 或规模证明线性扫描不足 |

当前没有最大 Award 数量。于是理论上，不受信任输入可使 map、slice、排序和返回副本消耗大量 CPU/内存。领域层暂不选择一个没有业务证据的魔法上限，但第 21 节 HTTP 入口必须先有请求体/数组数量限制；第 18 节也要考虑一条 Strategy 可关联多少行。真实配置规模或压测出现后，再决定上限应属于领域、运营政策还是 transport 防护。

### 7.4 时间预算

构造器没有 I/O、重试、取消或 timeout；它应该在调用 goroutine 内有界完成。其时间上界目前取决于：

- 名称最多 128 rune，单个文本扫描有界；
- Award 数量尚无上限，因此总体时间并非业务上有界；
- 排序 O(n log n)；
- `uint64` 运算为常量时间。

未来 Repository timeout、HTTP deadline、Redis timeout 和随机算法预算不能塞进领域对象。调用顺序应是外层先限制输入/设置 deadline，再获取数据并构造领域对象；构造错误不是依赖 timeout，也不应重试。

### 7.5 生命周期与关闭

本节对象不持有需要显式 `Close` 的资源。这个事实很有价值：

- 构造失败没有部分连接或 goroutine 泄漏；
- 单元测试无需外部清理；
- 对象可以由缓存、请求或应用服务按普通值生命周期管理；
- 领域代码不决定数据库连接池或 Redis client 的所有者。

第 19 与 24 节引入 Repository/cache adapter 时，连接与 client 生命周期应由应用装配层拥有，而不是 Strategy `Close()`。

## 8. 失败模型与恢复语义

### 8.1 构造失败是原子的

`NewAward` 或 `NewStrategy` 任一验证失败时返回零值加 error，不返回“尽量可用”的部分对象。原因是调用方无法可靠判断哪些不变量已经成立。具体失败包括：

- ID 为零；
- 名称为空、非法 UTF-8、含控制字符或超长；
- Weight 为零；
- Outcome 未知；
- Strategy 没有 Award；
- 嵌套 Award 为零值或不合法；
- 聚合内 Award ID 重复；
- totalWeight 求和溢出。

构造错误是确定性输入错误，不应该自动重试。恢复方式是修正输入或修复脏数据，而不是再次调用同一构造器。

### 8.2 部分成功

构造器逐项验证时可能已经在局部变量中累计了若干 ID 与 Weight，但这些状态不会发布到返回对象。失败后：

- 没有 Strategy 被返回为合法值；
- 没有外部状态被写入；
- 没有回滚动作；
- 没有日志副作用；
- 临时 map/slice 由 GC 回收。

这只证明内存构造无部分发布。第 18 节多行数据库写入必须另行使用事务和约束；第 19 节读取到一半失败也必须定义是整聚合失败、隔离脏行还是返回降级结果。

### 8.3 重复输入

- 重复调用 `NewAward` 使用相同输入，会得到等价值，不产生外部副作用；
- 重复调用 `NewStrategy` 使用相同集合，即便输入顺序不同，也会得到同一 ID 规范顺序；
- 一个 Strategy 内重复 Award ID 被拒绝，而不是后写覆盖前写；
- Award 名称重复被允许，因为名称不是身份；
- 重复构造不等于抽奖请求幂等，不能用于证明 `INV-03`。

### 8.4 乱序输入

调用方可按任意顺序提交 Award，构造器按 ID 规范化。这使对象避免依赖：

- SQL 未指定顺序的返回；
- map 遍历顺序；
- HTTP 数组顺序；
- 测试 fixture 编排顺序。

但如果旧版本曾将输入顺序用于随机区间或展示，升级到 ID 排序会改变行为。当前没有旧算法或存量数据，所以现在建立规范顺序可逆成本最低。第 20 节发布算法后，顺序将成为兼容性敏感点，任何修改都必须有版本或迁移策略。

### 8.5 旧版本与脏数据

当前没有数据库，因此还没有真实旧版本数据。未来可能出现：

- Outcome 使用未知旧字符串；
- 名称超过新上限；
- 重复 Award 行；
- totalWeight 溢出；
- Strategy 没有 Award；
- 数据库排序或 ID 类型与领域不兼容；
- 老缓存缺少 schema version。

Repository 不应通过反射或包内字段赋值跳过校验让脏数据“先跑起来”。第 19 节必须选择：加载整个聚合失败并告警、隔离配置、迁移修复，还是保留版本化兼容构造器。当前不预先决定恢复政策，但禁止无声丢弃无效 Award 后继续抽奖，因为那会改变概率分布。

### 8.6 取消与 deadline

领域构造器没有 context，不能被中途取消。对当前 128-rune 名称和预期小集合，这是有意的：纯 CPU 的短操作不应把 transport context 传入领域。若未来未设 Award 上限导致构造可被大输入拖长，应优先在 transport/application 层限制数量，而不是每次循环检查 HTTP context。

### 8.7 依赖抖动

本节没有 MySQL、Redis、HTTP 或消息依赖，因此没有依赖重试语义。未来 adapter 的暂时故障不能被转换成 `no_reward`：

- MySQL timeout 不是未中奖；
- Redis miss 不是未中奖；
- Benefit 不可用不是未中奖；
- 随机源失败也不是未中奖。

`no_reward` 只是一项合法候选被算法选中的业务结果。这个边界是防止“故障伪装成业务成功”的核心安全条件。

### 8.8 恢复人员可能犯的错误

未来运维或开发人员可能：

- 为了加载脏数据，临时放宽构造器而不迁移存量；
- 把未知 Outcome 映射成 `no_reward`，掩盖配置版本不兼容；
- 把 Weight 归一化后写回，因整数截断改变比例；
- 按数据库返回顺序构造算法区间，绕过规范排序；
- 将 totalWeight 作为可独立修改字段存储，造成双事实源；
- 把错误日志中的自由文本名称做 metrics label，造成高基数与隐私泄漏；
- 遇到全 `no_reward` 策略时擅自添加 reward，而没有产品审批；
- 将构造错误重试，形成热循环但永远不能成功。

恢复流程尚无 Runbook，因为本节没有运行时操作面；第 18～24 节出现真实持久化、发布或缓存恢复动作时才应增加对应 Runbook，而不是编造当前不存在的操作步骤。

### 8.9 错误兼容语义

当前错误通过 sentinel value 分类，并允许 `errors.Is`：

- 上层可以稳定区分缺失 ID、非法名称、零权重、未知 Outcome、重复 ID 和溢出；
- 重复 ID error 包装具体 ID，便于内部诊断；
- error 文本不是稳定机器协议，未来 HTTP/metrics 不应按字符串比较；
- Award 嵌套失败目前直接返回 Award 错误，没有数组索引/字段路径；
- 构造器不携带原名称，减少自由文本泄漏，但也降低精确运营诊断。

第 21 节若需要字段级 API 错误，应在 adapter/application 建立结构化映射或扩展领域错误类型。不能直接把内部 error 文本原样公开给客户端，也不能现在提前决定所有错误都是 HTTP 400 或 422。

## 9. 安全与隐私推导

### 9.1 最小权限

本节领域包没有数据库、文件、网络、环境变量或系统调用权限，只依赖 Go 标准库。这将攻击面限制在输入值与 CPU/内存预算上。

未来各层仍需遵守：

- HTTP adapter 负责认证和请求大小限制；
- application/Governance 负责谁能创建、修改、发布策略；
- Repository 只获得 Lottery 所需表权限；
- Redis cache 只保存派生配置，不能拥有修改权威事实的能力；
- 前端只能得到展示和操作所需字段；
- Benefit 只接受明确交付命令，不让 Lottery 直接改权益余额。

### 9.2 名称输入的现有防线

当前名称防线能降低：

- 非法 UTF-8 导致的编码歧义；
- 全空白名称造成的不可识别配置；
- 首尾空白形成肉眼相同、字节不同的名称；
- 换行、制表等控制字符破坏单行日志或界面；
- 无界字符串造成明显的存储和响应膨胀。

但它没有解决：

- HTML/JS/SQL escaping；这些必须由模板、JSON encoder 和参数化 SQL 完成；
- Unicode NFC/NFKC 规范化；视觉相同名称仍可能具有不同字节；
- bidi formatting、零宽字符和其他 `Cf` 格式字符；`unicode.IsControl` 不能被当作完整反欺骗过滤；
- homoglyph/confusable 名称，例如不同字符看起来相同；
- emoji 组合与 grapheme cluster 数量；
- 内容审核、商标、违法营销文案或监管披露；
- 名称中误填手机号、邮箱或其他个人信息。

因此“领域名称合法”只代表最小技术约束成立，不代表内容安全或合规审核通过。

### 9.3 ID 安全

`uint64` ID 紧凑但可能可枚举。当前没有 API，所以还没有越权暴露；第 21 节必须保证：

- 知道 Strategy/Award ID 不等于有权读取或使用；
- 服务端做对象级授权，不能依赖 ID 难猜；
- 日志只在需要时记录 ID；
- 浏览器 JSON 避免超过安全整数后丢精度；
- 若采用字符串编码，要明确格式、最大长度和前导零规范；
- 外部公开 ID 与内部主键是否分离，由真实安全和集成需求驱动。

### 9.4 秘密生命周期

本节对象不接收 secret、token、DSN 或 credential。Strategy/Award 名称也不应被用来承载这些内容。未来序列化、日志和缓存必须避免把认证上下文混入领域快照。

### 9.5 传输安全

本节没有传输。现有 Compose loopback 成功不能外推为未来 Lottery API 的生产 TLS、鉴权或 CSRF 防护。第 21 节开放 route 时必须重新审查：

- 谁可创建/查询/执行抽奖；
- 请求与响应是否包含用户或敏感配置；
- TLS 终止、same-origin、CSRF/CORS 和 replay；
- body、数组、名称和数值范围限制；
- 公开错误是否泄漏内部配置。

### 9.6 供应链

领域实现只使用 `cmp`、`errors`、`fmt`、`math`、`slices`、`strings`、`unicode`、`unicode/utf8` 等标准库能力，没有新增第三方依赖。这降低了本节供应链与版本更新面，但不证明 Go toolchain、构建产物或整个仓库供应链已审计。

### 9.7 公平性与合规不是一个布尔字段

合法 Weight 只说明数学输入可累加，不说明抽奖“公平”。真正的公平性至少还需要：

- 配置由谁批准，修改是否留痕；
- 展示概率与生效配置是否一致；
- 随机源和映射算法是否存在偏差；
- Strategy 版本是否在一次抽奖期间稳定；
- 库存耗尽或降级是否改变公开概率；
- no_reward 是否符合活动声明；
- 实际结果分布怎样监测，样本量和置信区间如何解释；
- 是否需要第三方审计、监管备案或地区限制；
- 用户争议时能否重建当时配置与结果，而又不泄漏可操纵随机性的秘密。

这些能力当前全部未实现，不能在项目介绍中写成已完成。

### 10.3 所有权与顺序测试

- 修改构造输入切片后，Strategy 内第一项不变：证伪“构造器保留调用方数组”。
- 修改 `Awards()` 返回切片后，再次读取不变：证伪“访问器泄漏内部数组”。
- 乱序输入后按 ID 升序读取：证伪“调用方偶然顺序成为领域状态”。
- 查找存在 ID 返回对应 Award，不存在 ID 返回 `(zero, false)`：证伪“未找到被误当成第一个或错误 Award”。

这些测试仍然不能证明深层引用复制、超大集合容量、同对象并发压力、数据库顺序、缓存反序列化或算法映射。

### 10.4 静态与竞态证据的边界

本节合理的工程检查包括：

- `gofmt`：只证明格式符合工具输出；
- `go vet`：只检查已实现的一组静态模式，不是完整形式验证；
- `go test`：证明已列用例在当前工具链和环境通过；
- `go test -race`：只对测试实际执行的并发路径查找数据竞争；没有执行的路径仍未知；
- `make verify`：证明仓库门禁整体通过，不代表所有业务页面真实接入或业务 SLO 达标；
- `git diff --check`：发现空白错误，不验证语义。

具体命令、环境、结果和清理项只由[第 17 节 QA](../../qa/lessons/lesson-17.md)记录。本文不预填“通过”。

### 10.5 本节证据明确不能证明的事项

即使全部测试绿色，也不能宣称：

- 已存在 MySQL 表、事务或恢复能力；
- Repository 能无损重建聚合；
- 概率抽奖算法已实现或无偏；
- 真实命中率符合 Weight；
- 一次请求只形成一个最终结果；
- HTTP API、鉴权、错误映射或 JSON ID 已正确；
- React 抽奖页真实调用后端；
- Redis 已接入或缓存一致性成立；
- reward 有库存或已交付；
- 配置已经审核、合规或公平；
- 10,000 RPS / P99 候选 SLO 已达到；
- 多进程、重启、故障或旧版本数据兼容已验证。

### 10.6 负向断言

本节最重要的负向证据不是“能构造一个对象”，而是这些非法状态不能通过公开构造边界：

```text
StrategyID == 0                     → 必须失败
AwardID == 0                        → 必须失败
trim 后空名称                       → 必须失败
非法 UTF-8 / 控制字符 / >128 rune   → 必须失败
Weight == 0                         → 必须失败
未知 AwardOutcome                   → 必须失败
空 Award 集合                       → 必须失败
零值 Award                          → 必须失败
同 Strategy 内重复 AwardID          → 必须失败
totalWeight uint64 溢出              → 必须失败
调用方修改输入/返回 slice            → 不能改变聚合
```

反过来，以下不是当前非法状态：

```text
单 Award Strategy                    → 当前允许
全部 no_reward                       → 当前允许
Award 名称重复                        → 当前允许
权重总和不等于 100/10000             → 当前允许
单项/总和恰好 MaxUint64              → 当前允许
输入 Award 乱序                       → 当前允许并规范排序
```

这组正反边界比“使用了 DDD 聚合”更能重放真实设计。

## 12. 需求未提但架构师会主动检查的点

### 12.1 `uint64` ID 与 JSON/JavaScript 精度

Go 和 MySQL 可以精确保存 `uint64` 范围，但浏览器 JavaScript 的 `number` 不能精确表示所有大于 `2^53-1` 的整数。若第 21 节直接输出：

```json
{"strategy_id": 18446744073709551615}
```

浏览器解析后可能得到被舍入的值，再回传时查到另一条记录或无法查找。可行方案包括：

- API 始终把 ID 编码成十进制字符串；
- 把可分配 ID 上限明确限制在安全整数范围；
- 使用外部 string/UUID ID，与内部主键分离；
- 前端使用 string/BigInt，但 JSON 本身仍需字符串协议。

当前不替第 21 节做决定，但这个风险必须在第一个 API 之前关闭。不能因为测试中的 ID 很小就忽略。

### 12.2 rune、byte 与 grapheme cluster

当前 128 rune 上限是“最多 128 个 Unicode code point”，不是：

- 最多 128 bytes；中文和 emoji 通常占多个 UTF-8 bytes；
- 最多 128 个用户感知字符；一个带多个组合标记的字素可包含多个 rune；
- 最多 128 个屏幕列宽；全角、emoji 和字体渲染不同；
- 已做 Unicode normalization；`é` 的预组合和分解形式可能具有不同 rune/byte 数；
- 已屏蔽所有不可见或 bidi 格式字符。

第 18 节必须验证数据库列、字符集和索引不会截断合法名称；第 22 节必须验证 UI 溢出和无障碍；真实国际化需求出现时再决定 grapheme 与 normalization 策略。

### 12.3 浅复制的未来风险

当前 `Award` 只含整数、string enum 和 string name；这些值复制后不暴露可修改集合，所以 slice 元素浅复制足够。

还有一层更隐蔽的浅复制：`Strategy` 本身是值类型，复制一个 Strategy 会复制 slice descriptor，而不会复制内部 Award 数组。当前包外没有任何原地修改方法，访问器又只返回副本，所以两个 Strategy 值共享只读数组并不会破坏语义；但这份安全依赖“永久只读”前提。若未来增加包内 mutation、惰性排序或可变缓存，即使外部代码只做了普通赋值，两个 Strategy 副本也可能相互影响。

如果未来 Award 加入：

- `[]Rule`；
- `map[string]string` metadata；
- `*BenefitDescriptor`；
- 可变图片/本地化集合；

现有输入/输出 slice 复制只能复制引用头，调用方仍可通过内部引用修改聚合。新增这类字段的 PR 必须：

1. 明确所有权；
2. 选择深复制、只读值类型或专用不可变容器；
3. 增加嵌套别名测试；
4. 重新评估并发安全和缓存序列化；
5. 更新本手记/ADR。

同理，首次增加 Strategy 修改方法时，不能只补一个 pointer receiver：必须决定它是返回全新 Strategy 的 copy-on-write 命令，还是把聚合改成有明确身份与版本的受控可变对象，并增加“复制后修改互不影响”的证据。

### 12.4 没有最大 Award 数量

领域未设上限避免无证据的“最多 100 个”，但这不是无限输入安全。风险包括：

- 构造 map/slice 内存放大；
- O(n log n) 排序耗时；
- `Awards()` 每次复制；
- API 响应膨胀；
- 数据库多行事务与锁范围；
- Redis value 过大；
- 第 20 节算法或第 22 节 UI 无法有效展示。

第 21 节必须有 transport 级请求体和数组上限，即使领域上限仍未决定。之后用真实运营场景、表大小、缓存 value、延迟和成本决定是否把上限提升为领域政策。

### 12.5 `MaxUint64` 总权重虽合法，但会把问题推给算法

当前允许 totalWeight 恰好为 `math.MaxUint64`，数学上没有溢出。但第 20 节不能天真地：

- 转成 `int` 或 `int64`；
- 计算 `totalWeight + 1`；
- 用有偏的 `% totalWeight`；
- 让 `0` 与上界的闭区间/开区间混乱；
- 累加时再次溢出。

算法必须显式定义随机区间并覆盖 0、边界、最后一个 bucket 与 MaxUint64。若标准随机 API 无法安全覆盖全范围，可能需要限制 Weight 上界；那会反过来触发本节契约重评。

相对权重还带来“数学等价但字节不等价”的问题：`1:3` 与 `100:300` 分布相同，却会产生不同 total、审计 diff、缓存值和 Strategy 版本。当前构造器不自动求最大公约数做约分，因为静默改写运营输入会丢失原始配置意图，也会让后续审计难以解释；代价是某些本可约分的极大权重组合会因求和溢出被拒绝。第 20/31 节需要决定：只在 UI 提示可约分、在发布前显式规范化，还是把原始值与规范值分别保存。无论选择哪一种，都不能让算法、API 与数据库各自私下归一化。

Weight 与 ID 一样是 `uint64`，若第 21 节把它直接编码成 JSON number，同样存在超过 JavaScript 安全整数后的舍入风险。API 需要对 ID 和 Weight 分别制定表示规则；“ID 用字符串”不会自动解决 Weight。

### 12.6 名称不是安全标识，也不是本地化模型

Strategy/Award 名称用于人类识别，但：

- 可以重复；
- 可以修改；
- 没有 locale；
- 没有稳定 code；
- 可能含视觉混淆字符；
- 不适合做 metrics label、缓存 key 或授权依据。

运营后台应同时展示 ID 或稳定 code；国际化出现时应建立本地化投影，而不是把多语言 JSON 塞进一个 name 字段。

### 12.7 全 `no_reward` 与单 Award 的治理位置

领域当前允许两者，因为它们在数学与结构上都完整：

- 单 Award 可以表达 100% reward、100% no_reward、测试配置或确定性回退；
- 全 no_reward 可以表达暂时不提供奖励但仍返回正常结果的配置。

然而“可构造”不等于“可发布”。上层运营政策可能要求：

- 至少一个 reward；
- reward 总比例高于某下限；
- 全 no_reward 只能处于草稿/维护状态；
- 单 Award 必须标注为确定性活动；
- 展示文案必须与概率一致。

将这些政策放在 application/Governance 或 Strategy 生命周期规则中，比现在硬编码更可演进。若业务确认它们永远非法，再把规则提升为领域不变量并迁移存量。

### 12.8 Award ID 唯一性的范围

代码只保证一个 Strategy 内无重复 ID。第 18 节必须明确：

- Award 是全局 ID + `strategy_id` 外键，还是复合主键；
- Award 是否可能从一个 Strategy 移动到另一个；
- URL/cache key 是否只给 Award ID 就足以定位；
- 数据合并和导入时怎样避免冲突；
- Strategy 删除或版本化时 Award ID 是否复用。

在这个决定前，外部 API 不应假设 Award ID 单独全局可寻址。

### 12.9 错误诊断与隐私的张力

当前 sentinel error 易分类，但嵌套 Award 错误不携带数组位置，运维可能只看到“award name invalid”而不知道哪一项。直接把名称放进 error 又可能泄漏自由文本或 PII。

未来可考虑结构化内部错误：包含安全字段如 Award ID、字段 code 和索引，但公开 API 只返回受控路径与错误 code；日志根据权限记录最小必要信息。这个决定等到真实 adapter 有上下文时再做。

### 12.10 规范排序与算法兼容

排序不仅影响文档美观，还可能影响相同随机值对应哪个 Award。第 20 节一旦将权重累计区间绑定当前 ID 顺序：

- 新增一个 ID 较小的 Award 会移动后续区间；
- 仅修改 ID 可能改变所有映射；
- Strategy 版本切换期间必须保证一次请求看到单一版本；
- 结果重放不能只保存随机值，至少要保存策略版本/候选快照。

这不是说 ID 排序错误，而是排序在算法上线后会成为兼容契约。第 46 节中奖快照必须考虑这一点。

### 12.11 配置变更与历史重放

当前对象不可变，但系统还没有 Strategy version。不可变内存值不等于历史不可变：Repository 未来可能直接覆盖数据库行。若用户争议或补偿需要重建当时结果，仅有当前 Strategy 不够。

必须在首次允许运营修改或首次保存 DrawResult 前回答：

- Strategy 是更新原版本还是创建新版本；
- 生效时间与 Activity 引用怎样原子切换；
- DrawResult 保存 Award 名称/Outcome/Weight 快照到什么程度；
- 删除和归档如何处理；
- 缓存如何区分版本；
- 审计记录由谁拥有。

### 12.12 性能候选目标不能由对象推导

NFR 中抽奖决策 10,000 RPS、P99 ≤ 150ms 是候选目标，不是本节结果。纯对象测试不包含：

- MySQL 查询；
- Redis 命中/回源；
- 随机算法；
- HTTP JSON；
- 用户资格与库存事务；
- 并发和故障注入。

本节最多能为后续基准提供确定输入模型，不能把无 I/O 的构造性能宣传成业务接口性能。

### 12.13 发布顺序与兼容窗口

当前无外部状态，发布顺序简单。进入后续章节后，应按兼容窗口演进：

1. 先发布能读取旧/新格式的代码或 schema；
2. 再迁移/回填数据；
3. 再切换写入；
4. 等旧消费者退出后移除兼容；
5. Redis 派生缓存按 schema/version 失效重建。

特别是 Outcome 新枚举和 ID JSON 表示不能单边修改，否则旧客户端会把未知值当失败或丢精度。

### 12.14 可观测性与指标基数

未来可观测性应记录：

- `strategy_id` 是否作为 trace attribute（需评估基数与敏感性）；
- 构造错误按有限 error code 计数；
- 不把 Strategy/Award 名称作为 metrics label；
- 加载脏配置、缓存版本不兼容和 total overflow 需要告警；
- 实际分布监控必须有正确样本窗口和期望版本；
- 业务 no_reward 与技术 error 必须分开统计。

否则系统可能把依赖故障造成的无结果误计成正常未中奖率。

### 12.15 合规、审计与伦理

面向真实营销抽奖，架构师还要询问：

- 是否必须公示概率、奖品数量、活动规则和变更时间；
- 未成年人、地区、会员等级是否有准入限制；
- 是否允许动态调权，谁批准，是否要保存变更前后值；
- no_reward 文案是否构成误导；
- 是否要为用户争议提供可核验记录；
- 随机种子和审计信息如何既可验证又不被用于预测；
- 个人数据最小化、保留期和删除请求怎样处理；
- 监管或合同是否要求第三方随机性/审计。

当前模型没有回答这些问题；在公开活动前必须由产品、法务、安全与工程共同关闭，而不是让 Weight 类型替代合规评审。

### 12.16 成本与缓存诱惑

不可变 Strategy 很适合缓存，但“适合”不等于第 17 节就要加 Redis。过早缓存会增加：

- 双重序列化模型；
- 失效与版本问题；
- 回源风暴；
- 缓存 value 大小；
- 旧 schema 兼容；
- 故障降级误判。

第 24 节应以第 19/20/21 节的真实读取路径和测量为输入，Redis 只做派生加速，MySQL/领域构造仍保持事实边界。

| R17-23 | 领域包不需要 logger/metrics | 纯函数返回分类 error | 缺少请求上下文内诊断 | API/Repository 接入后无法定位 | 在 application/adapter 加观测，不把 logger 注入实体；第 19/21 节复核 |
| R17-24 | 标准库依赖足以实现当前契约 | 当前实现无第三方库 | grapheme/UUID/decimal 等需求可能新增依赖 | 新需求与实现复杂度 | 新增依赖前做供应链、许可证与维护评估 |

| R17-27 | 聚合整体加载可接受 | 当前最小模型和预期小集合 | 大集合加载、缓存和事务冲突 | 真实策略规模、DB 查询/内存 profile | 第 19/24/95 节测量；必要时引入快照或派生结构 |

风险账本不是一次性清单。每个后续章节关闭或改变条目时，应在对应设计手记记录新证据，而不是回写历史让当时的未知消失。

## 14. 未来演进问题

### 14.1 第 18 节：第一次正式业务建表必须回答

1. Strategy 与 Award 分成哪两张表，表名如何反映聚合所有权？
2. `uint64` 映射 MySQL `BIGINT UNSIGNED` 还是限制在 signed 范围？Go driver 扫描边界如何验证？
3. Award ID 是全局 PK 还是 `(strategy_id, award_id)` 复合键？
4. 如何用约束保证一个 Strategy 内 Award ID 唯一？
5. Weight 使用何种列类型，怎样防止 0 和溢出？
6. Outcome 用字符串列 + check、MySQL ENUM 还是代码字典？升级新值如何兼容？
7. 名称使用什么字符集/collation，`VARCHAR(128)` 是否与 128 rune 契约一致？
8. 数据库能否保证 Strategy 至少一个 Award，还是必须依赖事务/application 校验？
9. 是否存 totalWeight；如果存，哪个是事实源，怎样防漂移？
10. 规范顺序是否仅由 ID 推导，是否需要 position？
11. 删除 Strategy 时 Award 的生命周期和外键策略是什么？
12. 初始数据与 Migration 回滚/前向修复怎样处理？

### 14.2 第 19 节：Repository 必须回答

1. Repository 返回完整 Strategy 还是 row/DTO？
2. 如何保证 N+1、事务快照和排序语义？
3. 读取到无 Award、重复、未知 Outcome 或超限名称时如何失败？
4. 是整聚合失败、隔离配置还是提供迁移兼容？禁止无声丢行。
5. 写 Strategy 和 Awards 是否在同一事务；部分失败怎样回滚？
6. 并发更新采用版本号、锁还是暂时只读？
7. Repository interface 放在何处，是否泄漏 sqlx/MySQL 类型？
8. context/deadline 归应用端口还是实体？
9. ID 生成由 DB、应用还是外部系统负责？
10. 如何集成测试最大 ID、Unicode、重复约束和脏数据？

### 14.3 第 20 节：概率算法必须回答

1. 随机源接口怎样注入，测试如何提供确定序列？
2. 随机区间是 `[0,totalWeight)` 还是 `[1,totalWeight]`，边界怎样证明？
3. 如何处理 totalWeight == MaxUint64 而不做 `+1` 或有符号转换？
4. 如何避免 modulo bias？
5. 遍历顺序是否明确使用 Strategy 的 ID 规范顺序？
6. 第一个/最后一个 bucket、权重 1、单 Award、全 no_reward 如何测试？
7. 随机源失败返回 error 还是有 fallback？绝不能伪装 no_reward。
8. 单元边界测试与统计分布测试分别能证明什么？
9. 是否需要密码学随机性，威胁模型与成本是什么？
10. 基准如何避免把纯算法 QPS宣传成端到端 Lottery SLO？

### 14.4 第 21 节：第一个 Lottery API 必须回答

1. `uint64` ID 以 JSON string 还是 number 传输？
2. DTO 的 Weight 是 string、number 还是展示百分比？怎样避免精度/范围问题？
3. 领域 sentinel error 映射哪个稳定业务 code 和 HTTP status？
4. 哪些内部细节可以公开，哪些只进受控日志？
5. 如何限制 body、名称和 Award 数量，防止资源滥用？
6. 谁可查询配置、谁可触发抽奖、谁可创建或修改策略？
7. request ID、trace、审计和 metrics 怎样避免高基数/PII？
8. 结果未知、配置非法、未找到和依赖失败怎样区分？
9. API 是执行选择还是创建最终 DrawResult；当前章节是否仍没有 `INV-03` 证据？
10. OpenAPI/前端类型如何保持枚举向后兼容？

### 14.5 第 22 节：React 抽奖页必须回答

1. 移除或明确隔离现有 Mock，怎样证明真实请求走 Go API？
2. ID 全程是否保持 string，避免 JavaScript number 舍入？
3. loading、error、no_reward、reward 和结果未知怎样分别呈现？
4. 重复点击、页面刷新、AbortController 和迟到响应怎样处理？
5. 名称如何 escape、截断、支持 128-rune 极端文本和无障碍？
6. 单 Award、同名 Award 与全 no_reward 的用户体验是否允许？
7. 浏览器证据能否关联 request ID、API 日志和数据库/算法事实？

### 14.6 第 23 节：规则升级必须回答

1. 哪些是 Strategy 配置规则，哪些属于 Participation 资格？
2. 发布政策是否要求至少一个 reward？
3. 规则失败与 no_reward 是否严格分离？
4. 规则顺序、短路、解释和版本怎样表达？
5. 不把 User 状态塞回 Strategy 的机制是什么？

### 14.7 第 24 节：Redis 缓存必须回答

1. MySQL/Repository 是否保持唯一事实源？
2. cache key 是否包含 Strategy ID 与版本？
3. value schema 如何版本化，`uint64` 与 Outcome 如何编码？
4. 命中后是否重新通过领域构造器验证？
5. 更新时采用删除、双删、版本 key 还是事件失效？
6. Redis 不可用、旧 value、反序列化失败和穿透时怎样回源？
7. 大 Strategy value、TTL 抖动、热 key 和回源风暴如何测量？
8. 缓存命中率与端到端 SLO 如何记录，不能把环境中 Redis 运行当作业务接入？

### 15.4 证据总边界

截至本节，可以诚实地说：

> GrowthOS-Go 在 Lottery 上下文建立了最小 Strategy 聚合与 Award 实体，通过私有字段、构造器、正整数相对权重、显式 reward/no_reward、名称约束、重复与溢出检查、规范排序以及防御复制，使未来持久化和算法只能消费满足当前不变量的配置对象。

截至本节，不能说：

> 已实现随机抽奖、概率公平、抽奖幂等、最终结果持久化、库存控制、权益发放、Lottery API、真实 React 抽奖页、Redis 缓存、高并发抽奖或生产合规。

这条诚实边界本身就是本节最重要的架构产物：先把对象能承诺的事实说准确，后面的每一层才能用新证据扩展，而不是用新技术覆盖旧歧义。
