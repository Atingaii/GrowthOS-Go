# 第 8 节：画 V0 系统设计

**状态：** 已完成

**完成日期：** 2026-08-09

**阶段：** 产品需求与系统分析

**本节不写 Go 业务代码、不建业务表、不发布真实 API。V0 是逻辑设计基线，不是最终架构，也不是当前已实现能力的宣传图。**

## 1. 本节业务诉求

前 7 节分别确定了产品定位、用户和运营流程、AI Operator、安全审批、领域事件、业务边界与非功能目标，但信息散落在多份文档里。进入工程阶段前，需要一套最小系统设计回答：

- 谁在 GrowthOS 边界内外；
- 平台必须承担哪些业务能力；
- 哪个上下文有权确认哪类事实；
- 第一版为什么使用模块化单体；
- 当前实现、近期构建和远期方向如何区分；
- 哪些技术和数据结构现在仍不应该决定。

## 2. 上一版系统状态

当前已确认八个候选限界上下文：Marketing、Participation、Lottery、Benefit、Feed、Behavior & Analytics、Governance 和 AI Operations。第 7 节还给出了核心事实优先、分析和 AI 可降级的质量顺序。

但如果直接把这些上下文画成八个服务，会产生三个错误：

1. 把业务语言边界误解成部署边界；
2. 把第 73 节后的技术路线误写成当前事实；
3. 在没有业务表和运行数据时提前锁定 RPC、MQ、缓存与数据所有权实现。

因此本节只建立 V0 逻辑边界，并单独给出近期模块化单体运行形态。

## 3. 方案分析

| 方案 | 优点 | 问题 | 结论 |
| --- | --- | --- | --- |
| 直接画最终微服务和全套中间件 | 看起来完整，方便展示技术清单 | 无法证明拆分理由，掩盖未实现状态，后续文档容易漂移 | 不采用 |
| 只画一个 GrowthOS 大方框 | 简单，不提前设计技术 | 看不出事实所有权、治理与外部边界 | 不采用 |
| 逻辑产品/上下文图 + 近期运行形态 + 状态标记 | 同时保留业务结构和演进空间，可区分边界与部署 | 需要持续维护状态 | 采用 |

## 5. 产品架构的关键判断

### 5.1 Feed 是营销触达入口

Growth Feed 不是通用社交内容流。它承载活动、优惠券、签到、任务等营销内容，通过召回、过滤、排序和频控把适合的内容交给用户，再以曝光、点击、参与和转化反馈调整后续触达。

### 5.2 外部交易不是平台内部订单

GrowthOS 会接收支付、退款和交易订单系统确认的事实，用于返利、转化和归因；但 V0 不拥有商品、购物车、支付和履约。营销活动订单与用户参与订单也不能冒充电商交易订单。

如果以后要加入自营电商，需要重新分析商品、购物车、交易、支付和履约上下文，而不是给 `activity` 表不断加字段。

### 5.3 治理是人工与 AI 的共同控制面

人工后台和 AI Operator 的写操作都需要权限、审批、风险和审计。AI Operations 负责理解和编排，Governance 决定操作是否允许；模型不能直接写数据库或宣布活动、发券、调积分成功。

## 6. 领域与部署不能画等号

限界上下文解决语言、规则和事实所有权问题，服务解决部署、隔离和扩缩容问题。二者可能一一对应，也可能多个上下文运行在同一个进程中。

GrowthOS 第一版选择：

```text
一个 Go 进程
  + 多个清晰业务模块
  + 一个 React 前端工程
  + 按需求出现的 MySQL Migration
```

只有后续出现不同负载、发布节奏、可用性、合规或团队边界，并且拆分收益能够验证时，才拆独立服务。

## 7. 数据库变化

**无。**

本节没有足够业务细节决定表、字段、索引和事务。第 13 节只建立 MySQL 连接与 Migration 机制，第 18 节才因 Strategy 和 Award 需求创建第一批业务表。

因此本节不会：

- 预建八个上下文的空库；
- 输出最终 ER 图；
- 为未来消息和服务拆分增加技术表；
- 锁死 Migration 编号。

## 11. 本节不做什么

- 不做 Go HTTP 健康接口、配置、日志或错误码；
- 不创建业务数据库和 Migration；
- 不引入 Redis、RocketMQ、Nacos、ClickHouse 或 OpenSearch；
- 不确定最终服务数、部署拓扑和云平台；
- 不实现真实前后端联调；
- 不把课程路线图中的能力写成当前交付。
