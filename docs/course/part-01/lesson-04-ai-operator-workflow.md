# 第 4 节：设计 AI Operator 工作流

**状态：** 已完成

**完成日期：** 2026-08-08

**阶段：** 产品需求分析

**本节不写 Agent 代码、不接入 LLM、不建业务表、不新增真实 API。**

## 1. 本节目标

第 3 节明确了人工运营如何创建、审批、发布和复盘活动。本节设计 AI 如何在不削弱这些控制的前提下参与运营。

AI Operator 的目标不是让一句自然语言直接变成生产写操作，而是建立：

```text
自然语言目标 → 澄清 → 查询 → 结构化计划 → 风险校验
→ 人工确认/审批 → Tool 执行 → 结果验证 → 审计
```

## 2. AI Native 不等于聊天框加超级权限

如果 AI 能直接改数据库、自动批准自己的任务，或把超时当成失败后盲目重试，那么它只会放大已有风险。

GrowthOS 中的 AI 是受控协作者：它理解目标、组织信息、生成草稿和编排业务 Tool，但业务规则、权限、预算、审批和事实记录仍由确定性的系统执行。

## 3. 主任务示例

运营提出：

> 给连续 14 天未登录、近 90 天有消费的会员设计一个召回活动，通过 Feed 触达，奖励为 10 元优惠券，总预算不超过 2 万元，下周一开始运行 7 天。

AI 首先应识别目标、人群、渠道、权益、预算和时间约束，再询问缺少的保护指标、频控、优惠券门槛或审批人。之后才查询历史数据并生成草稿计划。

完整流程、风险矩阵、任务状态和 Tool 结果语义见[AI Operator 工作流 v1](../../product/ai-operator-workflow-v1.md)。

## 4. AI 的四类参与方式

### 4.1 查询与解释

AI 可以查询有权限的数据，并用人话解释人群规模、历史活动、库存、预算消耗和漏斗变化。每个结论都要展示数据来源和时间，估算不能写成精确承诺。

### 4.2 建议与草稿

AI 可以建议人群、频控和权益组合，或创建未发布草稿。建议不自动成为配置，草稿不等于已审批或已发布。

### 4.3 申请与执行

AI 可以汇总计划、成本和风险并发起审批。在有效审批和运行时权限都满足后，才可调用受控写 Tool。高风险操作的申请人不能成为自己的审批人。

### 4.4 监控与协助止损

AI 可以发现预算、失败率或投诉异常，解释影响并建议暂停。自动止损只能基于预授权、边界清晰的紧急策略，执行后立即产生通知和审计。

## 5. 为什么必须是结构化计划

“我会帮你创建活动”无法评审。一个可执行计划至少包含：

- 要调用的 Tool 和顺序；
- 关键参数、数据来源和更新时间；
- 影响人数、预算和最坏成本；
- 可撤销、不可逆和需审批步骤；
- 配置差异和假设；
- 失败、重试、补偿与人工接管方式。

运营可以修改单个草稿参数或拒绝计划，不能只能“一键全部同意”。

## 6. 审批不是一句“我同意”

审批绑定计划版本、Tool 版本、环境、租户、人群、预算、权益和关键参数。扩大人群、提高预算、修改权益、切换环境、权限变化或审批过期后，原审批不能继续使用。

执行时还要重新鉴权。Tool 能被发现，不代表当前用户在任何参数下都能调用。

## 7. Tool 超时为什么不能直接重试

Tool 超时只代表调用方没有及时收到结果，不代表业务没有执行。对创建活动、发券、调积分等写操作直接重试，可能产生重复业务。

正确处理是使用业务请求号查询原操作状态：明确未执行才能按策略重试；结果未知则进入人工或补偿流程。

## 8. 必须诚实表达部分成功

多步骤任务可能创建草稿成功、绑定权益成功，但提交审批失败。AI 必须显示已完成对象和失败步骤，将任务标记为“部分成功”，而不是说“操作失败”后重跑全部，也不能说“活动已创建完成”。

模型文字只是解释，Tool 的结构化返回和后续查询才是业务结果证据。

## 9. AI 工作台需要展示什么

AI Operator 不应只有聊天区域，还要展示计划、版本、Tool 步骤、关键参数、预算风险、审批状态、逐步结果、业务对象 ID、失败恢复入口和 Trace。运营可以随时取消未执行步骤或接管任务。

现有前端 Agent 页面只是设计与 Mock 框架，不能作为本工作流已经实现的证据。

## 10. 当前不提前决定什么

本节不决定：

- 最终 LLM 厂商、模型或 Prompt；
- 最终 MCP 协议表、Agent 任务表和审批表；
- Planner 的实现算法或 Agent 框架；
- Tool Schema、风险计算和自动审批的最终代码；
- RAG、Prompt Injection 检测和 Agent Evaluation 的完整实现。

这些能力在第 81～93 节由真实协议与业务需求推动实现。

## 12. 本节复盘

AI Operator 的价值是降低运营理解和编排复杂度，而不是移除控制。自然语言负责表达目标，结构化计划负责评审，业务 Tool 负责执行，权限与审批负责授权，业务查询负责验证，审计负责追责。

只有这些边界同时成立，AI 才能安全地进入真实营销平台。

## 13. 留给第 5 节的问题

用户、人工运营和 AI Operator 三条旅程已经建立。下一节需要通过事件风暴识别：

- 哪些动作会产生必须保存的领域事件；
- 哪些只是命令、查询或界面状态；
- 活动、参与、抽奖、权益、行为、审批和 Tool 调用如何关联；
- 正常事件、失败事件和补偿事件分别是什么；
- 哪些事件属于同一领域，哪些需要跨边界协作。
