# 第 6 节：第一次划分限界上下文

**状态：** 已完成

**完成日期：** 2026-08-09

**阶段：** 产品需求分析

**本节不拆微服务、不建业务表、不新增真实前端 API。**

## 1. 本节目标

第 5 节已经把活动创建、审批、触达、参与、抽奖、权益交付、行为反馈和 AI Tool 调用还原为业务事实。本节继续回答：这些事实分别属于哪套业务语言，谁有权确认事实成立，跨边界时应交换什么。

本节产出的是限界上下文 v1 假设。它帮助后续代码和数据库保持职责清晰，但允许被新需求推翻，不是最终微服务图。

## 2. 限界上下文不是什么

必须先避免三个常见误解：

```text
Bounded Context != 微服务
Bounded Context != 数据库
Bounded Context != Go package
```

限界上下文首先是一套模型和语言有效的边界。同一个词在边界内必须含义稳定，不同边界可以拥有不同模型。当前系统仍采用 Modular Monolith；未来是否拆服务、独立数据库或使用 RPC/MQ，要由团队协作、负载、可用性和一致性需求推动。

## 3. 为什么原来的领域名称太粗

第 1 节最初使用了 `Marketing`、`Lottery`、`Account`、`Benefit`、`Feed`、`Behavior` 和 `AI`。事件风暴暴露了几个问题：

- `Account` 可能表示登录账户、活动参与次数、积分余额或财务账户，无法指导所有权；
- 审批、权限和审计同时服务人工运营与 AI，放进 `AI` 会产生两套治理规则；
- 抽奖选中奖品和权益实际到账是两个事实，不能由一个模型含糊确认；
- Feed 负责“展示什么”，Behavior 负责“发生了什么以及如何分析”，生命周期不同；
- 活动负责目标和生命周期，Strategy 负责抽奖决策，二者不能互相替代。

因此 v1 不按页面菜单或技术组件划分，而按语言、业务规则、生命周期、事实所有权和变化原因划分。

## 4. v1 的八个限界上下文

### 4.1 Marketing：营销活动

负责活动草稿、版本、目标、预算、投放渠道和生命周期。只有 Marketing 能确认“活动已发布”“活动已暂停”“活动已结束”。

它不负责概率抽奖、用户参与次数、权益到账、Feed 排序或 AI 推理。审批通过只是发布前置条件，不等于活动已发布。

### 4.2 Lottery：抽奖策略

负责 Strategy、Award、概率装配、抽奖规则判断和结果选择。只有 Lottery 能确认“抽奖已完成”和“奖品已选定”。

Strategy 是可复用的决策配置，不是面向用户、带时间窗的 Activity。Lottery 选出奖励描述，但不直接修改积分或优惠券事实。

### 4.3 Participation：活动参与

负责用户参加活动时的资格、参与次数、活动 SKU 额度、参与订单和幂等语义。只有 Participation 能确认“用户已参与”。

本节用 Participation 替代含糊的裸 `Account`。后续若需要账户模型，必须明确写成“活动参与账户”“积分账户”等完整名称。

### 4.4 Benefit：权益

负责 Reward 对应的 Points、Coupon 和其他权益的发放、持有、流水、领取、核销与补偿。只有 Benefit 能确认“积分或优惠券等权益已到账”。抽奖奖励若是活动参与次数，Benefit 发起交付，Participation 仍是次数事实的确认方。

抽奖结果是权益交付的输入，不代表交付已经成功。余额和不可变流水的具体设计等真实需求出现后再完成。

### 4.5 Feed：增长触达

负责 FeedItem、候选召回、过滤、排序、频控、游标和实验分配，让合适的营销内容触达用户。

Feed 不拥有活动和优惠券主数据，只消费必要摘要，并在展示模型中保留当前查询需要的引用或快照。Feed 只能确认“候选内容已返回”；客户端上报并被采集后，Behavior & Analytics 才能记录可分析的曝光事实。

### 4.6 Behavior & Analytics：行为与分析

负责曝光、点击、参与、领取、使用、转化等行为采集，以及画像、漏斗、实验指标和归因结果。只有该上下文能确认“分析指标已生成”。

分析数据允许延迟、重复和纠正，但不能反向改写 Participation 或 Benefit 的交易事实。行为事件与领域事实相似时，也必须保留来源和语义差异。

### 4.7 Governance：治理

负责人工后台和 AI 共用的身份权限、审批策略、风险等级与审计。只有 Governance 能确认“审批已通过”或“审批已拒绝”。

审批通过不等于活动发布成功、权益已经发放或 Tool 已经执行。把治理独立出来，可以避免人工操作与 AI 操作各维护一套权限和审批规则。

### 4.8 AI Operations：AI 运营

负责 AI Task、意图识别、结构化计划、Tool 编排、执行进度和人工接管。只有 AI Operations 能确认“AI 计划已生成”“AI 任务已完成”。

AI 不拥有活动、权益或指标事实。模型输出是建议；业务结果必须来自受控 Tool 和对应业务上下文的验证。

## 5. 主业务协作链

```text
Governance 审批
  ↓
Marketing 发布活动
  ↓
Feed 获取可投放活动摘要并触达用户
  ↓
Participation 校验资格与次数，确认参与事实
  ↓
Lottery 计算抽奖结果
  ↓
Benefit 发放权益
  ↓
Behavior & Analytics 采集反馈并生成指标
  ↓
Feed / Marketing 根据反馈优化策略
```

AI Operations 不能横跨边界直接修改数据。它只能发现受控 Tool，经 Governance 完成权限与审批检查，再调用 Marketing、Feed、Benefit 或 Behavior & Analytics 提供的业务能力。

这张链路只表示职责与依赖，不表示所有步骤必须同步，也不表示已经选择 HTTP、gRPC 或 RocketMQ。

## 6. 事实所有权

| 业务事实 | 唯一确认方 | 不能替代它的信号 |
| --- | --- | --- |
| 审批已通过 | Governance | 审批按钮已点击、AI 建议通过 |
| 活动已发布 | Marketing | 审批通过、页面提示成功 |
| 用户已参与 | Participation | 点击活动、行为埋点已接收 |
| 抽奖已完成、奖品已选定 | Lottery | 随机函数返回、前端动画结束 |
| 积分或优惠券等权益已到账 | Benefit | Lottery 中奖、发放请求已提交 |
| 活动参与次数已增加 | Participation | Benefit 发起次数奖励交付 |
| Feed 候选内容已返回 | Feed | 召回完成、排序完成 |
| Feed 内容已曝光 | Behavior & Analytics | Feed 接口返回候选列表、页面开始渲染 |
| 漏斗指标已生成 | Behavior & Analytics | 原始事件已写入、单次转化发生 |
| AI 计划已生成 | AI Operations | LLM 返回了一段未解析文本 |

一个事实只能有一个权威确认方，其他上下文保留的是引用、快照、查询投影或集成事件，不能形成第二个事实源。

## 7. 统一语言 v1

| 术语 | 当前统一含义 |
| --- | --- |
| Activity | 面向用户、带时间窗和生命周期的营销活动；中文统一称“活动” |
| Strategy | Lottery 中可复用的抽奖决策配置，不等于活动 |
| Rule | 某个上下文内部的确定性业务约束，使用时必须说明语境 |
| Participation | 用户对活动的一次受控参与事实 |
| Quota | 用户可使用的活动参与次数，不等于积分余额 |
| Reward | 业务承诺给用户的奖励描述 |
| Benefit | 已进入发放、持有和使用生命周期的具体权益 |
| Event | 已经发生的业务事实，不是按钮动作、页面状态或数据库日志 |
| Plan | AI 的结构化执行计划，不是营销活动 |
| Task | 系统或 AI 的执行任务，不能泛指活动 |
| Account | 禁止脱离语境单独使用，必须写明活动参与账户、积分账户等 |

代码名称将在相应实现章节结合 Go 习惯决定，本节不通过中英文术语提前锁定包名和表名。

## 8. 跨上下文协作原则

跨边界的信息分为四类：

1. **命令：** 请求另一个上下文执行受控动作，接收方仍有权拒绝；
2. **查询模型：** 为读取场景提供的摘要或投影，不转移事实所有权；
3. **集成事件：** 把已确认的业务事实通知其他上下文；
4. **审计记录：** 说明谁在何时请求、批准或执行，不代替领域事实。

上下文内部领域事件不必全部对外公开。跨上下文事件需要稳定语义和最小必要快照，但具体契约、版本、同步/异步方式和一致性策略留给后续章节。

## 9. 外部系统边界

当前识别但不纳入 GrowthOS 核心模型的外部系统包括：

- 用户、会员和身份认证系统；
- 支付、交易或订单系统；
- 外部券中心、短信、Push 等渠道；
- LLM Provider；
- 企业权限或组织目录。

GrowthOS 可以通过防腐层适配这些系统，但不能假设自己拥有对方的数据生命周期。用户标签、订单转化和外部券状态都需要明确来源。

## 10. 当前假设与演进触发条件

- Participation 与 Marketing 当前分开建模；若后续规则始终共同变化且没有独立生命周期，可重新合并评估；
- Points、Coupon 和 Quota 暂归 Benefit；当团队、合规或负载差异足够大时再讨论拆分；
- Behavior 与 Analytics 暂为一个上下文；采集和分析出现完全不同的团队及运行约束后再拆；
- Governance 同时服务人工与 AI；若平台接入企业级统一 IAM，应通过外部系统适配而不是复制权限事实；
- Feed 的曝光确认语义需要在行为协议章节继续验证，当前不把接口返回等同于真实曝光。

## 11. 本节不做什么

- 不确定最终微服务数量、独立数据库数量或部署拓扑；
- 不创建表、索引、Migration、Topic、RPC 或 HTTP 契约；
- 不把八个上下文机械映射为八个 Go 顶层包；
- 不决定调用一定同步或异步；
- 不绘制最终 ER 图或最终聚合模型；
- 不修改第 14 节前端 Mock 页面来伪装业务能力。

## 13. 复盘与下一节问题

我们现在知道每类事实由谁确认，却还不知道它们需要多快、允许失败多久、哪些必须强一致。第 7 节将把业务风险转成可验证的非功能目标：

> 哪些链路需要低延迟？哪些事实要求强一致，哪些允许最终一致？目标 QPS、P99、可用性、幂等、审计、追踪和恢复能力应该如何定义？
