# 第 1 节：大营销系统到底解决什么问题

**状态：** 已完成
**完成日期：** 2026-08-08
**阶段：** 产品需求分析
**本节不写业务代码、不建业务表。**

## 1. 本节目标

在选择 Go 框架、画领域模型和设计数据库之前，先回答三个问题：

1. 电商、出行、金融、内容和游戏为何反复需要营销能力？
2. 为什么单次活动系统无法形成持续增长？
3. 为什么 AI 应成为受治理的运营入口，而不是一个直接改库的聊天框？

本节出口是一份可供后续拆解的产品问题定义。它不是最终 PRD，也不承诺尚未验证的架构。

## 2. 行业场景：业务不同，增长任务相似

### 2.1 电商

典型任务是拉新、促活、转化和复购：用户从首页或推荐流看到活动，参加抽奖或领取优惠券，在订单中核销，平台再依据曝光、点击和购买反馈优化下一轮触达。

难点不只是“发券”，而是库存与预算受控、资格判断一致、权益可追踪、活动效果可归因，并能承受大促的突发流量。

### 2.2 出行

典型任务是激活新乘客、召回沉默用户、平衡时段与区域供需。奖励可能是打车券、会员权益、积分或任务进度。

营销策略必须理解城市、时间、路线、供需和用户生命周期。同一张券对不同时间地点的价值完全不同，因此固定群发无法持续有效。

### 2.3 金融

典型任务是开户激活、绑卡、首投、持续使用和会员经营。金融营销比普通内容推荐更强调资格、额度、风险、审批、审计和可解释性。

系统不仅要回答“给谁什么奖励”，还必须回答“为什么有资格、谁批准、是否重复发放、结果能否对账”。

### 2.4 内容

典型任务是提升消费时长、互动、订阅和创作者参与。Feed 本身就是触达界面，活动、任务、会员和内容候选需要共同参与排序。

如果营销与推荐割裂，用户会看到与兴趣无关的活动；如果只有推荐而没有权益和实验闭环，运营又无法快速验证增长假设。

### 2.5 游戏

典型任务是新手成长、日活、回流、付费和社交传播。签到、任务、抽奖、积分和虚拟奖品组合频繁，活动峰值明显。

系统需要处理规则版本、概率、公平性、虚拟资产发放、幂等与反作弊，也要避免短期奖励损害长期留存和经济系统。

## 3. 五类业务背后的共同矛盾

上述行业虽然对象不同，却共享同一条增长链路：

```text
识别用户与场景
      ↓
选择内容、活动或权益
      ↓
通过 Feed/渠道触达
      ↓
用户参与并获得结果
      ↓
记录曝光、点击、参与、领取、核销与转化
      ↓
分析效果并更新下一轮策略
```

单次项目通常只能打通链路中的一小段，长期会暴露六类问题：

1. **能力重复：** 每个活动重新实现资格、库存、奖励、幂等和风控。
2. **体验割裂：** Feed、活动、积分和优惠券各有入口与状态，用户难以理解。
3. **数据断裂：** 曝光、参与、发奖和转化无法用统一身份、事件和实验关联。
4. **决策缓慢：** 运营依赖研发写 SQL、改配置、发版，反馈周期长。
5. **峰值风险：** 平时低流量掩盖了热点库存、重复消息、雪崩和降级问题。
6. **治理不足：** 权限、审批、审计和回滚跟不上自动化能力。

因此目标不应是再做一个抽奖服务，而是建立可组合、可度量、可治理的增长操作系统。

## 4. GrowthOS 的产品能力分层

### 第一层：Business

这一层保证业务交易成立：

- 活动与策略；
- 抽奖与参与次数；
- 积分、优惠券和其他奖励；
- 账户、订单、流水、库存和发放记录。

它的核心问题是业务正确性：资格是否正确、是否超发、重复请求是否幂等、历史是否可审计。

### 第二层：Growth

这一层让一次交易变成持续优化：

- Growth Feed 触达；
- 曝光、点击、参与、领取、转化等行为事件；
- 实时画像、召回、过滤、排序和频控；
- 实验、漏斗与指标反馈。

它的核心问题是闭环：系统是否知道触达了谁、发生了什么、策略是否有效，以及下一轮如何调整。

### 第三层：AI Native

这一层让运营用自然语言组合平台能力，但不绕过治理：

- MCP Gateway 把稳定 HTTP/RPC 能力描述为受控工具；
- Agent 负责理解意图、查询信息、制定步骤和调用工具；
- RBAC、风险等级、审批与审计约束执行；
- Trace 将 Agent、Tool 和业务结果关联起来。

它的核心问题不是“接入一个模型”，而是让 AI 在明确权限、契约和责任边界内参与真实运营。

## 5. 为什么必须先有业务和增长闭环，再谈 AI

Agent 的能力上限由底层业务工具决定。如果活动创建仍靠人工改表、指标口径不统一、奖励接口没有幂等，那么增加 LLM 只会更快地产生不可控操作。

GrowthOS 采用以下顺序：

```text
稳定业务用例
  -> 可观测接口与事件
  -> 统一工具契约
  -> 权限和风险控制
  -> Agent 规划与执行
```

AI Operator 未来可以：

- 查询活动、漏斗、库存、Feed 或 Trace；
- 基于已授权模板生成活动草案；
- 调用低风险、可回滚的运营工具；
- 对高风险动作生成执行计划并请求人工审批。

AI Operator 不可以：

- 直接连接生产数据库修改事实数据；
- 绕过业务 API 的校验、幂等和审计；
- 自行扩大权限或跳过高风险审批；
- 把模型文本当作已执行的业务结果。

所以“AI Native”意味着业务能力从设计时就考虑机器可发现、结构化调用、最小授权和全链路审计，而不是把聊天界面放在传统后台之上。

## 6. 平台边界

### 第一阶段要做

- 完成 Go 版从产品需求、数据库演进、DDD、高并发、Feed、数据、MCP、Agent、前端到生产化的全链路。
- 使用需求和证据逐步引入表、索引、缓存、消息、服务拆分和分析存储。
- 同时保留消费者体验、运营效率、平台稳定性和治理四个视角。
- 每节落正文、ADR（适用时）与 QA 证据，保持实现和文档同步。

### 当前不做

- 不在第 1 节给出最终 ER 图、最终服务拓扑或最终技术选型。
- 不把 GrowthOS 定义为通用 CRM、广告投放平台、支付系统或完整推荐基础设施。
- 不为尚未出现的规模问题提前引入所有中间件。
- 不同时实现 Java 版；Go 版完成后才将稳定 Specification 用于下一轮独立规划。

## 7. 价值假设与验证方式

本节提出的是待后续实现验证的假设：

| 价值假设 | 后续证据 |
| --- | --- |
| 复用活动、策略与权益能力能缩短运营交付周期 | 活动配置流程、发布记录、重复开发量对比 |
| Feed 与行为闭环能提升触达相关性 | 曝光到转化漏斗、A/B 实验和频控指标 |
| 统一账户与流水能提升权益可信度 | 幂等测试、对账、用户申诉回溯和故障恢复演练 |
| 渐进式架构能避免无证据的复杂度 | 每次 ADR、压测基线和迁移原因 |
| 受控 Agent 能降低运营操作成本 | Tool 成功率、审批率、审计完整性和人工耗时 |

> **后续状态：** 第 7 节已形成[非功能需求基线 v1](../../product/non-functional-requirements-v1.md)，把关键路径转成候选 QPS、P99、可用性与一致性目标；当前仍没有运行时实测结果。

## 9. 本节复盘

我们尚未设计任何表，也尚未实现第 11 节的 Gin 服务，但已经明确了系统为什么存在：它不是功能集合，而是从触达、参与、权益到反馈优化的闭环；AI 不是旁路自动化，而是建立在稳定业务工具和治理机制上的新交互层。工程技术基线由 [ADR-0005](../../decisions/ADR-0005-domestic-mainstream-technology-baseline.md) 记录，具体组件仍只在对应需求章节接入。

这一结论也给后续设计设下约束：任何新增模块都要能说明它解决了链路中的什么问题，任何复杂基础设施都要有需求、规模或故障证据。

## 10. 留给第 2 节的问题

“用户增长闭环”仍然过于抽象。下一节要选择一个具体用户，从打开 App 开始，逐步回答：

- Feed 在什么时机展示什么？
- 曝光和点击在何时记录？
- 参与活动前要检查什么？
- 中奖后权益如何可见、领取和使用？
- 消费或分享如何回流为下一次触达信号？
- 中途失败、重复点击、资格不足和活动结束时用户看到什么？

只有完整走通这条旅程，才能继续定义运营端如何创建它。
