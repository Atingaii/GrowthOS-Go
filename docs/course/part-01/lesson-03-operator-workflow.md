# 第 3 节：设计运营人员工作流

**状态：** 已完成

**完成日期：** 2026-08-08

**阶段：** 产品需求分析

**本节不写业务代码、不建业务表、不新增真实 API。**

## 1. 本节目标

第 2 节确定了用户如何从 Feed 触达走到权益使用。本节反向回答：运营人员如何把这条旅程安全地创建、发布、观察和结束。

本节不把运营后台理解成一组 CRUD 页面，而是建立一条可治理的业务流程：

```text
业务目标 → 人群 → 触达 → 规则 → 权益 → 预算
→ 校验 → 预览 → 审批 → 发布 → 运行控制 → 复盘
```

## 2. 为什么不能先做“活动表单”

如果一开始就按数据库字段设计表单，运营会面对 `strategy_id`、状态码和 JSON 配置，却无法回答活动为什么做、影响谁、最坏成本是多少、失败时如何止损。

运营工作流应从业务目标开始，再逐步收敛为可执行配置。数据库和领域模型以后要支撑该流程，而不是反过来让运营适应表结构。

## 3. 主运营场景

沿用第 2 节的回访用户旅程：运营希望召回连续 14 天未登录、近 90 天有消费的会员，通过 Feed 提供抽奖机会，奖励为有使用门槛和有效期的优惠券。

运营需要完成：

- 明确业务目标和保护指标；
- 定义包含人群与排除人群；
- 设计 Feed 内容和活动详情；
- 配置资格、次数、抽奖策略和权益；
- 约束预算、库存、频率和时间；
- 通过校验、预览和审批后发布；
- 运行中观察效果和风险；
- 活动结束后形成可复用结论。

## 4. 完整工作流

详细角色、阶段输入、自动校验、审批矩阵和生命周期见[运营人员工作流 v1](../../product/operator-workflow-v1.md)。

### 4.1 业务简报

第一步不是“新建活动名称”，而是明确希望改变哪类用户的什么行为、主指标、保护指标、预算和负责人。无法衡量的目标不能直接进入发布流程。

### 4.2 人群与排除

目标人群必须可复现，并标记数据更新时间。除包含条件外，还要排除员工、风控名单、已经参加同类活动或拒绝营销的用户，防止只会扩大覆盖却不能控制风险。

### 4.3 触达与用户旅程

运营配置 Feed 卡片、活动详情和结果去向。预览必须覆盖第 2 节定义的完整旅程，而不是只预览一张图片。

### 4.4 规则、权益与预算

参与规则、奖品库存、单位成本、有效期、用户上限和总预算共同决定活动是否能运行。预算估算帮助运营理解最坏成本，但线上还必须存在真实的预算与库存控制。

### 4.5 校验、预览与审批

系统校验分为阻断、警告和信息。阻断项不允许提交；警告项可提交但审批人必须明确确认。审批基于不可变的配置快照，审批后修改关键字段需要生成新版本。

### 4.6 发布与运行控制

发布可以立即、定时或灰度进行。运行中要能查看转化过程、成本、库存、失败和保护指标。异常时先暂停新的参与，再调查影响范围，不能删除历史记录假装恢复。

### 4.7 结束与复盘

结束后保留活动版本、用户参与、权益和指标口径。复盘回答目标、成本、主要流失、异常和下一步，而不是只汇报曝光总量。

## 5. 谁创建，谁审批，谁止损

活动运营负责业务目标和配置，权益运营负责权益可用性，数据分析负责指标口径，审批/风控负责高风险确认，SRE 负责技术止损。小团队可一人多岗，但同一个高风险操作不能默认由申请人自己批准。

紧急暂停与普通发布不同：授权人员可以先阻止新的参与以减少损失，但必须记录原因、影响、执行人和后续处置。

## 6. 暂停、结束和回滚不是一回事

- **暂停：** 临时不接受新参与，处理完成后可以恢复；
- **提前结束：** 永久停止该版本的新参与，不能原地恢复；
- **撤回：** 发布前取消审批或排期；
- **取消：** 放弃一个未运行草稿；
- **回滚：** 切换回上一个已验证版本，不删除已经发生的参与和权益事实。

明确这些语义，后续状态机、接口权限和审计才能保持一致。

## 7. 当前不提前决定什么

本节不决定：

- 最终活动表和审批表结构；
- 最终状态枚举或状态机代码；
- 人群平台、权益中心和实验系统的最终服务边界；
- 自动审批算法和预算公式的固定实现；
- 运营后台的最终字段与页面布局。

这些都要随着事件风暴、领域边界和真实业务需求继续演进。

## 9. 本节复盘

一个活动不是一行数据库记录，而是从目标提出到最终复盘的一段受控生命周期。运营效率来自可复用的目标、人群、规则、权益和预览能力；平台安全来自预算上限、职责分离、审批、版本、暂停与审计。

后续运营后台即使已经有完整 UI 框架，也不能把 Mock 页面当作流程已实现。每一个真实步骤仍需要后端契约、状态事实和 QA 证据支持。

## 10. 留给第 4 节的问题

运营工作流明确后，AI Operator 可以参与哪些步骤仍需定义：

- AI 能否自动查询人群规模、历史活动和预算参考？
- AI 可以生成草稿还是直接发布？
- 哪些 Tool 调用可以自动执行，哪些必须人工审批？
- AI 如何展示计划、参数、成本和风险，而不是只返回自然语言？
- Tool 失败、部分成功和审批超时如何反馈给运营？
