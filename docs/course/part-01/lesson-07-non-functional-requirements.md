# 第 7 节：确定非功能需求

**状态：** 已完成

**完成日期：** 2026-08-09

**阶段：** 产品需求分析

**本节不写 Go 业务代码、不建业务表、不新增真实前端 API。所有数值都是待实现后验证的目标，不是当前实测成绩。**

## 1. 本节目标

前 6 节说明了 GrowthOS 要解决什么问题、业务事实如何流动以及由谁确认。本节把“高并发、稳定、幂等、可追踪”这些模糊形容词改成可测量的非功能需求，为第 8 节 V0 系统设计和后续实现提供验收边界。

非功能需求回答的不是系统“做什么”，而是：

- 在什么流量和数据规模下仍能工作；
- 用户需要等待多久；
- 哪些失败可以降级，哪些必须拒绝；
- 已确认的业务事实能否重复、丢失或被覆盖；
- 出现故障后允许丢多少数据、多久恢复；
- 如何证明一次请求、审批、消息和 Tool 调用发生过。

## 2. 先区分目标、指标和承诺

| 术语 | 中文含义 | 本项目当前状态 |
| --- | --- | --- |
| SLI | 实际测量到的服务指标，例如成功率和 P99 延迟 | 尚无业务后端，当前为空 |
| SLO | 团队希望在统计窗口内达到的内部目标 | 本节建立 v1 候选目标 |
| SLA | 对客户作出的合同承诺，通常包含违约责任 | 当前不定义 |
| Error Budget | 由 SLO 推导出的允许失败额度 | 实现监控后计算和执行 |

例如“P99 小于 300ms”表示 99% 的有效请求在 300ms 内完成，不表示任何一次请求都不会更慢。“可用性 99.95%”也不是永不故障，而是一个自然月内允许约 21 分 55 秒不可用。

本节中的数字均标注为 **目标值**。后续只有在明确环境、数据量、脚本、持续时间和结果的压测报告中，才能写成 **实测值**。

## 3. 先按业务风险分级

| 等级 | 典型链路 | 失败原则 |
| --- | --- | --- |
| T0 核心事实 | 用户参与、抽奖结果、积分/优惠券到账、额度与流水 | 不重复、不静默丢失；无法确认时返回处理中或结果未知，不能伪报成功 |
| T1 核心控制 | 活动发布/暂停、审批、权限、预算和库存控制 | 高风险操作失败关闭；状态冲突必须显式返回 |
| T2 增长体验 | Feed 查询、召回、排序、频控和画像 | 可以降级到基础候选或时间/热度排序，不影响核心交易事实 |
| T3 分析与智能 | 行为分析、漏斗、搜索、LLM 和 AI 计划 | 可以延迟或暂停；人工运营与核心交易仍可继续 |

风险等级决定一致性、可用性和降级策略。不能为了让 Feed 更快而放松积分流水，也不能为了等分析结果阻塞用户参与。

## 4. V1 容量假设

GrowthOS 面向高流量业务，但课程会从单机小流量逐步验证。生产候选容量先作为架构压力输入：

| 能力 | 稳态目标 | 5 分钟峰值目标 | 延迟目标 | 统计口径 |
| --- | ---: | ---: | ---: | --- |
| Feed 读取 | 10,000 RPS | 50,000 RPS | P99 ≤ 200ms | 不含客户端网络和图片下载 |
| 行为事件接收 | 20,000 RPS | 100,000 RPS | P99 ≤ 100ms | 表示事件被可靠接收，不表示分析完成 |
| 活动参与 | 2,000 RPS | 10,000 RPS | P99 ≤ 300ms | 到参与事实和抽奖结果可确认 |
| 抽奖决策 | 2,000 RPS | 10,000 RPS | P99 ≤ 150ms | 不包含外部权益到账时间 |
| 权益发放受理 | 1,000 RPS | 5,000 RPS | P99 ≤ 300ms | 表示受理或本地完成，响应必须区分状态 |
| 运营查询/写入 | 100 RPS | 300 RPS | 查询 P99 ≤ 500ms，写入 P99 ≤ 800ms | 不包含离线报表 |
| 分析查询 | 200 RPS | 500 RPS | P99 ≤ 2s | 面向常用漏斗与指标查询 |
| MCP Tool 网关 | 200 RPS | 500 RPS | 网关开销 P99 ≤ 100ms | 不包含 Tool、LLM 和人工审批耗时 |

这些数字不是要求 Modular Monolith 第一版立即达到。它们用于判断后续热点、异步化、缓存、分片和服务拆分是否有真实必要。

## 5. 分阶段性能门槛

| 里程碑 | 首要性能验收 | 目的 |
| --- | --- | --- |
| M0 · 第 16 节 | 健康接口在本地 100 RPS、持续 5 分钟下无错误，P99 ≤ 100ms | 验证工程、连接池和开发环境 |
| M1 · 第 24 节 | 单实例抽奖读取 500 RPS、持续 10 分钟，P99 ≤ 200ms | 建立第一个算法与缓存基线 |
| M2 · 第 40 节 | 活动参与 1,000 RPS、持续 10 分钟，检查超卖、重复和锁等待 | 证明 MySQL 与 Redis 库存演进原因 |
| M4 · 第 72 节 | Feed 5,000 RPS、行为接收 20,000 RPS，持续 30 分钟 | 验证增长反馈链路 |
| M5 · 第 80 节 | 对生产候选峰值进行分布式容量验证 | 用证据决定扩容和分片 |
| M6 · 第 88 节 | MCP 网关 200 RPS，权限与审计不丢失 | 验证 AI 工具出口开销 |
| M7 · 第 96 节 | 完整峰值、12 小时稳定性和故障注入 | 形成最终压测与容量报告 |

每次测试必须记录机器规格、实例数、数据规模、冷热缓存、请求比例、脚本版本、成功率、P50/P95/P99、资源使用和瓶颈。不同环境的数字不能直接横向比较。

## 6. 可用性目标

以自然月为统计窗口，业务拒绝不计为系统不可用；超时、5xx、错误成功和无法确认的非预期结果计入失败。

| 能力 | 生产候选 SLO | 降级要求 |
| --- | ---: | --- |
| Participation / Lottery / Benefit 核心链路 | 99.95% | 不能用重复扣减、超发或假成功换可用性 |
| Marketing / Governance 核心控制 | 99.95% | 高风险写操作在权限或审批不可用时失败关闭 |
| Feed 读取 | 99.90% | 个性化不可用时降级到可投放的时间/热度候选 |
| Behavior 事件接收 | 99.90% | 客户端批量、重试或本地缓冲，不能拖慢交易主链路 |
| 分析与运营搜索 | 99.90% | 延迟展示并标注数据更新时间 |
| AI Operations | 99.50% | LLM 或 MCP 不可用时切换人工运营，不阻断业务系统 |

第三方支付、交易、外部券、消息渠道和 LLM 的不可用必须单独观测。GrowthOS 只能衡量自身调用、超时、隔离和恢复能力，不能把依赖方故障从端到端体验中隐藏。

## 7. 一致性和业务不变量

### 7.1 必须在权威上下文内原子确认

- 同一业务请求只能形成一份有效参与订单；
- 一次有效参与最多消耗一次参与次数；
- 一次抽奖只能存在一个最终结果，结果未知不能重新抽取另一个结果；
- 积分、优惠券等权益的余额变化必须能追溯到唯一业务流水；
- 活动发布、暂停和审批使用版本检查，不能静默覆盖并发修改；
- 已确认的库存领取总量不得超过可分配库存；发现不一致必须进入可见补偿，而不是删除记录。

### 7.2 允许有界最终一致

| 派生或跨系统数据 | 正常收敛目标 | 超时后的处理 |
| --- | ---: | --- |
| Redis 库存与 MySQL 最终库存 | ≤ 5s | 告警、停止继续放量并触发核对/补偿 |
| 权益异步发放 | 95% ≤ 3s，99.9% ≤ 5min | 保持处理中，重试或人工补偿，不显示已到账 |
| Behavior 到实时画像 | ≤ 10s | Feed 使用旧画像或基础排序 |
| Behavior 到分析漏斗 | ≤ 5min | 页面展示数据水位和更新时间 |
| OpenSearch 查询投影 | ≤ 60s | 回退精确 ID 查询或提示索引延迟 |
| 外部支付转化回传 | 依赖方定义，GrowthOS 接收后 ≤ 60s 入分析链 | 保留来源时间，迟到事件重新归因 |

上述组件尚未实现，收敛目标会在对应章节通过消息积压、延迟分位数和对账差异验证。

## 8. 幂等、重复和结果未知

“Exactly Once”不是依靠一句技术口号实现。本项目采用“可能重复投递 + 权威上下文幂等 + 唯一业务标识 + 可查询最终结果”的业务语义。

| 场景 | 幂等要求 |
| --- | --- |
| 用户参与、抽奖、领券 | 同一用户业务请求重试返回同一业务结果，不重复扣减或发放 |
| 积分和权益流水 | 业务来源 + 业务流水号长期唯一，保留期限不短于业务事实 |
| 活动发布/暂停 | 请求幂等且校验活动版本，旧版本操作返回冲突 |
| 外部回调和消息消费 | 允许重复到达，重复消费不改变已确认结果 |
| 行为采集 | 允许客户端批量重试，以事件 ID 去重；分析口径必须说明去重窗口 |
| AI Tool 写操作 | 每次批准的 Tool Call 绑定不可复用的执行标识，超时后先查询再重试 |

接口超时不等于业务失败。只要系统可能已经执行，就必须返回“处理中/结果未知”或提供按业务请求号查询结果的能力，不能提示用户盲目再试。

## 9. 恢复目标

| 故障范围 | 数据范围 | RPO：最多允许丢失 | RTO：恢复目标 |
| --- | --- | ---: | ---: |
| 单进程/单实例故障 | 已确认核心事实 | 0 | ≤ 5min |
| 主数据库灾难恢复 | 参与、订单、抽奖、权益、审批和审计 | ≤ 5min | ≤ 60min |
| 配置与活动数据 | 草稿、版本、规则与发布状态 | ≤ 5min | ≤ 60min |
| 行为原始数据与消息链 | 已可靠接收的行为事件 | ≤ 15min | ≤ 4h |
| 搜索、画像和分析投影 | 可从事实或事件重建的数据 | 可重建 | ≤ 8h |

RPO 是故障后最多允许丢失的数据时间范围，RTO 是恢复服务所需的目标时间。目标必须通过备份恢复、主从切换、消息重放和投影重建演练证明，只有配置文件不算灾备。

## 10. 可观测与排障要求

- 所有 HTTP、后续 RPC、消息、定时任务、MCP Tool 和 Agent Task 可关联同一个 `trace_id`；
- 核心写操作必须记录业务请求号、对象 ID、结果状态、错误码和耗时，不在日志中打印密码、Token、完整个人信息或模型秘密；
- 指标至少覆盖请求量、成功率、P50/P95/P99、连接池、慢 SQL、缓存命中、库存差异、消息积压、补偿数量和外部依赖；
- 错误、高风险操作和结果未知链路保留 100% Trace；普通流量采样率由成本与排障需要调整；
- 告警必须指向用户影响和处理手册，不能只因为 CPU 短暂升高就制造噪声；
- 时间统一保存为 UTC，展示层按用户时区转换，跨系统时钟偏差需要监控。

## 11. 安全、隐私与审计

| 领域 | v1 要求 |
| --- | --- |
| 身份与权限 | 默认拒绝；服务端鉴权；租户、角色和资源范围共同校验 |
| 高风险操作 | 申请人与审批人职责分离；审批失效、版本变化后重新确认 |
| 传输与秘密 | 生产通信加密；API Key、密码和证书不进仓库、日志和前端包 |
| 数据最小化 | API、事件、日志和 Prompt 只传递完成任务所需字段 |
| 审计 | 记录操作者、动作、目标、前后版本、审批、结果和关联 Trace；普通用户无权覆盖删除 |
| AI | Tool 参数结构化校验、最小授权、调用预算、Prompt 注入隔离和人工接管 |
| 依赖安全 | 锁定依赖版本，持续扫描高危漏洞，升级需回归测试 |

默认建议高风险运营与 AI Tool 审计保留至少 365 天，应用日志保留 30 天，在线 Trace 保留 7 天；行为数据保存期限根据用户授权、行业和部署地区再收紧。它们是产品默认值，不替代法律与合规评审。

### 11.1 AI 与审批的控制目标

| 控制项 | v1 候选目标 |
| --- | --- |
| 审批有效期 | 默认不超过 24h；活动版本、Tool 参数、预算或风险等级变化后立即失效 |
| Tool 网关开销 | P99 ≤ 100ms，不包含实际 Tool、LLM 和人工等待时间 |
| 单次 Tool 执行超时 | 由具体业务接口登记；超时后进入结果未知并先查询，不自动换执行 ID |
| AI 任务恢复 | 每个已确认 Tool 结果形成检查点；执行器恢复后 15min 内恢复可继续任务 |
| 结果未知核对 | 核心写 Tool 5min 内完成自动查询或升级人工处理 |
| 审计完整性 | 高风险写操作 100% 关联操作者、审批、参数摘要、结果、业务对象和 `trace_id` |
| 执行预算 | 每个任务限制 Tool 次数、Token、累计时长和可操作资源范围，具体额度按场景配置 |

这里的 100% 是业务不变量：如果无法可靠记录高风险写操作的审计事实，就不能把操作当作正常成功继续执行。审计记录失败的事务和补偿方式在 Governance 实现阶段决定。

## 12. 降级矩阵

| 故障 | 允许行为 | 禁止行为 |
| --- | --- | --- |
| 个性化排序不可用 | 返回经过活动有效性校验的时间/热度 Feed | 返回已结束或用户不合格活动 |
| Behavior/Analytics 不可用 | 缓冲、重试，核心交易继续 | 为等埋点阻塞参与和权益 |
| Redis 不可用 | 按当前业务风险回源、限流或暂停热点活动 | 无保护地把全部峰值打到 MySQL |
| MQ/异步任务不可用 | 写入可靠任务、显示处理中、恢复后补偿 | 把“发送失败”伪装成权益到账 |
| 外部券中心不可用 | 保持待发放，按策略重试和告警 | 重复创建新券或显示已到账 |
| LLM/MCP 不可用 | 人工运营继续，已确认业务事实不受影响 | 让模型绕过 Tool 直接写库 |
| Governance 不可用 | 只读可按策略继续，高风险写操作失败关闭 | 跳过权限或审批以提高成功率 |

## 13. 验证策略和证据格式

每项 NFR 至少需要一种可重复证据：

- 性能：k6/JMeter 脚本、环境说明和分位数报告；
- 一致性：并发、重试、重复消息、超时后查询和对账测试；
- 恢复：备份恢复、进程中断、依赖超时、消息积压与重放演练；
- 安全：权限矩阵、越权测试、秘密扫描、依赖扫描和审计查询；
- 可观测：从用户错误反查 Trace、日志、指标和业务对象；
- 降级：故障注入后验证核心链路、提示语义和恢复过程。

报告必须同时保留失败结果。一次测试通过不能永久证明 SLO，持续监控建立后才按滚动窗口计算实际 SLI 和 Error Budget。

## 14. 本节不做什么

- 不声称任何业务吞吐、P99 或可用性已经达标；
- 不因为目标是 10 万 RPS 就提前引入微服务、MQ、分片或多活；
- 不确定最终机器规格、实例数量和云厂商；
- 不用 GrowthOS 自身指标掩盖支付、外部券或 LLM 的端到端故障；
- 不创建业务接口、数据库、压测脚本或监控面板；
- 不把内部 SLO 写成对外 SLA。
