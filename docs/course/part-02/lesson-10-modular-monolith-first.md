# 第 10 节：为什么第一版不直接微服务

**状态：** 已完成

**完成日期：** 2026-08-29

**阶段：** Go + React 从零搭建

**本节确定运行时和代码边界，不新增产品接口、数据库表或远程服务。**

## 1. 本节工程诉求

第 9 节已经建立单仓库工程基线。第 11 节即将启动第一个 Go HTTP 进程，因此必须先回答：路线图包含多个限界上下文和远期分布式能力，第一版是否应直接拆成微服务？

当前要解决的问题不是“微服务是否先进”，而是用最低的分布式成本保护已经识别出的业务边界，并为以后可验证地拆分留下出口。

## 2. 当前证据

- 尚无真实业务流量、容量曲线或热点数据；
- 尚无需要独立发布的稳定团队边界；
- 抽奖、活动账户、订单与权益的早期主链路包含强一致性不变量；
- 当前交付团队需要先验证业务模型、Schema 和接口，而不是先治理大量网络契约；
- 第 73～80 节已经预留基于运行证据的服务拆分阶段。

因此，提前拆分会把未知的领域问题转化成确定的网络、部署和数据一致性问题。

## 3. 方案比较

| 维度 | 直接微服务 | 无边界单体 | 模块化单体 |
| --- | --- | --- | --- |
| 初始部署 | 多进程、多配置、多健康检查 | 单进程 | 单进程 |
| 一致性 | 需尽早处理分布式事务与消息 | 可用本地事务，但易越界 | 核心不变量可用本地事务，模块拥有事实 |
| 代码边界 | 网络天然形成边界，但契约尚不稳定 | 容易互相调用实现细节 | 通过包、端口、契约和依赖测试约束 |
| 调试与学习 | 链路长、故障面大 | 简单但结构易腐化 | 链路短且保留架构演进证据 |
| 以后拆分 | 已经承担成本，但边界可能错误 | 重构成本高 | 先稳定模块端口，再替换进程内调用 |

选择模块化单体不是忽略分布式，而是把分布式复杂度推迟到能够用指标、故障域和组织事实说明收益的时候。

## 4. 源码与依赖规则

第一版遵守以下依赖方向：

```text
cmd/growth-api
      │ 只做装配
      ▼
internal/<domain>/application
      │ 使用领域对象与端口
      ▼
internal/<domain>/domain

internal/infrastructure ──实现──> 各模块端口
```

具体规则：

1. `cmd/*` 不承载业务规则；
2. 模块内部拥有自己的领域模型、应用用例和持久化端口；
3. 模块不导入另一个模块的基础设施包，不绕过端口读写他方表；
4. MySQL 是业务事实存储，但“共用一个实例”不等于“共享所有表的写权限”；
5. Redis、消息、搜索和分析存储都是可替换适配器，其数据必须可由事实重建；
6. 跨模块同步调用只暴露最小应用契约，异步协作使用有版本的事件；
7. 第 73 节以前若出现真实拆分证据，必须新增 ADR，而不是悄悄创建第二个服务。

## 5. 事务边界

早期抽奖、库存、账户和权益会优先在一个进程与一个业务库内完成。单个用例只在拥有事实的模块内开启事务；跨模块流程由应用层编排，随着可靠消息和补偿能力出现再缩短事务边界。

本节不预制最终事务模型。第 18 节开始由实际表和不变量决定事务范围，第 41～47 节再用失败证据引入最终一致性与补偿。

## 6. 何时拆分

拆分评审必须记录可重复证据，而不是仅凭代码量：

| 证据 | 示例判断 |
| --- | --- |
| 负载 | Behavior Collector 吞吐和资源模型与营销 API 明显不同 |
| 可用性 | Feed 故障不能影响抽奖主链路，且进程内隔离无法满足目标 |
| 发布 | 模块需要独立频繁发布，单体发布窗口形成可量化瓶颈 |
| 合规 | 数据访问和存储边界要求物理隔离 |
| 团队 | 所有权和接口已稳定，独立团队能承担服务全生命周期 |

满足证据也不等于一次拆完。第 74 节只拆第一批收益明确的服务，第 75～80 节补齐契约、发现、追踪、治理和查询模型。

## 7. 数据库与 API 变化

**数据库变化：无。** 本节不创建空 Schema，也不通过数据库结构假装模块已经实现。

**API 变化：无。** 第一个 `GET /health` 仍由第 11 节交付；本节只约束其所在进程和后续模块装配方式。

边界登记见[第 10 节 API 记录](../../api/lessons/lesson-10.md)。

## 8. 架构决策

[ADR-0007](../../decisions/ADR-0007-modular-monolith-first.md) 固化“模块化单体优先、证据驱动拆分”的长期决策。它与 ADR-0001 的演进式交付一致，并为第 73～80 节定义可核查的触发条件。

## 9. QA 验收

本节通过文档、仓库结构和质量门禁核查：

- 决策没有把远期微服务描述为当前能力；
- 仓库依赖规则与 V0 系统设计、限界上下文保持一致；
- 第 11～72 节的单进程边界和第 73 节后的拆分条件明确；
- 未引入无需求支撑的 RPC、注册中心、共享服务包或数据库表；
- 文档索引、课程状态和 API 台账一致。

执行证据见[第 10 节 QA 验收](../../qa/lessons/lesson-10.md)。

## 10. 本节复盘

第一版不直接微服务，是因为当前最重要的风险是业务模型和契约尚未被实现验证。模块化单体用进程内低成本保留领域边界，也让以后可以比较拆分前后的真实收益。
