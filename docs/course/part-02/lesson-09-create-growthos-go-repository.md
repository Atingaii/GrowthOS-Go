# 第 9 节：创建 GrowthOS-Go 仓库

**状态：** 已完成

**完成日期：** 2026-08-23

**阶段：** Go + React 从零搭建

**本节只建立可持续演进的仓库工程基线，不启动 Go 产品服务、不创建业务表，也不把预留目录描述为已实现能力。**

## 1. 本节工程诉求

前 8 节已经确定产品、领域、NFR 和 V0 系统边界。进入编码阶段后，需要一个能够长期承载以下内容的仓库：

- Go 模块、可执行程序与私有业务模块；
- React 前端工程；
- 前向 SQL Migration 与部署资产；
- 产品、架构、ADR、API、QA 和课程文档；
- 本地与 CI 使用同一入口的质量门禁。

仓库同时要保留演进空间：现在只有一个模块化单体的方向，不能因为路线图中出现了 Redis、MQ、MCP 或微服务，就提前创建伪实现和空服务。

## 2. 上一版系统状态

第 8 节输出的是逻辑系统设计。它说明 GrowthOS 第一版采用一个 Go 进程、清晰业务模块和一个 React 工程，但还没有把这些约束落到可检查的仓库结构。

如果没有统一工程基线，后续章节容易出现：

1. 每一节自行选择目录和命令，模块边界持续漂移；
2. 文档、Migration、前端和后端散落到不同仓库，单个需求难以原子交付；
3. 开发者本地验证与 CI 执行不同命令；
4. 路线图中的远期组件被误认为已经实现。

## 3. 方案分析

| 方案 | 优点 | 问题 | 结论 |
| --- | --- | --- | --- |
| 按未来微服务拆多个仓库 | 部署边界看起来清楚 | 当前没有拆分证据，跨仓库变更与治理成本高 | 不采用 |
| 单仓库但不约束目录 | 初始化最快 | 业务、基础设施和工具代码容易混杂 | 不采用 |
| 单仓库 + 单 Go module + 明确目录职责 + 统一门禁 | 当前变更可原子提交，边界可检查，也保留以后拆分空间 | 需要持续维护仓库地图 | 采用 |

本节选择 monorepo 是当前阶段的交付策略，不是承诺所有能力永远在一个仓库或进程中。服务拆分仍需等待第 73 节后的真实负载、发布、隔离或团队证据。

## 4. 仓库工程基线

当前仓库结构为：

```text
GrowthOS-Go/
├── cmd/             # Go 可执行程序和仓库工具入口
├── internal/        # 仓库私有的领域与基础设施边界
├── pkg/             # 仅容纳确需被外部导入的稳定 Go 包
├── configs/         # 无秘密、可版本化的配置示例
├── migrations/      # 第 13 节起加入前向 SQL Migration
├── deploy/          # 第 16 节起按需加入部署资产
├── scripts/         # 可重复的本地自动化
├── web/             # React + TypeScript 前端工程
└── docs/            # 产品、架构、决策、API、QA 与课程事实
```

详细职责和引入时机以[仓库地图](../../architecture/repository-map.md)为准。

目录不等于运行时能力。`cmd/growth-api` 要到第 11 节才出现可启动的 HTTP 服务；`migrations` 要到第 13 节才加入 Migration；领域目录中的占位文件只保护规划边界，不证明活动、抽奖、Feed、MCP 或 Agent 已经实现。

## 5. Go module 与依赖边界

根目录 `go.mod` 建立单一 Go module：

```text
github.com/growthos/growth-os-go
```

本节不引入第三方运行时依赖。Go 标准库已经足以实现当前的文档检查和同步工具；Gin、配置、日志、MySQL 驱动与 Migration 工具分别等待对应章节按真实需要接入。

依赖方向遵守以下规则：

- `cmd/*` 只负责装配和进程生命周期；
- 业务代码留在 `internal/<domain>`，不能把 `pkg` 当成公共杂物目录；
- 领域模块不能直接依赖其他模块的数据库实现；
- `internal/infrastructure` 实现技术适配器，不承载业务规则。

这些是模块化单体的源代码边界，不是已经拆出的服务边界。

## 6. 本地开发与质量门禁

`Makefile` 提供仓库级统一入口：

| 命令 | 当前职责 |
| --- | --- |
| `make fmt` / `make fmt-check` | 格式化 Go 文件并检查漂移 |
| `make test` | 执行全部 Go 测试 |
| `make doc-check` | 校验必需文档、链接、ADR、课程状态和章节 API 记录 |
| `make web-verify` | 执行 TypeScript 类型检查和 Vite 生产构建 |
| `make verify` | 汇总当前所有本地质量门禁 |

GitHub Actions 在干净 Linux runner 上安装 Go、Node.js 与 pnpm 后执行相同的 `make verify`。本地和 CI 共享入口，减少两套验证流程产生的漂移。

`.editorconfig` 统一 UTF-8、LF、文件尾换行和缩进规则；`.gitignore` 排除 IDE、构建产物、日志和环境秘密。真实密钥不进入仓库，后续配置只能提交无秘密示例。

## 7. 文档也是仓库交付物

本仓库把课程实现过程作为可验证事实保存：

- `docs/course/status.csv` 是 96 节状态的唯一来源；
- 完成章节必须同时存在正文、QA 证据和章节 API 记录；
- 长期技术取舍登记 ADR；
- 行为、Schema、配置和接口变化要与实现同批更新；
- `cmd/doccheck` 负责检查可自动判断的结构性漂移。

文档门禁不能证明设计一定正确，但能阻止“状态写成已完成、证据或链接却不存在”这类可机械发现的问题。

## 8. 数据库变化

**无。**

本节只建立 `migrations/` 的未来职责，不创建数据库、不选择 Migration 工具，也不生成空业务表。第 13 节先建立连接与 Migration 机制，第 18 节再因抽奖需求创建第一批业务表。

## 9. API 变化

**无。**

本节没有启动监听端口，也没有新增 HTTP、RPC、事件或 MCP 契约。`cmd/growth-api` 仍是预留入口，第一个 `GET /health` 由第 11 节实现。详细边界见[第 9 节 API 记录](../../api/lessons/lesson-09.md)。

## 10. QA 验收

本节验证：

- 仓库是有效 Git 工作区和 Go module；
- 目录职责与仓库地图一致；
- Go 测试、文档漂移检查、前端类型检查和生产构建通过；
- 完成状态具有正文、QA 与 API 记录；
- 仓库没有因为本节新增业务 API、数据库、缓存、MQ 或微服务实现。

证据见[第 9 节 QA 验收](../../qa/lessons/lesson-09.md)。

## 11. 本节不做什么

- 不解释或实现微服务拆分，第 10 节专门完成该决策；
- 不引入 Gin 或健康接口；
- 不设计配置、日志和错误码；
- 不连接 MySQL，不创建 Migration；
- 不新增 Redis、RocketMQ、Nacos、ClickHouse 或 OpenSearch；
- 不把前端 Mock 交互登记为真实 API；
- 不提交环境秘密、个人 IDE 配置或构建产物。

## 12. ADR 判断

本节不新增 ADR。单仓库、Go 优先、渐进式交付、文档随代码演进等约束已由 [ADR-0001](../../decisions/ADR-0001-evolutionary-delivery.md)、[ADR-0002](../../decisions/ADR-0002-go-first-delivery.md) 和 [ADR-0003](../../decisions/ADR-0003-documentation-as-deliverable.md)覆盖。本节把这些已接受决策落实为可验证的仓库基线，没有形成新的长期取舍。

## 13. 本节复盘

第 9 节建立的不是最终目录树，而是一套让后续变化可落地、可验证、可追溯的最小工程容器。现在可以在同一变更中交付 Go、React、Migration 与文档，同时仍明确哪些目录只是占位、哪些能力尚未开始。

## 14. 下一节留下的问题

仓库已经能够承载多个业务上下文，但“目录分开”不等于“进程必须拆开”。第 10 节需要回答：

> 为什么 GrowthOS 第一版选择模块化单体，而不是直接把 Marketing、Lottery、Benefit、Feed 和 AI Operations 拆成微服务？
