# 第 11 节：使用 Gin 初始化 Go Web 服务

**状态：** 已完成

**日期：** 2026-08-29

**阶段：** Go + React 从零搭建

**本节只建立最小 HTTP 进程、健康接口和可控生命周期；不接入 MySQL、Redis、RabbitMQ 或其他业务基础设施，也不把“进程可启动”描述为“业务后端已完成”。**

## 1. 本节工程诉求

第 9 节建立了可演进的仓库，第 10 节确定第一版使用模块化单体，但到上一检查点为止，`cmd/growth-api` 仍只是目录占位。继续实现日志、数据库或业务用例之前，需要先建立一个可以真实运行和测试的产品进程，并回答四个基础问题：

1. HTTP 路由和进程装配分别放在哪里；
2. 外部如何判断进程已经能够处理 HTTP 请求；
3. 操作系统要求进程退出时，怎样停止接收请求并给在途请求收尾时间；
4. 启动、监听和关闭错误如何传回入口，使失败不会被伪装成正常退出。

本节选择 Gin 不是因为健康接口本身需要复杂框架，而是落实 [ADR-0005](../../decisions/ADR-0005-domestic-mainstream-technology-baseline.md) 已确定的 HTTP 技术主线，并为后续业务路由、中间件和统一错误体系提供同一个演进起点。

## 2. 上一版系统状态

工程基线加固后的仓库具备 Go module、文档工具、质量门禁和 React Mock 框架，但没有产品监听端口：

```text
cmd/growth-api          只有占位边界
internal/infrastructure 没有 HTTP 适配器
业务数据库              未建立
前端                    仍读取 Mock 数据
```

这意味着 `go test ./...` 能验证仓库工具，却无法证明 GrowthOS 有一个产品进程。第 11 节补上的只是第一条可执行竖切片：

```text
OS signal / context
        │
        ▼
cmd/growth-api（装配）
        │
        ▼
httpserver（监听与关闭）
        │
        ▼
httpapi（Gin 路由与 handler）
        │
        ▼
GET /health
```

图中的边界是技术职责，不是新的业务限界上下文。

## 3. 本节范围与非目标

### 3.1 交付范围

- 在 Go 1.26.6 工具链基线上引入 Gin v1.12.0 并建立最小路由；
- 提供 `GET /health` 进程健康接口；
- 用标准库 `http.Server` 承载 Gin handler，而不是直接调用阻塞且难以编排关闭的快捷启动方法；
- 监听 `os.Interrupt` 和 `SIGTERM`，在上下文取消时执行有超时的优雅关闭；
- 将监听、运行和关闭错误传回入口；
- 通过 handler、路由和生命周期测试保护首个运行时契约。

### 3.2 明确不做

- 不连接 MySQL，不创建数据库和 Migration；
- 不连接 Redis、RabbitMQ、RocketMQ、PostgreSQL 或任何其他中间件；
- 不新增活动、抽奖、权益、Feed、MCP 或 Agent 业务接口；
- 不在本节建立完整配置、结构化日志、统一响应和错误码体系；这些属于第 12 节；
- 不修改 React 的 Mock 数据源，也不声称已完成前后端联调；首次联调仍在第 15 节。

本机 Docker Desktop 中是否已经运行某种容器，不等于项目已经使用它。只有代码、配置、验证和文档共同接入后，才可以把基础设施写成当前能力。

## 4. 方案分析

| 方案 | 优点 | 当前问题 | 结论 |
| --- | --- | --- | --- |
| 直接使用 `net/http` | 依赖最少，标准库能力完整 | 与课程已接受的 Gin 技术基线不一致，后续还要迁移路由层 | 不采用 |
| 在 `main` 中调用 Gin 快捷启动 | 代码短，适合一次性示例 | 路由、监听、信号和关闭耦合，难以单独测试错误路径 | 不采用 |
| Gin 作为 handler + `http.Server` 管生命周期 | 保留 Gin 路由生态，也能显式控制启动、错误和关闭 | 初始文件略多 | 采用 |

关键点是把“HTTP 框架”和“进程生命周期”分开。Gin 负责把方法与路径匹配到 handler；标准库 Server 负责监听、在途连接和 Shutdown；`cmd/growth-api` 只负责装配版本、信号和退出码。

### 4.1 为什么采用 Go 1.26.6 与 Gin v1.12.0

实施日 [Gin v1.12.0](https://github.com/gin-gonic/gin/releases/tag/v1.12.0) 是官方最新稳定版，它的官方 [`go.mod`](https://github.com/gin-gonic/gin/blob/v1.12.0/go.mod) 要求 Go 1.25.0。仓库原来的 `go 1.24.0` 不仅不能满足这个依赖要求，而且按 Go 官方[发布策略与历史](https://go.dev/doc/devel/release)已经退出支持窗口。为了保留旧工具链而固定 Gin v1.11.0，会把“少改一个版本号”置于安全补丁和可复现基线之上。

本节因此先把项目最低工具链升级到本机已经安装并验证、仍在官方支持窗口内的 Go 1.26.6，再接受 Gin v1.12.0。CI 使用 `go.mod` 作为 setup-go 的版本输入，本地与 CI 不再分别维护基线；`go.sum` 固定完整依赖图。Go 1.26.6 是本节的最低可复现检查点，并不阻止使用同一受支持分支的更新补丁版本。

工具链升级的方案、支持窗口、补丁维护和 CI 影响由 [ADR-0008](../../decisions/ADR-0008-supported-go-toolchain-baseline.md) 固化。以后升级 Go 或 Gin 必须同时验证官方版本要求、依赖安全与全仓门禁，不能只修改版本号。

## 5. 工程布局与依赖方向

第 11 节把占位边界落实为以下职责：

```text
cmd/growth-api/main.go
  └─ 进程入口、构建版本注入、signal context 与依赖装配

internal/infrastructure/httpapi/
  ├─ health.go       # 健康响应与 handler
  ├─ router.go       # Gin engine 和路由注册
  └─ *_test.go       # handler / router 契约测试

internal/infrastructure/httpserver/
  ├─ server.go       # http.Server、监听、context 取消和 Shutdown
  └─ server_test.go  # 正常关闭与错误传播测试
```

依赖保持单向：入口依赖基础设施装配，HTTP Server 只接收一个 `http.Handler`，并不知道 Gin 路由或未来业务模块的实现。`httpapi` 当前也不依赖任何数据库、缓存或业务包。

这种分法避免两个常见问题：把 handler 塞进 `main.go` 后无法复用测试；让路由层直接控制进程退出后，又难以验证监听和关闭错误。

## 6. 首个健康接口

规范接口是：

```http
GET /health
```

成功时返回 `200 OK`、`Content-Type: application/json`、`Cache-Control: no-store` 和以下结构：

```json
{
  "status": "ok",
  "version": "dev",
  "timestamp": "2026-08-29T12:34:56.123456789Z"
}
```

字段语义：

| 字段 | 语义 |
| --- | --- |
| `status` | 当前进程的最小存活状态；本节固定为 `ok` |
| `version` | 构建标签；默认 `dev` 只表示未注入发布标签的开发构建 |
| `timestamp` | handler 生成响应时的 UTC 时间，格式为 RFC3339Nano |

版本值由入口注入 handler。发布构建可使用 Go linker flag 写入标签，例如：

```bash
go build -ldflags "-X main.version=<label>" ./cmd/growth-api
```

`dev` 不是语义版本，也不能据此声称某个发布已经部署。测试使用可注入时钟生成确定时间，避免依赖真实墙上时钟造成脆弱断言。

`Cache-Control: no-store` 防止中间缓存或浏览器把旧响应中的时间和构建标签误当成当前进程状态。不支持的方法返回 405；统一错误响应体仍留给第 12 节。

### 6.1 为什么路径不带 `/api/v1`

`/health` 描述的是进程和部署单元，不是营销领域资源。它通常被本地脚本、容器探针和编排平台调用，随着业务 API 版本升级仍应保持稳定。因此本节只注册 `/health`，不同时提供 `/api/v1/health` 别名。

重复路径会形成两个都需要长期维护、测试和下线说明的公共契约，却没有新增语义。后续业务 API 可以从 `/api/v1` 开始；访问当前未注册的 `/api/v1/health` 得到 404，但第 12 节建立统一错误体系以前，不把 Gin 默认 404 响应体当作稳定契约。

### 6.2 这是 liveness，不是依赖 readiness

本节没有数据库、缓存或消息依赖，所以 `status=ok` 只证明：请求已经到达当前 Go 进程，Gin 路由和 handler 能够响应。它不证明：

- MySQL、Redis 或 MQ 可用；
- 业务 Migration 已执行；
- 前端已经完成真实联调；
- 活动、抽奖或权益链路可以工作；
- 系统达到第 7 节的容量、可用性或恢复目标。

以后出现真实必需依赖时，再基于启动和流量接入语义决定是否增加 readiness；不能让一个总是返回 200 的接口伪装成依赖检查。

## 7. 进程生命周期

运行路径按以下顺序建立：

1. `main` 创建能够接收 `os.Interrupt` 与 `SIGTERM` 的 signal context；
2. 入口装配版本、Gin router 与 HTTP Server；
3. Server 默认监听 `:8080`，固定采用 5 秒请求头、15 秒读取、30 秒写入和 60 秒空闲连接超时；本节尚未引入环境配置体系；
4. 服务运行期间等待监听结果或 context 取消；
5. 收到正常终止信号后，创建最长 5 秒的关闭上下文并调用 `Shutdown`；
6. 在途请求在窗口内完成，监听器停止接受新连接；
7. 正常信号关闭返回 `nil`，监听、Serve 或 Shutdown 的异常继续向上传播；
8. `main` 记录非空错误并以非零状态退出。

```text
启动 ──> 监听 :8080 ──> 处理请求
                    ├─ Serve/监听错误 ──> 返回错误 ──> 非零退出
                    └─ SIGINT/SIGTERM ──> Shutdown(5s)
                                           ├─ 成功 ──> 正常退出
                                           └─ 失败 ──> 返回错误 ──> 非零退出
```

优雅关闭不等于无限等待。关闭窗口到期时必须把错误暴露给进程管理器，不能静默假装所有请求已经安全完成。反过来，`http.ErrServerClosed` 是主动 Shutdown 的预期结果，不应被误报为运行故障。

本节保留固定地址和固定关闭窗口，是为了先把生命周期语义做清楚。第 12 节引入配置体系时，应把可部署差异集中管理并验证非法值，而不是从多个包直接读取环境变量。

Gin 默认会信任所有代理网段提供的转发地址。当前项目尚未配置受信反向代理，如果照搬默认值，客户端可以伪造 `X-Forwarded-For`，污染后续基于来源 IP 的日志、审计和控制。本节在 Gin v1.12.0 的 router 初始化时显式禁用代理信任，并用测试证明 `ClientIP()` 只采用直连对端；第 12 节以后只有拿到明确代理 CIDR allowlist 才能重新启用。

## 8. 可测试性设计

最小服务也需要保护失败路径，而不只测试一条 200：

| 层次 | 应验证内容 | 隔离方式 |
| --- | --- | --- |
| Health handler | 状态码、JSON Content-Type、三个字段和 UTC RFC3339Nano 时间 | 注入固定时钟与版本 |
| Router | `GET /health` 命中；未注册的版本化别名返回 404；不支持的方法返回 405 | `httptest`，不占真实端口 |
| 来源地址 | 默认忽略客户端伪造的 `X-Forwarded-For` | 固定 RemoteAddr 与转发头对照 |
| HTTP Server | context 取消触发 Shutdown，正常关闭不报错 | 临时监听地址或受控 Server |
| 错误路径 | 无法监听、Serve 失败或 Shutdown 失败时向上传播 | 注入/构造可重复错误条件 |
| 仓库回归 | 所有 Go 包、文档检查和已有前端门禁保持通过 | `make verify` |

测试不应依赖本机 `:8080` 恰好空闲，也不应通过固定 sleep 猜测服务是否已启动。时间、地址和取消信号都要可控，才能让本地与 CI 得到一致结果。

## 9. 本地运行与人工核查

主代理完成最终质量门禁后，可用以下命令复现本节行为：

```bash
go run ./cmd/growth-api
```

在另一个终端请求健康接口：

```bash
curl -i http://127.0.0.1:8080/health
```

然后向前台进程发送 `Ctrl+C`，确认进程在关闭窗口内退出。人工观察只能补充自动化测试；不能用一次 curl 代替错误传播和生命周期测试。

## 12. QA 验收

本节最终需要同时核查：

- Gin 路由契约和时间/版本字段可重复测试；
- 仅注册规范 `/health`，没有隐式形成第二条版本化健康契约；
- signal context、5 秒关闭预算和错误传播符合设计；
- 请求头、读取、写入和空闲连接超时固定为 5/15/30/60 秒并由回归测试保护；
- 默认不采信未配置代理的转发来源地址；
- `cmd` 只装配，HTTP API 与 Server 生命周期职责分开；
- 没有提前接入数据库、Redis、MQ 或业务 API；
- Go、文档和既有前端质量门禁全部通过。

实际命令、环境、运行时响应、信号退出码和剩余风险见[第 11 节 QA 验收证据](../../qa/lessons/lesson-11.md)。本节普通测试、Race 测试、全仓门禁和真实进程冒烟均已通过。

## 14. 本节复盘

第 11 节建立的价值不只是返回一段 JSON，而是给后续能力一个受控的运行边界：路由可以单测、进程能够响应终止信号、监听与关闭错误不会被吞掉、构建身份和时间语义可以验证。

同时，边界仍然很小。当前只是一个没有业务依赖的 Gin 进程；数据库、缓存、消息、业务接口、真实前端联调和生产 readiness 都尚未完成。

## 15. 下一节遗留问题
