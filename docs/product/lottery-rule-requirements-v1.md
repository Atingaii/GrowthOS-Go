**状态：** v1 需求分析基线；第 23 节只确认问题、语言、所有权和演进边界，不代表规则已经实现

**更新日期：** 2026-08-30

**来源章节：** 第 23 节“需求升级抽奖策略需要规则”

**关联决策：** [ADR-0019：Lottery 规则所有权与评估边界](../decisions/ADR-0019-lottery-rule-ownership-and-evaluation-boundaries.md)

## 1. 先给结论

GrowthOS 当前能回答的问题是：

> 给定一个已经合法重建的 `Strategy` 快照，怎样从其固定 Award 集合中完成一次无偏的加权选择？

真实营销抽奖还必须回答另一组问题：

- 当前活动是否允许参与；
- 这个主体是否满足参与条件、是否还有次数、是否被风险策略拒绝；
- 应当路由到哪个 Strategy 或候选池；
- 候选奖励此刻是否可分配；
- 本次选择依据了哪些规则版本和事实版本；
- 失败究竟是业务拒绝、权限拒绝、资源不可用，还是技术故障；
- 已经完成选择后怎样形成唯一最终结果并进入权益交付。

这些问题不会由一个“万能 Rule 接口”统一拥有。规则应跟随事实所有者和业务阶段分布在 Marketing、Participation、Lottery、Benefit 与 Governance 等边界中；Lottery 现有 `WeightedSelector` 继续只承担终端加权选择，不读取用户、活动、库存、权限或缓存。

第 23 节的交付物是可追溯的需求与架构停止线，不新增 Go 接口、数据库表、HTTP 字段、React 判断、Redis 访问或规则引擎。第 25～30 节会在真实需求和失败证据出现后逐步实现资格、规则链、规则树、决策引擎与 Activity 边界；第 31～35 节再建立公共访问控制；第 43～52 节逐步闭合库存、结果快照、可靠交付与补偿。

## 2. 当前真实基线

第 17～22 节已经建立：

1. Lottery `Strategy` / `Award` 聚合及正整数相对权重；
2. 两张 MySQL 配置表、原子 Create 与一致快照 FindByID；
3. 对完整 `uint64` 范围成立的无偏 `WeightedSelector`；
4. development/test 专用、默认关闭、只读的 ephemeral selection API；
5. 真实消费该临时 API 的 React 页面。

这些能力只证明：合法配置能够被读取，并能选择配置中的一个 `reward` 或 `no_reward` Award。它们没有证明：

- 存在可发布的 Activity 或公开活动身份；
- 请求对应真实用户、会员或参与账户；
- 用户符合资格、拥有额度或通过风控；
- 存在 Strategy/规则版本或可回放决策；
- 奖励有库存、已预占或能够发放；
- 存在 DrawID、幂等键、唯一最终结果或结果查询；
- 接口已经认证、授权、限流或可用于生产；
- Redis 已参与任何 Lottery 业务判断。

因此，本文件不能把当前 ephemeral selection 重命名成正式抽奖，也不能用文档虚构尚不存在的领域对象和实现证据。

## 3. 触发本次升级的组合场景

本轮需求分析使用一个足够具体、但尚不落代码的“新用户抽奖”场景：

> 一场面向新用户的活动只有在已发布且处于有效时间窗时才能参与。请求主体必须满足新用户定义、仍有可用参与次数，且没有被风险判断拒绝。不同会员等级可能路由到不同 Strategy。无法分配的奖励不能被当作可发放奖励；合法完成选择后仍可能命中 Strategy 中显式配置的 `no_reward`。

该场景故意把不同来源的判断放在一起，以暴露边界，而不是要求第 23 节一次性实现它们。

### 3.1 期望的概念流程

```text
调用身份与权限前置检查
  -> Activity 发布态/时间窗检查
  -> Participation 新用户/额度/风险资格判断
  -> Lottery Strategy 路由与决策
  -> 奖励可分配性确认
  -> 现有 WeightedSelector 终端选择
  -> 正式 Draw/Result 落定
  -> Benefit 受理、发放或补偿
```

这只是业务阶段图，不是包结构、函数调用顺序、同步协议、规则 DSL 或事务设计。后续章节可以在不改变语义边界的前提下选择同步查询、快照、预占、事件或本地模块调用。

### 3.2 场景中的四个关键反例

1. 用户不满足新用户条件时，不能通过选择 `no_reward` 假装完成抽奖；这是参与资格拒绝，选择根本不应开始。
2. 库存服务超时或所有 reward 候选都无法确认可分配时，不能降级为 `no_reward`；这是资源不可用或技术结果未知。
3. 操作者没有读取或修改 Strategy 的权限时，不能返回“用户不符合活动规则”；这是授权边界，不能借业务文案隐藏。
4. `WeightedSelector` 的随机源失败时，不能重新执行整条流程后声称仍是同一次抽奖；当前没有正式 Draw/Result 和幂等事实。

## 4. 统一语言与禁止混用

| 术语 | 本文件中的唯一含义 | 禁止混用 |
| --- | --- | --- |
| 业务规则 | 根据权威事实对业务阶段作出继续、拒绝、路由或约束判断 | HTTP 校验、CSS 条件、数据库 CHECK 的统称 |
| 事实 | 由明确权威来源确认、带身份和必要时效语义的数据 | 客户端自报字段、过期缓存、推测值 |
| 资格 / Eligibility | 主体是否满足一次 Activity Participation 的业务条件 | 登录成功、拥有后台权限、中奖 |
| 授权 / Authorization | 已识别主体是否可对资源执行动作及其数据范围 | 新用户判断、次数校验、页面是否显示 |
| 路由 / Routing | 根据已确认事实选择后续 Strategy、规则集或候选池 | 加权随机选择、HTTP 路由 |
| 可分配性 / Availability | 某奖励在本次业务承诺前是否可被安全分配 | Award 配置存在、前端显示“有货” |
| 选择 / Selection | 在确定候选集合内依据权重得到一个 Award | 已预占库存、已形成最终 Draw、已发奖 |
| `reward` | Strategy 中合法的奖励候选结果 | 权益已经到账 |
| `no_reward` | Strategy 中显式配置且被合法选中的未中奖结果 | 资格拒绝、无库存、超时、异常 fallback |
| 拒绝 / Rejection | 规则依据足够事实作出的确定业务结论 | 依赖失败、数据未知、权限不足 |
| 技术失败 | 依赖、数据契约、超时或内部不变量使系统无法作出可信决定 | 用户不符合条件 |
| 结果未知 | 请求可能产生副作用但调用方暂时不能确认最终事实 | 可以安全地当作失败重新抽取 |

### 4.1 三类决策必须正交

一个请求至少可能经过三类互不替代的判断：

1. **访问决策：** 谁在调用，是否允许对目标资源执行动作；
2. **业务资格决策：** 这个参与主体是否满足活动规则；
3. **Lottery 结果决策：** 在合法候选内最终选中什么。

访问允许不代表业务资格成立，业务资格成立也不代表必然中奖。前端隐藏入口只是一种体验投影，不能替代访问决策；命中 `no_reward` 也不能反推用户不合格。

## 5. 从第一性原则拆解规则问题

任何规则进入系统前，都先回答七个问题：

1. **为什么需要它：** 它保护的是活动承诺、用户资格、预算、库存、风控还是权限？
2. **依据什么事实：** 输入是否来自权威源，是否有采集时间、版本和完整性要求？
3. **谁拥有结论：** 哪个上下文有权确认继续、拒绝或路由，谁只能消费摘要？
4. **何时评估：** 在参与建立前、候选选择前、结果落定前，还是发放前？
5. **失败意味着什么：** 确定拒绝、暂时不可用、结果未知还是内部错误？
6. **怎样解释和审计：** 稳定 code、用户文案、内部 trace 与敏感信息怎样分离？
7. **怎样演进：** 规则身份、规则集版本、配置 schema 和事实版本如何各自变化？

只有这些问题有了稳定答案，才有资格讨论责任链、规则树、决策表、DSL 或第三方引擎。先选技术再寻找规则，会把当前示例偶然形状固化为长期架构。

## 6. 规则分类与阶段所有权

### 6.1 Activity 门控规则

典型问题：Activity 是否已发布、是否在时间窗、是否暂停、渠道是否允许。

- 权威事实：Activity 版本与生命周期；
- 决策所有者：Marketing；
- 输出：允许进入 Participation，或以稳定业务原因拒绝；
- 不应进入：Lottery Strategy 字段、WeightedSelector、React 本地时钟；
- 计划落点：第 30 节校准 Strategy/Activity 边界，后续 Activity 流程继续深化。

### 6.2 Participation 资格规则

典型问题：是否新用户、是否命中目标人群、是否还有次数、是否通过参与风控。

- 权威事实：主体引用、用户/会员事实摘要、参与账户、参与订单和额度流水；
- 决策所有者：Participation；
- 输出：确定允许或业务拒绝；
- 不应进入：Lottery Award 权重、前端表单、授权角色；
- 计划落点：第 25 节建立首个用户资格，第 26 节用最小责任链组合前置判断。

### 6.3 Lottery 决策与路由规则

典型问题：某会员等级使用哪个 Strategy、某风险分层是否进入保守池、规则结果怎样选择后续节点。

- 权威事实：Lottery 发布的决策配置，以及来自其他上下文的受控事实快照；
- 决策所有者：Lottery；
- 输出：继续、拒绝或路由到明确的 Strategy/候选集合；
- 不应进入：用户身份生命周期、Activity 发布状态、权益到账状态；
- 计划落点：第 27 节用真实复杂度暴露线性链不足，第 28～29 节再设计持久化规则树与执行引擎。

### 6.4 候选可分配规则

典型问题：奖励是否还有可分配库存、是否处于有效期、外部券模板是否可用。

- 权威事实：Benefit 上下文内部库存子能力持有的库存、模板和交付状态；
- 结论所有者：Benefit；Lottery 只能消费可分配摘要或预占结果；
- 输出：候选可用于本次承诺、不可用，或技术上无法确认；
- 不应进入：Award `Weight == 0` 魔法值、Strategy 名称、浏览器静态数组；
- 计划落点：第 43～44 节形成 MySQL 与 Redis Lua 库存语义，第 45 节串联完整活动抽奖。

“排除不可用候选后怎样处理权重”是后续必须显式决定的产品规则。本文件不默认在剩余候选间重归一化，也不默认把不可用权重转给 `no_reward`；这两种做法都会改变用户实际概率，需要版本化、审计和产品确认。

### 6.5 终端加权选择规则

典型问题：在一个已确定、合法且稳定的 Strategy 快照内怎样按相对权重选择 Award。

- 权威事实：Lottery Strategy/Award 配置；
- 所有者：Lottery；
- 当前实现：`WeightedSelector`；
- 输出：`reward` 或 `no_reward` Award，或技术失败；
- 不应新增：用户、活动、库存、权限、HTTP、Redis 依赖。

### 6.6 正式 Draw/Result 落定规则

典型问题：合法参与和终端选择怎样形成可查询、可恢复且不可再次随机的正式结果。

- 权威事实：参与业务 identity、规则/Strategy 快照、选择事实与 Draw/Result 状态；
- 决策所有者：Lottery；Benefit 的可分配或预占结果只是落定前的受控输入；
- 输出：正式结果、处理中或结果未知，不把响应超时解释为可以重新随机；
- 计划落点：第 45 节形成完整活动抽奖主链，第 51 节补齐结果快照与恢复；
- 不应进入：Benefit 发放流水或第 23 节 ephemeral selection 响应。

### 6.7 Benefit 发放与补偿规则

典型问题：正式结果怎样被受理并交付，重复消息如何去重，外部发放失败怎样补偿。

- 权威事实：Benefit 内部库存预占、Reward、发放流水、外部回执与补偿状态；
- 决策所有者：Benefit；Lottery 只提供不可变 Draw/Result 引用或必要快照；
- 输出：受理、处理中、交付成功、交付失败或补偿状态；
- 计划落点：第 46～52 节逐步处理一致性、可靠消息、结果快照、发放状态机与补偿；
- 不应进入：Lottery 规则接口、WeightedSelector 或临时选择响应。

### 6.8 访问控制规则

典型问题：操作者能否读取、创建、发布、修改或审批某个资源，作用域是什么。

- 权威事实：身份、主体、角色、权限、资源、动作和数据范围；
- 决策所有者：Governance（统一访问控制能力）；
- 计划落点：第 31～35 节；
- 不应进入：Participation “新用户”规则或 Lottery 业务拒绝原因。

## 7. 权威事实与信任契约

### 7.1 三个角色必须分开

| 角色 | 负责什么 | 不能做什么 |
| --- | --- | --- |
| 事实所有者 | 确认某条事实成立并维护其生命周期 | 把消费者的本地缓存当成自己的权威写模型 |
| 规则所有者 | 定义怎样根据事实作出业务判断 | 擅自改写其他上下文的事实语义 |
| 编排者 | 按业务阶段获取决定并组合流程 | 因调用方便而吞并所有规则和数据 |

规则代码放在哪个包不是事实所有权的充分证据。即使 Modular Monolith 中一次函数调用跨过两个模块，调用方仍只能消费被提供的契约，不能直接查写对方表后自行宣布结论。

### 7.2 事实台账

| 事实 | 权威来源 | 消费方式要求 | 时间/版本要求 | 不可用时语义 | 计划章节 |
| --- | --- | --- | --- | --- | --- |
| 调用者身份与会话 | 企业 IAM/身份能力，经 Governance 适配 | 只接收服务端确认的 Principal，不信任客户端角色 | 会话签发、过期与撤销语义独立 | 未认证，不是业务不合格 | 31～35 |
| Activity 发布态、时间窗、版本 | Marketing | 读取发布快照或由 Marketing 给出门控决定 | 明确业务时区、版本和评估时刻 | 无法确认时不可继续 | 30 及后续 Activity 章节 |
| 用户注册/会员等级等主数据 | 外部用户/会员系统 | 通过防腐层取得必要最小摘要 | 带来源、采集时间；不得由浏览器自报 | 无法确认时是依赖失败/暂不可用 | 25～29 |
| 新用户/目标人群资格 | Participation | 消费权威用户摘要后形成参与决定 | 规则身份和规则集版本可追溯 | 确定不符合才是业务拒绝 | 25～29 |
| 可用参与次数与已消费流水 | Participation | 通过参与账户/订单确认，不从 UI 余额推算 | 并发下需要版本或事务证据 | 无法确认时不能继续选择 | 39～45 |
| 风险判断 | 风险事实提供方；Participation 拥有本场景准入决定 | 只消费最小 verdict 与必要版本，不复制原始敏感特征 | 明确有效期和决策时间 | 超时不能默认通过 | 25～29，后续风险能力再校准 |
| Strategy/Award/Weight | Lottery | 通过合法聚合快照使用 | 当前尚无聚合版本，不得伪造 | 非法/缺失为配置或技术失败 | 已有 17～20；版本后续决定 |
| Strategy 路由与决策图 | Lottery | 第 27～29 节只使用显式、可识别且已经验证/恢复的不可变配置；第 30 节才由 Activity 发布绑定 | graph revision 与 schema version 分离；不得隐式选择 latest | 配置无效必须失败关闭 | 27～30 |
| 奖励可分配库存与模板状态 | Benefit（内部库存子能力） | 查询可信摘要或执行预占；不能读 UI 展示字段 | 需要版本、时效与并发语义 | 不可用与无库存分开 | 43～52 |
| 最终 Draw/Result | Lottery | 由唯一业务请求形成可查询事实 | 固定规则、Strategy、事实快照版本 | 结果未知必须查询/恢复 | 45、51～52 |
| 权益发放状态与流水 | Benefit | 以幂等业务命令推进状态 | 唯一流水、重试与补偿可追溯 | 处理中/失败不能显示假成功 | 46～61 |
| 当前时刻 | 受控服务端时钟 | 所有时间规则使用一次评估时刻 | 指定时区；不得每个规则各读一次浏览器时钟 | 时钟不可信时失败并告警 | 规则实现时引入 |

## 8. 需求目录

### 8.1 场景与产品语义

| 编号 | 需求 | 可验收边界 |
| --- | --- | --- |
| LRR-001 | 系统必须在执行终端加权选择前确认 Activity 门控、Participation 资格和目标 Strategy 路由已经得到可信决定 | 任一前置阶段未确认时不得调用 `WeightedSelector` |
| LRR-002 | “新用户”的业务定义必须有稳定规则身份并说明所依据的权威事实，不能由昵称、前端标记或客户端时间推测 | 客户端篡改 `is_new_user` 不影响服务端决定 |
| LRR-003 | 会员分层路由必须输出明确 Strategy/决策目标；没有匹配分支时按显式缺省策略处理，而不是取 map 第一项 | 同一事实快照和规则版本得到同一路由结果 |
| LRR-004 | 合法未中奖必须来自 Strategy 中显式的 `no_reward` Award | 资格拒绝、无库存、依赖失败均不能序列化成 `no_reward` |
| LRR-005 | 奖励不可分配时的概率处理必须由版本化产品策略明确决定 | 在决定前不得默认重归一化、补抽或转移权重 |
| LRR-006 | 选择 reward 只表示 Lottery 选择结果，不表示库存已扣、Draw 已持久化或权益已到账 | UI/API/日志不能提前显示发放成功 |
| LRR-007 | 正式流程必须有唯一请求/参与/Draw 身份后，才能承诺安全重试或结果查询 | 当前 ephemeral API 继续明确不可当正式 Draw |

### 8.2 决策确定性与顺序

| 编号 | 需求 | 可验收边界 |
| --- | --- | --- |
| LRR-008 | 除终端随机票据外，相同规则版本、相同事实快照和相同评估时刻必须产生相同前置决定 | 不依赖 map/SQL 偶然顺序或每节点各读当前时间 |
| LRR-009 | 规则的评估顺序必须有业务理由和确定定义；先后顺序影响可见原因或副作用时必须成为版本化契约 | 变更顺序需要兼容与回归证据 |
| LRR-010 | 前置判断默认短路：一旦得到足够的确定拒绝，不再执行无必要的下游选择和外部副作用 | 被拒绝请求不消费随机票据、不创建发放事实 |
| LRR-011 | 为内部诊断可以记录多个无副作用判断，但用户最终原因必须遵循稳定优先级和最小披露原则 | 不因并行执行顺序导致响应 reason 漂移 |
| LRR-012 | `WeightedSelector` 仍是无用户、活动、库存和权限依赖的纯终端选择器 | 第 23 节及后续规则不得给它增加这些字段或端口 |

### 8.3 事实质量与时效

| 编号 | 需求 | 可验收边界 |
| --- | --- | --- |
| LRR-013 | 每个外部事实必须登记来源、必要采集时间、可接受新鲜度及未知处理方式 | 规则不能把缺字段默认成允许 |
| LRR-014 | 决策读取缓存时必须知道缓存的是可重建投影而非权威事实，并有版本/失效语义 | 第 24 节 Redis 不缓存用户资格或一次决策结果 |
| LRR-015 | 时间窗判断使用受控服务端评估时刻和显式业务时区 | 浏览器时钟、节点时区或夏令时差异不决定资格 |
| LRR-016 | 涉及库存、额度或一次性承诺的事实不能仅靠先读后写的陈旧布尔值保证 | 后续章节必须提供事务、版本、预占或原子证据 |
| LRR-017 | 跨上下文复制的事实必须标明来源、版本/采集时间和失效策略 | 消费者不得修改副本后反向宣布权威事实 |

### 8.4 版本、解释与审计

| 编号 | 需求 | 可验收边界 |
| --- | --- | --- |
| LRR-018 | 规则身份、规则集版本、配置 schema 版本、Strategy 版本和应用发布版本必须概念分离 | 不能用 Git SHA 或 `updated_at` 冒充全部版本 |
| LRR-019 | 稳定 `RuleCode` / `ReasonCode` 与可修改用户文案分离 | 文案调整不破坏指标、客户端分支或历史查询 |
| LRR-020 | 内部决策轨迹按评估顺序记录规则身份、版本、结果类别、必要耗时和来源摘要 | 不记录随机材料、完整 PII、凭证或风险原始特征 |
| LRR-021 | 正式 Draw/Result 出现后，应能关联当时使用的 Activity、规则集、Strategy 和必要事实版本/快照 | 事后不能只用当前配置解释历史结果 |
| LRR-022 | 用户可见解释、运营诊断和安全审计采用不同披露级别 | 普通用户看不到风控阈值、角色策略或内部拓扑 |

### 8.5 失败、安全与恢复

| 编号 | 需求 | 可验收边界 |
| --- | --- | --- |
| LRR-023 | 业务拒绝、未认证、无权限、资源不可用、技术失败和结果未知必须保持不同稳定类别 | 指标、重试、HTTP 映射和用户文案可分别处理 |
| LRR-024 | 规则依赖失败默认失败关闭；只有经产品和风险评审的非关键增强规则才能显式降级 | 风控/资格/权限依赖超时不能默认放行 |
| LRR-025 | 规则输入必须由服务端从可信上下文收集；客户端只能提交业务意图和必要标识，不能提交最终资格/角色/verdict | 修改请求 JSON 不能越过资格或授权 |
| LRR-026 | 决策超时或调用中断不得静默再次随机选择；有副作用后结果未知时必须通过业务身份查询或恢复 | 正式 Draw 前不宣传透明自动重试 |
| LRR-027 | 规则配置必须在启用前验证根、边、循环、深度、不可达节点、缺省分支与结果确定性 | 第 28～29 节的规则树不能“存得进去就能运行” |
| LRR-028 | 任何规则失败不得泄露 SQL、错误链、凭证、完整输入、风控阈值或随机材料 | 公开响应只含安全 code、message 与关联 ID |

| 编号 | 需求 | 可验收边界 |
| --- | --- | --- |
| LRR-029 | 新规则先登记业务目的、事实所有者、决策所有者、失败语义和顺序，再选择实现模式 | 评审不接受只有类图或 DSL 的规则需求 |
| LRR-030 | 不同上下文的规则不得为了复用一个接口而失去各自语言；共享只能发生在无业务语义的基础设施层 | Authorization、Eligibility、Inventory 不共用万能 `Rule` 模型 |
| LRR-031 | 访问控制由第 31～35 节公共模型统一安排；业务规则不得检查硬编码 `admin`，前端不得成为安全边界 | 直接 API 与 UI 投影最终使用同一服务端授权语义 |
| LRR-032 | 规则技术升级必须由真实复杂度、可变更性、解释或运营配置需求触发 | 第 23 节不新增责任链、树、DSL 或第三方引擎 |

## 9. 决策输出与失败语义

### 9.1 概念输出类别

未来各阶段可以使用不同领域类型，但必须能表达以下概念，不能用一个 `bool` 或一个 `error` 包办：

| 概念结果 | 含义 | 是否进入下游 | 是否可直接重试 |
| --- | --- | --- | --- |
| Continue | 当前阶段条件成立 | 可以 | 不适用 |
| Reject | 事实充分，业务条件不成立 | 不可以 | 同一事实/版本下没有意义 |
| Route | 选择明确的后续分支或 Strategy | 进入指定分支 | 不适用 |
| Unavailable | 业务资源目前无法提供，但不是用户违规 | 通常不可以 | 取决于是否已产生副作用和产品策略 |
| Technical failure | 无法得到可信决定 | 不可以 | 仅在幂等/无副作用证据充分时 |
| Unknown | 可能已经形成结果但调用方无法确认 | 不可以重新随机执行 | 必须查询、恢复或人工处理 |

这张表不是要求创建通用枚举。每个上下文应使用自己的业务语言，并由编排层把结果映射到稳定跨层语义。

### 9.2 外部表现矩阵

| 场景 | 内部类别 | 对用户的最低解释 | 监控类别 | 禁止表现 |
| --- | --- | --- | --- | --- |
| Activity 未开始/已结束 | 确定业务拒绝 | 活动当前不可参与 | 业务拒绝，按 reason 聚合 | `no_reward`、500 |
| 用户不是新用户 | 确定业务拒绝 | 不满足参与条件 | 业务拒绝，敏感维度受限 | 权限不足、系统错误 |
| 次数不足 | 确定业务拒绝 | 可用参与次数不足 | 额度拒绝 | 随机补抽 |
| 风险 verdict 拒绝 | 确定业务拒绝 | 请求暂不能参与；具体披露由风控策略决定 | 安全审计/低基数指标 | 暴露规则阈值或特征 |
| 未认证 | 认证失败 | 需要登录或会话已失效 | 认证指标 | 伪装成不符合活动条件 |
| 无权管理 Strategy | 授权拒绝 | 无权执行该操作 | 授权拒绝审计 | 只隐藏按钮却允许 API |
| 命中 `no_reward` | 选择成功 | 本次未中奖 | 成功结果分布 | error、重试提示 |
| 候选库存为零 | 业务资源不可用 | 奖励暂不可用或按已定义产品策略处理 | 库存/可用性指标 | 自动改成 `no_reward` |
| 库存依赖超时 | 技术失败/未知 | 暂时无法完成，请按结果身份查询或稍后处理 | 依赖错误/未知结果 | 默认认为库存为零或允许 |
| 随机源失败 | 技术失败 | 暂时无法完成 | Lottery 技术错误 | `no_reward` 或 fallback Award |

### 9.3 Reason 优先级

当多个无副作用条件同时不满足时，系统仍只对外给出一个稳定主原因。优先级必须同时考虑：

1. 是否会泄露资源、活动或风控存在性；
2. 用户能否采取行动修复；
3. 是否需要阻止后续副作用；
4. 指标是否保持低基数和长期兼容；
5. 同一规则版本下是否确定。

内部可以保留更完整的安全审计，但不能把所有命中原因直接返给普通用户。

## 10. 版本与决策证据模型

本节只定义概念，不创建字段或表。

### 10.1 必须区分的版本

| 版本 | 回答的问题 | 当前状态 |
| --- | --- | --- |
| Rule identity | 历史上是哪条业务规则 | 尚未实现 |
| RuleSet version | 一组规则在某次发布时的不可变组合 | 尚未实现 |
| Rule schema version | 规则配置结构怎样解析/迁移 | 尚未实现 |
| Strategy version | 某次选择使用哪份 Award/Weight 快照 | 当前没有，禁止用行 `updated_at` 冒充 |
| Activity version | 哪个发布版本引用哪份规则/Strategy | 第 30 节以后定义 |
| Fact source version | 输入事实来自哪个来源版本/水位 | 尚未实现 |
| Application version | 哪版程序执行了决定 | 可辅助诊断，不能替代业务版本 |

### 10.2 决策轨迹的最低概念信息

未来内部 trace 至少需要回答：

- 哪个业务请求、参与或 Draw 触发评估；
- 使用了哪个 Activity/规则集/Strategy 身份与版本；
- 哪些规则按什么确定顺序被评估；
- 每步得到继续、拒绝、路由或失败中的哪一类结果；
- 依赖事实来自何处，是否满足新鲜度要求；
- 哪一步短路，是否发生副作用；
- 公开 reason 与内部诊断怎样对应；
- 整体关联 ID 和必要耗时。

不得记录密码、会话 Cookie、完整个人资料、风险原始特征、券码、随机字节或 selector ticket。需要审计的不是“把所有输入全存下来”，而是用最小必要证据证明当时按哪份规则和可信事实作出了什么决定。

## 11. 威胁模型与信任边界

### 11.1 客户端到服务端

**威胁：** 客户端伪造新用户、会员等级、角色、库存或规则命中结果；修改隐藏字段；绕过前端入口直接请求 API。

**边界要求：** 客户端提交意图和必要身份引用，服务端从可信来源收集事实并重新授权。前端规则只用于输入提示和体验，不成为业务或安全证据。

### 11.2 身份/会员/风险来源到 Participation

**威胁：** 映射错误、陈旧快照、超时 fallback、过度复制个人数据、不同来源同名字段语义不一致。

**边界要求：** 使用防腐层与最小事实摘要，登记来源、新鲜度和未知策略；安全关键事实未知时失败关闭。Participation 确认本场景资格，不能让外部服务直接宣布 GrowthOS Participation 已成立。

### 11.3 Marketing/Participation 到 Lottery

**威胁：** Lottery 直接读对方表并自行解释发布态/额度；重复请求多次消费；上游用客户端可改字段冒充已验证决定。

**边界要求：** 只接受清晰的业务身份、可信决定或版本化事实快照。跨边界契约必须说明谁能确认参与已合法建立；正式 Draw 出现前不承诺幂等与唯一结果。

### 11.4 规则配置到执行器

**威胁：** 非法图、循环、不可达节点、缺省分支漂移、未知算子、超深配置导致资源耗尽、旧执行器误读新 schema。

**边界要求：** 发布前验证、schema 兼容、确定顺序、资源限制和失败关闭。数据库能保存 JSON 或节点，并不证明规则可安全执行。

### 11.5 缓存到规则消费者

**威胁：** 把 Redis 当权威源；缓存 key 没有版本；失效窗口让资格、库存或路由使用过期事实；缓存穿透触发不受控重试。

**边界要求：** 第 24 节只缓存可由 MySQL 重建的 Strategy 读取投影，并登记格式版本、TTL、miss/failure 回源和删除策略；不缓存一次性用户资格、决策结果、库存承诺或授权结论。

### 11.6 Lottery 到 Benefit（内部库存子能力）

**威胁：** 先看“有库存”再选择，随后并发耗尽；选择成功被前端当作到账；失败后重新抽取造成结果漂移。

**边界要求：** 后续章节明确候选过滤、预占、最终结果和发放的原子/补偿关系。在此之前不把 reward 候选宣传成已交付事实。

### 11.7 规则日志与审计系统

**威胁：** 高基数输入污染日志、控制字符注入、记录完整 PII/凭证/风控特征、普通操作者可篡改拒绝记录。

**边界要求：** 使用稳定低基数 code 与关联 ID，敏感字段最小化、脱敏和分权；审计记录与普通业务写权限分离。OWASP Logging Cheat Sheet 也明确建议避免直接记录访问令牌、会话标识和敏感个人数据，并防止日志注入；本项目只把该原则作为后续设计约束，不声称第 23 节已实现审计系统。

### 11.8 访问控制与业务规则的交界

**威胁：** 用“规则没通过”掩盖服务端无授权；为每个页面写不同角色开关；因资源不存在与无权限的响应差异泄露对象存在性。

**边界要求：** 第 31～35 节统一身份、主体、资源、动作和范围，服务端默认拒绝，前端只消费能力投影。具体 403/404 披露策略由访问控制威胁模型决定，但内部审计仍需区分授权判定与业务资格。

## 13. 明确停止线

第 23 节不得新增或修改以下实现：

- `Rule`、`RuleEngine`、`Specification`、`RuleChain` 等 Go 接口或结构；
- `map[string]any`、自由 JSON 表达式、脚本、插件或第三方规则引擎；
- 规则表、规则节点表或 `000003` Migration；
- Strategy/Award 表、领域字段、Repository、Selector 或随机源；
- Activity、User、Quota、Risk、Inventory、Draw/Result 的伪实体；
- ephemeral Lottery API 路由、DTO、状态码或 feature gate；
- React 资格判断、会员路由、库存过滤或权限开关；
- Redis 业务读取或 key；
- 认证、会话、RBAC、中间件或对象权限；
- 伪造的 Strategy/规则版本、`updated_at` 版本或历史 trace；
- 生产流量、业务 SLO、公平审计或合规结论。

本节也不能用一个大 `if/else` handler 代替规则模型。正确动作不是“先写简单点”，而是暂时不写生产实现，先把真实需求和责任边界说清楚。

## 14. 被评估但暂不决定的问题

以下问题已经被发现，但需要后续事实后再决定：

1. 不可用 reward 是在选择前过滤、预占后进入选择，还是由专用 fallback Strategy 处理？
2. 过滤候选后，权重重归一化、保持中奖率还是转移到显式 no_reward？
3. 新用户资格在活动开始时、首次参与时还是每次请求时计算并快照？
4. 风险规则是同步强制门、异步标记还是按风险等级组合？
5. 规则更新是否只影响新 Participation，还是允许已创建请求使用新版本？
6. Activity 怎样引用已发布 Strategy/RuleSet 版本，更新时是否需要审批？
7. 正式 Draw 在库存预占前还是后形成最终结果，未知状态怎样恢复？
8. 用户 reason 应披露到什么粒度，怎样防止枚举对象与反推风控阈值？
9. 什么时候真实规模证明需要决策表/DMN 兼容、表达式语言或外部规则平台？

这些问题被显式保留，比在没有证据时选择一个“看起来完整”的答案更可维护。

## 16. 外部参考与采用边界

以下来源用于校准概念，不等于项目已经采用对应标准或产品：

1. [OMG Decision Model and Notation (DMN)](https://www.omg.org/dmn/index.htm)：DMN 用模型和 notation 表达可重复业务决策，并将决策需求、决策逻辑与输入数据显式关联。本文件借鉴“先明确决策与输入，再选择表示法”的思路，但第 23 节不引入 DMN runtime。
2. [OMG DMN 1.5 Specification](https://www.omg.org/spec/DMN/1.5/PDF)：规范说明 decision table 的输入、输出、规则与 hit policy 等形式化语义。它证明复杂决策表示需要明确语义，不证明当前场景应立即使用决策表。
3. [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)：用于校准“默认拒绝、每次请求验证权限、服务端强制”的后续访问控制边界；这些能力安排在第 31～35 节，本节没有实现授权。
4. [OWASP Input Validation Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html)：用于校准语法验证与业务语义验证的区别；客户端校验不能替代服务端基于权威事实的业务判断。
5. [OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)：用于校准日志注入、敏感数据最小化和安全事件记录边界；本节只登记要求。
6. [RFC 9457: Problem Details for HTTP APIs](https://www.rfc-editor.org/rfc/rfc9457.html)：用于提醒未来 HTTP 错误表示应使用稳定机器可读类别而不是解析自然语言；本节不改变现有 API，也不承诺采用某个具体 envelope。

## 17. 本基线不是什么

这不是规则引擎技术选型报告，不是数据库 schema，不是 HTTP API contract，不是概率产品策略，也不是安全验收结果。它的价值在于把未来实现必须保留的业务边界提前说清楚，并且坦诚记录哪些问题尚无足够证据。

下一步第 24 节只做首次 Redis 读取投影缓存。用户资格这一真实新规则到第 25 节才进入代码；如果届时需求与本基线冲突，应新增可追溯决策，而不是悄悄让实现改变术语含义。
