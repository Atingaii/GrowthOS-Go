# ADR-0019：Lottery 规则所有权与评估边界

- **状态：** 已接受
- **日期：** 2026-08-30
- **负责人：** GrowthOS 维护者
- **适用范围：** 第 23 节“需求升级抽奖策略需要规则”
- **需求基线：** [Lottery 业务规则需求基线 v1](../product/lottery-rule-requirements-v1.md)
- **替代关系：** 不替代 ADR-0013、ADR-0017 或 ADR-0018；为它们之后的规则演进定义责任与停止线

## 背景

第 17～22 节已经把最小 Lottery 纵向切片推进到真实 React 消费者：

- `Strategy` / `Award` 聚合拥有候选与正整数相对权重；
- MySQL Repository 可以原子创建并一致读取合法聚合；
- `WeightedSelector` 可以在固定 Strategy 快照内完成无偏加权选择；
- development/test 专用 ephemeral API 只读加载 Strategy 并返回一次不持久化的 `reward` 或 `no_reward` 候选；
- React 页面真实调用该 API，但不拥有随机决定权。

这个实现故意没有 Activity、用户资格、额度、风险、Strategy 路由、库存、Draw/Result、幂等、权益发放或授权。现在出现的新用户抽奖需求同时提出了多类判断：

1. Activity 已发布且处于有效时间窗；
2. 用户满足新用户定义、仍有次数且未被风险策略拒绝；
3. 不同会员等级可能路由到不同 Strategy；
4. 不可分配奖励不能被当作正常可发放候选；
5. 合法选择仍允许命中显式 `no_reward`。

如果把这些判断全部塞进当前 Strategy、Selector、HTTP handler 或一个通用 Rule 接口，短期代码可能更少，长期却会混淆事实所有权、失败语义和上下文语言。反过来，如果只因为课程标题出现“规则”就立即引入规则树、JSON DSL 或第三方引擎，也会在没有真实规则形状、运营变更频率和兼容要求时提前锁死技术。

本 ADR 决定第 23 节现在应该确定什么、明确不实现什么，以及后续章节在什么证据出现时逐步升级。

## 决策驱动

1. Activity、Participation、Lottery、Benefit 与 Governance 的事实生命周期不同，不能由一个聚合或万能接口吞并。
2. 业务资格、访问授权、奖励选择与权益发放是不同决定，失败和重试语义必须分开。
3. 现有 `WeightedSelector` 已有严格、可测试的终端选择契约，不应因上游需求变成编排器。
4. 第 23 节没有真实用户、Activity、规则持久化或正式 Draw，不能用伪实体和伪版本制造完成感。
5. 规则执行必须基于权威、可追溯且满足时效要求的事实，不信任客户端自报 verdict。
6. 同一规则版本、事实快照和评估时刻应得到确定的前置决定；只有终端随机选择消费随机票据。
7. 业务拒绝、`no_reward`、资源不可用、技术失败与结果未知不能相互 fallback。
8. 决策解释需要稳定身份和低基数原因，但不能泄露风控阈值、PII、凭证或随机材料。
9. 规则表示复杂度应由真实分支、组合、持久化和运营配置需求驱动。
10. 第 24 节 Redis 缓存不能越过权威事实和一次性决定边界。
11. 第 31～35 节会建立公共访问控制，业务规则不得提前复制角色判断。
12. 每一后续章节必须保留单一主要学习目标，并能从上一节已验收 tip 线性演进。

## 非目标

本 ADR 不决定或实现：

- `Rule`、`RuleEngine`、`Specification`、`Chain`、`Node` 等 Go 类型；
- Activity、User、Membership、Quota、Risk、Inventory、Draw 或 Result 的生产模型；
- 规则表、规则树表、表达式 schema 或 Migration；
- JSON DSL、脚本、插件、DMN runtime 或第三方规则平台；
- HTTP route、DTO、状态码、错误 envelope 或 React 页面；
- Redis key、TTL、序列化 payload 或分布式锁；
- 会话、RBAC、ABAC、租户/对象级数据范围或前端权限组件；
- 候选过滤后的概率重归一化或库存预占协议；
- 正式抽奖的幂等、唯一最终结果、发放事务或补偿；
- 生产性能、公平审计、风控有效性或合规结论。

## 评估过的方案

### 方案一：继续在 handler/use case 中追加 `if/else`

| 优点 | 代价 / 风险 |
| --- | --- |
| 无需新增概念，短期最快 | transport 同时解释用户、活动、风险、Strategy 与库存事实 |
| 单一场景阅读直观 | 相同规则会在 HTTP、任务、MCP 和测试入口复制 |
| 暂时无需规则框架 | 顺序、短路、reason、版本和 trace 成为隐式控制流 |

**结论：不采用。** handler 负责传输映射，不应成为跨上下文业务事实所有者。第 23 节也不以“暂时写死、以后再重构”制造一段明知归属错误的生产代码。

### 方案二：把所有条件加入 `Strategy` 或 `WeightedSelector`

| 优点 | 代价 / 风险 |
| --- | --- |
| 抽奖相关数据看似集中 | Strategy 变成 Activity、Participation、Benefit 和 IAM 的上帝对象 |
| Selector 调用点保持一个 | 纯终端选择器被迫访问外部事实、时钟、库存和权限 |
| 可能减少编排层代码 | 聚合无法独立重建，缓存与随机算法被业务副作用污染 |

**结论：拒绝。** `Strategy` 继续只拥有 Lottery 决策配置；`WeightedSelector` 继续只在固定候选集合内选择。Activity 生命周期、用户额度和库存由各自上下文确认。

### 方案三：立即定义所有上下文共享的通用 `Rule` / `Specification`

概念形状可能类似“输入任意 Context，返回 bool/error”。

| 优点 | 代价 / 风险 |
| --- | --- |
| 看似高度复用，便于统一编排 | `map[string]any` 或巨大 Context 丢失领域类型和所有权 |
| 容易增加规则实现 | Authorization、Eligibility、Inventory 被压成相同 bool |
| 可以统一打日志 | reason、失败、重试与副作用语义只能取最弱公分母 |

**结论：不采用。** 不同上下文可以共享无业务语义的观测、配置校验或执行基础设施，但不能为了接口统一而丢失自己的领域语言。任何后续抽象必须由至少两个真实用例证明稳定共同点。

### 方案四：第 23 节直接实现线性责任链

| 优点 | 代价 / 风险 |
| --- | --- |
| 顺序和短路比 handler `if` 更显式 | 当前没有第一条可执行用户资格及权威输入 |
| 与第 26 节计划方向一致 | 会提前交付第 25～26 节，破坏逐节演进证据 |
| 单元测试容易注入节点 | 很可能先发明一个过宽接口，再被第 27 节分支需求推翻 |

**结论：暂不采用。** 第 25 节先落一条真实资格规则；第 26 节有至少两个顺序前置判断后再引入最小链，并只解决当时的线性问题。

### 方案五：立即持久化规则树或采用 DMN/规则平台

| 优点 | 代价 / 风险 |
| --- | --- |
| 可以支持运营配置、分支与可视化 | 当前没有节点语义、hit policy、发布流程或兼容需求 |
| 标准/平台可能提供成熟工具 | 引入 schema、runtime、安全面和运维依赖，教学因果倒置 |
| 看起来一步到位 | 容易把表达能力误当成业务正确性，非法图与事实所有权仍未解决 |

**结论：暂不采用。** OMG DMN 证明复杂决策可以被形式化建模，不证明本项目此刻需要 DMN。第 27 节先用真实分支暴露责任链局限，第 28～29 节再选择最小规则树持久化与执行语义。

### 方案六：先建立规则需求、事实所有权和评估边界，再按证据演进

| 优点 | 成本 / 风险 |
| --- | --- |
| 保留现有实现的真实边界 | 本节没有新增可运行功能，必须用清晰验收证明价值 |
| 后续每节都有明确触发问题 | 某些开放问题需要延后决策 |
| 避免通用接口和 schema 过早锁定 | 文档必须持续与后续实现同步，不能成为静态愿景 |
| 规则、授权和库存语义可分别演进 | 编排层以后需要显式处理多种决定 |

**结论：采用。** 第 23 节交付产品需求基线和本 ADR，不新增生产代码。

## 决策

### 1. 以业务阶段和事实所有权拆分规则

规则不属于一个全局 `rules` 上下文。它属于确认对应业务结论的上下文：

| 阶段 | 核心问题 | 权威事实 | 决定所有者 | 概念输出 |
| --- | --- | --- | --- | --- |
| 访问前置 | 调用主体能否执行动作 | 身份、角色、权限、资源、动作、范围 | Governance/统一访问控制 | 允许或授权拒绝 |
| Activity 门控 | 活动当前能否被参与 | 发布版本、状态、时间窗、渠道 | Marketing | 继续或业务拒绝 |
| Participation 资格 | 该主体是否可参与 | 用户摘要、新客定义、额度、参与/风险事实 | Participation | 继续或资格拒绝 |
| Lottery 路由 | 进入哪个 Strategy/分支 | Lottery 决策配置与可信输入摘要 | Lottery | route、拒绝或失败 |
| 候选可分配 | 奖励是否可承诺 | 库存、模板、预占与有效期 | Benefit（内部库存子能力） | 可用、不可用或未知 |
| 终端选择 | 固定候选内选中哪个 Award | Strategy/Award/Weight 与随机票据 | Lottery | `reward` / `no_reward` 或技术失败 |
| 结果与交付 | 怎样落定并交付 | Draw/Result、库存、Reward、流水 | Lottery + Benefit，各自确认事实 | 最终结果、处理中、成功、失败/补偿 |

“编排者调用了所有步骤”不等于编排者拥有所有事实。即使当前采用 Modular Monolith，各模块仍必须通过明确业务契约协作，不直接读写其他上下文的表来宣布结论。

### 2. 保持 `WeightedSelector` 为纯终端能力

1. selector 继续只接收合法 Strategy 和领域拥有的有界随机 source；
2. 它不接收 User、Activity、MemberTier、Quota、Risk、Inventory、Principal 或 Permission；
3. 它不读取 Repository、Redis、时钟或网络依赖；
4. 它不创建 Draw/Result、不扣库存、不发 Benefit；
5. `reward` 与 `no_reward` 都是选择成功；source、contract 或不变量错误仍是技术失败；
6. 前置规则拒绝时不得调用 selector，也不得消费随机票据；
7. 更改候选集合或权重的行为必须在调用 selector 前由明确产品策略完成，不能在 selector 内偷偷过滤。

这样可以继续独立证明概率映射正确，同时让资格、库存和交付根据自己的并发与失败语义演进。

### 3. 第 23 节只锁定概念结果，不创建通用返回类型

未来流程必须能够区分：

- `continue`：当前阶段已确认，可以继续；
- `reject`：事实充分且业务条件不成立；
- `route`：明确选择后续 Strategy 或分支；
- `unavailable`：业务资源暂不可用；
- `technical failure`：无法得到可信决定；
- `unknown`：可能已经产生副作用，但最终事实暂时无法确认。

这是一组跨文档语义，不要求各上下文实现同一个枚举或接口。Participation 应使用资格领域语言，Governance 应使用授权语言，Lottery 应使用路由/选择语言，Benefit 应使用受理/发放语言；编排和 transport 再显式映射。

### 4. 五种语义不得互相降级

1. **业务资格拒绝不等于 `no_reward`：** 被拒绝的请求没有完成 Lottery 选择。
2. **授权拒绝不等于业务资格拒绝：** 操作者无权访问与用户不满足活动条件是两个不同边界。
3. **资源不可用不等于 `no_reward`：** 无库存或奖励模板失效不能偷渡成概率结果。
4. **技术失败不等于确定拒绝：** 超时、坏配置、依赖故障和未知事实不能描述为用户不合格。
5. **结果未知不等于可以重试：** 有副作用后必须按业务身份查询、恢复或补偿，不能重新随机选择。

公开响应可以因防枚举和最小披露而合并文案，但内部稳定类别、审计和监控仍必须区分。具体 HTTP status/envelope 到相关 API 章节再决定。

### 5. 规则评估遵循确定性、短路和最小副作用

1. 除终端随机选择外，相同规则集版本、事实快照和评估时刻应产生相同结果；
2. 规则顺序影响 outcome、reason 或副作用时，顺序必须成为显式版本化契约；
3. 一次评估共享受控服务端评估时刻，不能让每个节点分别读取浏览器时钟或节点本地不同时刻；
4. 确定拒绝后默认短路，不继续消费随机票据、额度、库存或外部发放；
5. 需要收集多个诊断时，只允许评估无副作用条件，并以稳定优先级选取公开主 reason；
6. 下游调用失败时默认失败关闭，除非某项非关键增强规则经过独立产品/风险决策允许降级；
7. 安全关键的授权、资格、额度和风险依赖不得 fail open。

### 6. 权威事实先于规则表达

每条未来规则进入实现前必须登记：

- 业务目的与受保护承诺；
- 规则身份和所属上下文；
- 每项输入事实的权威来源；
- 来源版本/采集时间、时区和可接受新鲜度；
- 未知、缺失、过期和契约错误时的语义；
- 输出类别、短路位置和潜在副作用；
- 用户解释、运营诊断和安全审计的披露级别；
- 计划生效范围和兼容/撤销方式。

客户端提交的 `is_new_user`、`member_level`、`risk_passed`、`role`、`inventory_available` 或 `rule_result` 都是不可信声明，不能直接成为规则事实。服务端必须从权威上下文收集或验证。

### 7. 分离规则、配置和事实版本

后续建模必须概念分离：

| 版本 | 责任 |
| --- | --- |
| Rule identity | 稳定标识一条业务规则 |
| RuleSet version | 标识一次不可变发布组合及顺序/分支 |
| Rule schema version | 决定配置怎样解析和迁移 |
| Strategy version | 标识某次 Award/Weight 快照 |
| Activity version | 标识营销发布版本及其规则/Strategy 引用 |
| Fact source version | 标识外部输入的来源版本或数据水位 |
| Application version | 辅助定位执行程序，不替代业务版本 |

当前 Lottery 表没有聚合版本，根/子行 `updated_at` 也不是 Strategy version；第 23 节不得伪造一个数字宣称已经版本化。版本字段、发布方式和数据迁移只在对应真实用例出现后决定。

### 8. 稳定 code 与文案、trace 分离

1. 规则身份与 ReasonCode 长期稳定，不从自然语言文案反向解析；
2. 用户文案可本地化、可按安全策略模糊，不承担机器 contract；
3. 运营诊断可以包含资源身份、配置版本和可操作建议，但受权限控制；
4. 安全审计记录主体、动作、资源、规则/策略版本、决定与关联 ID，并限制写权限；
5. 内部有序 trace 记录规则身份、版本、结果类别和必要耗时，不记录完整 PII、凭证、会话、风险原始特征、券码、随机字节或 selector ticket；
6. 底层 SQL、网络、熵源或错误链不进入公开 reason；
7. 普通日志保持低基数，详细证据进入受控 trace/审计而不是把任意输入变成 label。

### 9. 第 24 节 Redis 只能缓存 Strategy 读取投影

第 24 节可以缓存由 MySQL Strategy/Award 配置完整重建的、可丢弃的读取投影，但必须：

- 具备缓存 payload 格式版本；
- key 至少能唯一定位 Strategy，并避免环境/命名空间冲突；
- miss、坏 payload、Redis 不可用时回到权威 Repository 或明确失败；
- 通过领域构造器恢复，不能绕过不变量；
- 记录 TTL/失效与观测边界；
- 不因缓存命中宣称拥有 Strategy 业务版本。

第 24 节不得缓存用户资格、风控 verdict、授权决定、一次规则评估结果、库存承诺、随机选择结果或最终 Draw。这些数据的时效、并发、隐私和幂等语义尚未建立。

### 10. 访问控制与业务规则保持正交

第 31～35 节建立统一的 Identity、Principal、Role、Permission、Resource、Action、Scope 和 Policy Decision 语言，并由服务端强制。Lottery/Participation 规则不得：

- 检查硬编码 `isAdmin` 或页面角色；
- 因导航被隐藏就假定 API 已受保护；
- 把权限不足映射成 `not_eligible`；
- 从 JWT/会话自定义字段直接推导新用户、额度或风控资格；
- 为运营端、MCP 和 Agent 分别复制权限逻辑。

前端能力投影只改善导航、路由和操作体验；直接 API 请求仍由服务端授权。这项决策在第 23 节只登记依赖，不提前实现访问控制。

### 11. 规则技术按证据分阶段升级

| 章节 | 触发证据 | 允许的最小升级 |
| --- | --- | --- |
| 23 | 组合场景暴露多种规则与所有权 | 需求基线与 ADR；无生产规则代码 |
| 25 | 第一条真实用户资格及权威事实可执行 | 使用 Participation 领域语言实现单一规则 |
| 26 | 至少两个有确定顺序和短路语义的前置判断 | 最小线性责任链，只解决当时流程 |
| 27 | 会员分层/多分支/共享子路径使链开始扭曲 | 记录链的可测失败模式与新需求 |
| 28 | 规则需要发布、持久化、兼容和图校验 | 最小规则树 schema 与前向 Migration |
| 29 | 已有合法持久化规则图 | 确定执行、短路、解释、资源限制与错误语义 |
| 30 | Activity 生命周期与 Strategy 引用成为真实对象 | 明确发布版本与跨上下文引用 |

不得为了让第 27 节“看起来有重构故事”而故意在第 26 节写坏接口；每一阶段只解决当时已知问题，并记录何种证据触发下一次升级。

### 12. 未来规则树必须先验证再执行

当第 28～29 节真正引入持久化决策图时，至少验证：

- 唯一合法 root；
- edge 指向存在节点；
- 禁止循环或定义明确的有界循环语义；
- 最大深度、最大节点数和评估预算；
- 不可达节点、孤儿节点和无终点路径；
- 每个分支的缺省/未匹配行为；
- 输入/output 类型和未知 operator；
- 同一输入是否得到确定路径；
- schema 版本与执行器兼容；
- 发布后不可变或有明确替换版本；
- 无权限操作者不能发布/修改；
- trace 不泄露敏感输入。

这是一条未来验收边界，不是第 23 节的 schema 设计。

## 信任边界

### 客户端边界

浏览器、移动端、MCP 调用者和 Agent 都是不可信输入来源。前端可以提示资格、裁剪导航或展示服务端决定，但不能证明用户属性、权限、库存或规则结果。所有关键判断必须在服务端基于可信事实重新执行或验证。

### 跨上下文边界

一个上下文只能宣布自己拥有的事实。Marketing 确认 Activity 生命周期，Participation 确认参与资格和额度，Lottery 确认路由与选择结果，Benefit 确认库存/权益状态，Governance 确认访问决策。消费者可以保存标明来源与失效语义的快照/投影，不能把副本改成权威写模型。

### 外部事实边界

用户、会员、支付、风险或券平台数据需要防腐映射。字段同名不代表语义相同；超时、缺失和过期不能自动映射为 `false` 或允许。只收集决定所需最小信息，避免为了“通用规则 Context”复制完整用户画像。

### 缓存边界

Redis 是可丢弃 adapter，不是规则事实所有者。命中缓存只说明读到一个投影，不说明它足以支持额度、库存、授权或一次性承诺。坏缓存必须失败关闭或回源，不能通过宽松 JSON 解码继续。

### 时间边界

Activity 时间窗、事实新鲜度和规则生效时间使用受控服务端评估时刻与显式时区。客户端时间、数据库连接节点时区或多个规则分别读取当前时间都可能造成边界漂移。

### 随机与结果边界

随机票据只在所有前置条件成立、候选与版本确定后消费。随机材料不进入日志或公开 trace。正式 Draw/Result 出现前，ephemeral selection 仍没有可查询的最终结果和透明重试保障。

### 日志、解释与审计边界

公开错误、运营诊断和安全审计的受众不同。公开 reason 遵循最小披露；运营诊断受权限保护；安全审计限制读写且记录授权与业务拒绝的不同类别。控制字符、任意输入和完整错误链不能直接写日志。

## 影响

### 正面影响

- 现有 Strategy/Award/Selector 契约保持小而可证明；
- Activity、资格、路由、库存、授权和发放各自有事实所有者；
- `no_reward` 不再被错误、无库存或拒绝滥用；
- 第 24～30 节得到清晰的逐步演进触发点；
- 第 31～35 节公共访问控制可以保护真实资源，而不是围绕空页面造角色；
- 版本、reason 和 trace 的长期兼容问题在 schema 出现前被发现；
- 第 43～52 节处理并发库存、结果快照和补偿时，不必拆除一个跨上下文万能引擎；
- 文档能诚实说明“发现了哪些规则问题”和“目前尚未实现什么”。

### 成本

- 第 23 节不会带来用户可见新功能；学习价值来自边界分析和可审计停止线；
- 后续编排层必须显式处理多种领域决定，不能依赖单一 bool/error；
- 跨上下文需要设计事实摘要、版本与失败映射；
- 同一业务流程的 trace 需要关联多个所有者；
- 延后技术选型意味着第 25～29 节仍要逐步新增和调整实现。

### 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| 文档过度设计、后续没有落实 | 每条要求绑定未来章节；每节验收时回查、修订或明确拒绝 |
| 所有权边界导致调用链变长 | 先保持模块化单体与进程内契约；只有运行证据支持时物理拆分 |
| 不做通用接口造成重复 | 允许小范围重复，等两个真实稳定用例后再抽无业务语义公共机制 |
| Reason 过粗影响排障 | 用户 reason、运营诊断和内部审计分层，不用公开文案承担全部诊断 |
| 失败关闭影响可用性 | 为关键与非关键规则分级；只有经过明确产品/风险评审才允许降级 |
| 延后库存概率策略阻塞完整流程 | 第 43～45 节在原子库存语义出现时做产品决策并版本化 |

## 迁移与撤销

本 ADR 不修改生产代码、数据库或外部 API，因此当前不存在数据迁移和运行时回滚。撤销只涉及文档，但不能无声删除已经识别的风险与开放问题。

后续实现应按以下路径演进：

1. 第 24 节只增加 Strategy 读取投影缓存，不改变规则所有权；
2. 第 25 节在 Participation 语言中落第一条真实资格；
3. 第 26 节根据真实顺序/短路需求引入最小链；
4. 第 27 节收集链不能表达的分支证据；
5. 第 28～29 节再决定规则树 schema 与执行契约；
6. 第 30 节让 Activity 以版本化方式引用 Lottery 配置；
7. 第 31～35 节建立服务端权威公共访问控制；
8. 第 39～52 节逐步建立额度、订单、库存、正式结果、可靠消息和补偿。

如果未来证明规则完全固定、没有运营配置或分支复杂度，则可以长期保留显式领域代码和最小链，无需为了路线图强行上规则树。若未来采用 DMN 或外部平台，也必须通过防腐层保留本 ADR 的所有权、失败、版本、最小披露和 selector 纯度边界。

## 重新评估触发条件

出现以下任一证据时新增 ADR，而不是静默扩大当前决定：

- 多个上下文确有稳定、同语义的规则执行抽象；
- 运营需要无代码编辑、审批、灰度、回滚或模拟规则；
- 决策分支、共享子路径或 hit policy 超过最小规则树表达能力；
- 规则吞吐、延迟或外部事实获取成为可测瓶颈；
- 规则需要跨语言/跨服务执行或与外部标准互操作；
- 合规要求可解释、可回放、公平审计或模型验证；
- 缓存事实新鲜度导致错误资格、路由或库存事故；
- 权限、资格或风控被错误合并，产生越权或错误拒绝；
- 结果未知、重复参与、重复抽取或重复发放事故出现；
- Activity/Strategy/RuleSet 的版本关系需要兼容历史请求；
- 候选过滤策略改变实际概率，需要明确产品与风险审批。

## 验收证据

第 23 节通过以下证据验收本决策，而不是通过不存在的规则代码：

1. [Lottery 业务规则需求基线 v1](../product/lottery-rule-requirements-v1.md)将组合场景的每类规则映射到事实所有者、决定所有者、失败语义和未来章节；
2. 课程、API、QA、设计手记和面试问答保持同一“纯需求/架构边界”口径；
3. 相对第 22 节验收 tip，`cmd/`、`internal/`、`web/`、`migrations/`、`deploy/`、`configs/` 没有生产实现变化；
4. Migration 仍只有 `000001` / `000002`；
5. Lottery API、Repository、Strategy/Award 与 WeightedSelector 契约不变；
6. `make doc-check` 与 `make verify` 继续通过。

这些证据只能证明需求与边界被明确、现有行为未漂移，不能证明资格规则、规则引擎、缓存、授权、库存、正式 Draw、发放或业务 SLO 已实现。

## 外部参考与采用边界

1. [OMG Decision Model and Notation](https://www.omg.org/dmn/index.htm)：用于校准“决策需求、输入数据和决策逻辑应显式建模”的方向；GrowthOS 第 23 节不采用 DMN runtime。
2. [OMG DMN 1.5 Specification](https://www.omg.org/spec/DMN/1.5/PDF)：decision table、输入输出和 hit policy 等形式语义说明，帮助识别“规则表不是几行 if 的数据库化”；当前没有证据选择这套表示。
3. [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)：用于校准默认拒绝、每次请求服务端授权与前端非安全边界；具体实现延后到第 31～35 节。
4. [OWASP Input Validation Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html)：用于区分语法校验和基于业务上下文的语义校验；客户端声明不能成为权威资格事实。
5. [OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)：用于校准敏感信息最小化、日志注入和安全事件记录；第 23 节只登记未来约束。
6. [RFC 9457: Problem Details for HTTP APIs](https://www.rfc-editor.org/rfc/rfc9457.html)：用于校准未来 HTTP 问题类别应稳定、机器可读且不依赖文案；本 ADR 不改变现有 fault envelope。

## 最终决策摘要

第 23 节不实现规则引擎。GrowthOS 先把“谁拥有事实、谁有权决定、何时评估、失败意味着什么、怎样版本化与解释”固定下来；后续只在真实复杂度出现时，从单一资格规则演进到线性链、规则树和决策引擎。

Lottery `WeightedSelector` 保持纯终端加权选择；Activity 门控归 Marketing，用户资格/额度归 Participation，Strategy 路由与选择归 Lottery，库存/交付归 Benefit，访问控制归 Governance。任何业务拒绝、授权拒绝、`no_reward`、不可用、技术失败和未知结果都不得相互冒充。
