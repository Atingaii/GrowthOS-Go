# ADR-0007：第一版采用模块化单体

- **状态：** 已接受
- **日期：** 2026-08-29
- **负责人：** GrowthOS 维护者

## 背景

GrowthOS 最终会覆盖营销、抽奖、权益、Feed、行为、实验、MCP 与 Agent，但当前尚未出现独立发布、故障隔离、团队自治或差异化扩缩容的实测证据。如果按远期领域边界直接拆成多个服务，首个可运行版本就必须承担 RPC、服务发现、分布式事务、链路治理和多套部署单元的成本。

系统仍需要防止单体退化为无边界代码：限界上下文已经划分事实所有权，后续数据库、应用用例和基础设施适配器必须保持明确依赖方向。

## 评估过的方案

| 方案 | 优点 | 代价与风险 | 结论 |
| --- | --- | --- | --- |
| 按路线图中的领域立即拆微服务 | 独立部署边界直观 | 当前没有拆分证据；引入分布式一致性、RPC 和运维复杂度 | 不采用 |
| 无模块约束的单体 | 启动成本最低 | 领域事实、事务和基础设施代码容易互相渗透 | 不采用 |
| 单进程模块化单体 | 保留本地事务和简单部署，同时用代码边界承载领域职责 | 需要持续执行依赖规则和模块测试 | 采用 |

## 决策

第一版产品运行时使用一个 Go API 进程和一个 MySQL 业务库，按 `internal/<domain>` 组织领域、应用与端口；`cmd/*` 只负责装配，技术实现集中在基础设施适配器中。跨模块协作优先通过应用端口、稳定领域契约或事务后事件完成，模块不得直接调用其他模块的数据库实现。

本决策约束当前部署形态，不把所有领域永久绑定在同一进程。第 73 节开始只有在以下至少一类证据成立时才评估拆分：

- 负载曲线或资源类型显著不同，单体扩容造成明确浪费；
- 发布频率、故障域或可用性目标需要独立部署；
- 数据合规或安全边界要求物理隔离；
- 团队所有权已经稳定，跨服务契约治理成本低于共享进程成本。

拆分必须先稳定模块端口和契约，再迁移调用方式；不能用共享表或跨库直连伪装服务边界。

## 影响

- 第 11～72 节优先在单进程中演进业务能力，可以使用本地事务保护核心不变量。
- HTTP、缓存和消息属于适配器，不能成为领域模型的直接依赖。
- 模块边界通过包可见性、依赖测试、契约和文档持续核查。
- 第 73～80 节将以压测、故障和部署证据选择首批拆分对象，并保留单体到服务的迁移路径。
- 开发环境在第 16 节只需一个产品 API 容器；中间件仍按真实需求逐步加入。
