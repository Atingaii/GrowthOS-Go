# ADR-0013：Lottery Strategy 聚合与候选结果领域契约

- **状态：** 已接受
- **日期：** 2026-08-29
- **负责人：** GrowthOS 维护者

## 背景

第 16 节结束时，GrowthOS 已经具备可复现的 Go、React、MySQL、Migration 与 Compose 工程底座，但还没有第一个业务领域模型。第 17 节需要回答“最简单随机抽奖至少需要哪些对象”，并给第 18 节建表、第 19 节 Repository 和第 20 节抽奖算法提供稳定的业务语言。

这一时间切片有几个容易混淆的事实：

1. `Strategy` 是 Lottery 内可复用的抽奖决策配置，不是带时间窗和生命周期的 Marketing Activity；
2. 当前需求只是描述一组可被选择的结果，还没有“某次用户抽奖”的请求、执行和结果记录；
3. “未中奖”是一次合法选择，而不是系统错误、空指针或没有结果；
4. 概率配置需要保持精确和可组合，但此时没有证据要求固定为百分数、万分比或小数；
5. 第 18 节才决定 SQL 表和列，第 19 节才决定 Repository，第 20 节才决定随机源与区间映射；
6. 领域对象以后会从 HTTP、数据库、缓存或消息中重建，但不应反向依赖这些适配器；
7. [INV-03](../product/non-functional-requirements-v1.md) 要求一次抽奖只有一个最终结果，但本节尚未拥有 Draw、请求标识或结果持久化，因此不能声称已经满足它。

如果现在直接从 API JSON、表结构或随机算法倒推对象，模型会把某个适配器或某个执行方案误当成业务本身。相反，本 ADR 先锁定所有后续实现都必须保留的最小领域契约。

## 决策驱动

方案必须同时满足：

- 能表达一个可复用策略及其至少一个候选结果；
- 构造完成后对象始终满足本节已知不变量；
- 能精确表达任意正整数比例，而不引入浮点比较和固定分母；
- 明确区分“有待交付奖励”和“合法未中奖”；
- 不把 `nil`、缺失行或异常当成未中奖；
- 领域模型不导入 SQL、HTTP、JSON、Redis 或框架类型；
- 输入顺序不成为隐藏业务状态或未来抽奖偏差来源；
- 未来适配器能识别非法存量数据，而不是绕过构造规则；
- 当前实现足够小，不提前承诺活动、库存、资格、幂等、结果持久化或发奖状态机。

## 评估过的方案

### 1. 只有一个 `Prize` 结构体，由 handler 临时拼装列表

| 优点 | 代价 / 风险 |
| --- | --- |
| 文件少、可以快速写出演示 | 没有对象拥有“至少一个候选、ID 唯一、总权重安全”等集合不变量 |
| 看似适合最小 Demo | handler、Repository 和算法会分别重复校验，错误语义漂移 |
| 输入顺序自然传给算法 | 调用方顺序会变成没有命名的概率或持久化契约 |

**结论：不采用。** 候选集合的不变量需要一个明确所有者；`Strategy` 作为聚合根负责建立完整、可安全使用的候选集合。

### 2. `Activity` 直接拥有奖品与概率

| 优点 | 代价 / 风险 |
| --- | --- |
| 页面概念直观，一场活动一份奖品列表 | Activity 的时间窗、发布、预算与生命周期会污染纯抽奖决策 |
| 可能减少一次关联 | 同一策略无法安全复用，Marketing 与 Lottery 事实所有权混淆 |
| 未来从活动直接抽奖 | 第 30 节“为什么 Strategy 不等于 Activity”的问题会被提前写死成错误答案 |

**结论：不采用。** `StrategyID` 明确标识 Lottery 决策配置；Marketing 未来只能引用它，不能接管其候选和概率事实。

### 3. 权重使用 `float32` / `float64` 百分比

| 优点 | 代价 / 风险 |
| --- | --- |
| 接近运营口头表达的 `10%` | 二进制浮点不能精确表示许多十进制小数 |
| 可以直接要求总和为 `1.0` 或 `100` | 求和与相等比较需要容差；序列化、数据库和语言之间可能漂移 |
| 算法示例常见 | 固定百分比精度会在业务提出更细粒度概率时成为 Migration 契约 |

**结论：不采用。** 概率展示属于适配层；领域只保存正整数相对权重。

### 4. 固定万分比，要求权重总和等于 `10_000`

| 优点 | 代价 / 风险 |
| --- | --- |
| 精确、易于展示和校验 | 提前锁定四位精度；调整一个奖项经常要求同步修改其他奖项 |
| 随机区间固定 | `1:3` 与 `2500:7500` 被迫使用特定表示，增加无业务价值的归一化 |
| SQL 字段较容易设计 | 存储便利反向决定领域语言 |

**结论：不采用。** `1:3` 与 `100:300` 在当前领域中表达同一分布；是否给运营端提供万分比输入，等真实编辑 API 出现后再决定。

### 5. 使用任意正整数相对权重

| 优点 | 成本 / 注意点 |
| --- | --- |
| 无浮点误差，不要求固定分母 | API/UI 以后需要计算展示比例并解释四舍五入 |
| 调整、合并候选自然 | 构造时必须检查零值和总和溢出 |
| 可以由多种外部表示映射 | 第 20 节的随机算法必须无偏地覆盖总权重区间 |

**结论：采用。** `Weight` 使用正 `uint64` 相对权重，`Strategy` 保存经过溢出检查的 `TotalWeight`。

### 6. 未中奖使用 `nil`、零值 Award 或 error

| 方案 | 问题 | 结论 |
| --- | --- | --- |
| `nil` / 找不到 Award | 无法区分合法未中奖、配置缺失、Repository 漏行和算法 bug | 不采用 |
| 返回 `error` | 把正常业务分支计入系统失败，重试可能改变结果 | 不采用 |
| 使用 `AwardID == 0` | 与“缺少持久身份”的非法状态冲突 | 不采用 |
| 显式 `no_reward` Award | 与中奖候选使用同一权重和身份机制，结果语义可审计 | 采用 |

### 7. Award 同时保存具体积分、券模板和库存

| 优点 | 代价 / 风险 |
| --- | --- |
| 看起来可以立即发奖 | Lottery 被迫理解每种 Benefit 生命周期和库存模型 |
| 少一次后续映射 | 第 49 节统一 Reward 模型前就承诺不稳定字段 |
| Demo 更完整 | 选择结果与实际交付事实混成一个对象，失败补偿无处表达 |

**结论：不采用。** 本节 `AwardOutcomeReward` 只表示“选择后存在一份待后续 Benefit 流程处理的奖励描述”，不表示已经发放、到账或扣减库存；具体 Reward 引用由后续真实需求驱动。

### 8. 暴露字段并允许任意修改

| 优点 | 代价 / 风险 |
| --- | --- |
| JSON/SQL scan 简单 | 调用方可构造零 ID、零权重、非法 outcome 和非规范名称 |
| 测试夹具短 | 聚合构造后的 `TotalWeight` 可能与被修改的 Award 不一致 |
| 少写 getter | 领域约束退化成注释 |

**结论：不采用。** 字段保持未导出，只通过构造器建立状态并通过只读方法观察；适配器负责映射，不得要求领域模型增加 transport tag。

### 9. 保留调用方候选顺序、按权重排序或按 AwardID 排序

| 方案 | 优点 | 风险 | 结论 |
| --- | --- | --- | --- |
| 保留输入顺序 | 最少工作；可以做 UI 顺序 | Repository 无 `ORDER BY` 时结果不稳定；顺序可能暗中影响算法 | 不采用为领域规范顺序 |
| 按权重排序 | 可能方便某些算法 | 权重调整会改变顺序；相同权重仍不确定；把算法策略倒灌领域 | 不采用 |
| 按 `AwardID` 升序 | 稳定、与权重无关、可重建 | 不是运营展示顺序；查找目前仍为线性 | 采用 |

规范顺序只用于确定性迭代、测试、序列化和未来映射；它不是中奖优先级，也不授权前端把它当成展示排序。若运营需要可编辑展示顺序，应新增独立业务字段，而不是复用输入或查询偶然顺序。

### 10. Award 名称必须唯一或只要求 ID 唯一

| 方案 | 问题 | 结论 |
| --- | --- | --- |
| 名称唯一 | 同名“神秘盒子”可能对应不同奖励；文案调整会破坏身份与引用 | 不采用 |
| ID 唯一、名称可重复 | 身份稳定，文案承担显示而非主键职责 | 采用 |

## 决策

### 聚合与身份

1. `internal/lottery/domain.Strategy` 是本节 Lottery 聚合根；它拥有一个 `StrategyID`、一个规范名称、一组 `Award` 和经过检查的总权重。
2. `StrategyID` 与 `AwardID` 使用正 `uint64`；零值永远表示缺少合法身份，不能作为“尚未保存”或“未中奖”的业务值。
3. `AwardID` 只要求在所属 Strategy 内唯一。本 ADR 不承诺跨 Strategy 全局唯一，也不提前决定第 18 节的主键、外键或 ID 生成方式。
4. Strategy 至少包含一个合法 Award。单 Award 策略是合法的确定性配置；领域不因为“随机抽奖”这个产品名称强制至少两个候选。
5. 同一 Strategy 中 Award 名称可以重复，身份比较和查找只能依赖 AwardID。

### 权重

6. `Weight` 是正 `uint64` 相对权重，不是百分数、概率小数或固定万分比。比例相同的权重集合具有相同概率语义。
7. 每个 Award 的 Weight 必须大于零。暂停、禁用或库存耗尽不是用零权重偷渡的状态；这些规则出现时应显式建模。
8. Strategy 构造时对所有 Weight 求和，并在加法前检查 `uint64` 溢出；溢出配置必须整体拒绝。
9. `TotalWeight` 是聚合根据成员状态计算并保存的派生值，调用方不能单独传入或修改。
10. 本节允许总权重达到 `math.MaxUint64`。第 18 节存储和第 20 节随机算法必须明确证明支持该范围；如果所选技术只能安全支持更窄范围，应通过新的领域决策缩小契约，不能静默截断或取模。

### 结果候选语义

11. `AwardOutcome` 是封闭词汇，当前只有 `reward` 与 `no_reward`。
12. `reward` 表示后续存在需要 Benefit 流程处理的奖励描述，不表示已发放、已到账、库存已扣或用户已有权益。
13. `no_reward` 表示一次选择可以合法完成而不产生奖励。它必须像其他候选一样拥有正 AwardID、名称和权重。
14. Strategy 可以全部由 `no_reward` 候选组成；领域不猜测运营意图或可接受的中奖率。后台风险提示、审批或发布限制应在相应需求出现时建模。
15. Outcome 不是具体 Benefit 类型。积分、优惠券、实物等种类及引用字段不在本节模型中。

### 名称契约

16. Strategy 与 Award 名称在构造入口执行相同的规范化和校验：必须是合法 UTF-8、先去除首尾 Unicode 空白、结果非空、不含 Unicode control character，最多 128 个 Unicode code point。
17. 构造器返回的是去除首尾空白后的规范名称；对象内部校验拒绝任何非规范状态。
18. 128 的单位是 Go `utf8.RuneCountInString` 所计数的 code point，不是 UTF-8 byte、字素簇或屏幕宽度。组合字符与单一预组字符不会自动执行 Unicode normalization。
19. 第 18 节数据库和未来 API 必须保留这一契约：不能按 byte 截断，不能依赖数据库静默去空格，也不能因为 collation 或 normalization 把领域允许的两个不同名称误当成同一身份。
20. 名称是可读标签，不是安全 HTML、日志模板或唯一键。所有输出适配器仍需按目标上下文转义；领域校验不能替代 XSS、日志和显示层防护。

### 所有权与规范顺序

21. Strategy 构造器防御性复制调用方的 Award slice；`Awards()` 每次返回新的 slice。调用方不能通过 slice alias 修改聚合集合。
22. Award 字段不导出且没有 setter；它作为值返回。任何状态变化都必须通过未来明确的领域操作或创建新值完成。
23. Strategy 在构造时按 AwardID 升序保存候选，`Awards()` 永远返回这一规范顺序。
24. 规范顺序不是概率优先级、运营展示顺序或 SQL 默认顺序。未来 Repository 必须显式重建聚合，算法不能依赖调用方或数据库偶然顺序。
25. `Award(id)` 按身份查找候选；当前候选规模没有证据需要额外索引，先保持简单线性查找。若真实规模或调用频率证明瓶颈，再在不改变外部语义的前提下增加内部索引。

### 适配器边界

26. `internal/lottery/domain` 不包含 `json`/`db` tag，不导入 Gin、`database/sql`、sqlx、Redis client 或 Migration 包。
27. HTTP DTO、SQL row、缓存 payload 和消息 schema 必须在各自适配层定义，并通过领域构造器重建对象。适配器不得直接制造未校验的私有状态。
28. `Err...` 哨兵错误只描述稳定的领域校验类别。HTTP status、公开错误码、数据库错误与日志 cause 由未来适配器映射。
29. 本节不定义 Repository interface。只有第 19 节出现真实加载/保存用例时，才能根据应用层需要设计端口，避免从数据库 CRUD 形状倒推领域 API。

### 当前明确不属于本决策的内容

30. 不定义数据库表、列、索引、外键、事务和 Migration；第 18 节负责。
31. 不定义 Repository、Unit of Work、SQL 查询和缓存；第 19 节及第 24 节负责。
32. 不定义 PRNG、密码学随机源、区间边界、取模拒绝采样或抽奖算法；第 20 节负责。
33. 不定义 HTTP 路由、请求/响应 DTO、认证、授权或幂等 key；第 21 节负责第一个 Lottery API。
34. 不替换 `/lottery` Mock 页面，也不把其客户端随机演示视为领域实现；第 22 节负责真实页面。
35. 不定义资格、次数、活动、库存、结果持久化、发奖或补偿；这些由后续对应上下文和章节负责。
36. 因为没有一次 Draw 的身份、执行和最终结果事实，本 ADR 不宣称 INV-03 已满足。

## 错误与恢复语义

构造 Strategy 是一个全有或全无的纯内存操作：任一 ID、名称、权重、Outcome、重复身份或总和校验失败，都返回零值 Strategy 和稳定错误；不会返回“部分可用”的候选集合。

这一区分很重要：

- `ErrAwardOutcomeInvalid` 表示配置词汇不可信，不是一次合法 `no_reward`；
- `ErrAwardWeightRequired` 表示候选永远无法被选择，不是“暂时禁用”；
- `ErrDuplicateAwardID` 包装冲突 ID，调用方可用 `errors.Is` 做稳定分类，但不应解析完整错误字符串；
- `ErrTotalWeightOverflow` 表示配置无法被当前数值契约安全表示，不允许 wrap、饱和或丢弃候选；
- 从数据库或缓存读到非法记录时，适配器必须使加载失败并记录安全诊断，不能把缺失行变成 `no_reward`。

本节没有外部副作用，所以没有重试、事务回滚或补偿语义。未来适配器可以重新读取并重试“加载”，但不能自动修改非法业务数据后假装成功。

## 安全与隐私边界

- 不导出字段可以减少绕过构造器的普通调用路径，但不等于对内存篡改或 `unsafe` 的安全防护；
- 名称拒绝控制字符，降低多行日志与不可见控制输入风险，但输出仍需按 HTML、JSON、SQL 参数或日志字段语境编码；
- ID 不是授权凭证，正整数校验不证明调用方有权查看或使用 Strategy；
- `reward` 不包含具体秘密、券码或个人数据；未来奖励引用也不能把凭据嵌进名称；
- 领域错误不携带用户输入全文，未来 adapter 不应在公开响应中回显非法名称或底层 row。

## 影响

### 正面影响

- 第一组业务对象已经拥有明确事实所有者和可执行不变量；
- Strategy 与 Activity、Award 与已到账 Benefit、`no_reward` 与 error 的语义不再混淆；
- 整数相对权重避免浮点误差和过早固定精度；
- 防御性复制、私有字段和规范顺序让聚合在进程内保持确定性；
- 持久化与传输无关，使第 18～24 节可以分别学习存储、端口、算法和 API，而不重写业务语言；
- 哨兵错误允许单元测试和未来适配器使用稳定类别，不依赖错误文案；
- 单候选、同名候选、全未中奖策略等边界被明确保留，不由开发者直觉偷偷禁止。

### 成本与风险

- 适配器需要额外 DTO/row 映射，不能直接给领域结构体加 tag 后 scan/unmarshal；
- 名称按 code point 而不是字素簇计数，用户感知字符数可能与上限不同；
- 当前没有 Unicode normalization，视觉相似名称可能是不同值；
- `uint64` 最大范围会给 MySQL 类型和第 20 节随机算法提出更严格要求；
- AwardID 排序需要 `O(n log n)` 构造，`Award(id)` 当前为 `O(n)`；在没有大候选集证据时接受该成本；
- 没有展示顺序字段，运营 UI 以后不能把 AwardID 顺序误用为业务展示顺序；
- Outcome 目前只有粗粒度两类，具体 Reward 关系出现时需要新增模型而不是扩展字符串自由值；
- 全 `no_reward` 策略在领域层合法，后续发布治理必须自行决定是否警告或禁止；
- 不包含 Draw/Result 意味着本节还不能保证幂等和唯一最终结果。

## 迁移与撤销

当前没有业务表和外部 API，撤销只涉及 Go 源码及其文档，不涉及数据回滚。但一旦第 18 节把该契约持久化，以下语义将成为数据兼容性约束：正 ID、正权重、封闭 Outcome、名称上限与规范化、Strategy 至少一个 Award，以及 AwardID 的所属范围。

未来如需改变这些语义，应：

1. 新增 ADR 说明触发证据和兼容方案；
2. 先定义旧数据如何读取、迁移和回滚，再修改构造器；
3. 对外部 API/消息采用版本化 DTO，不直接暴露 Go 内部表示；
4. 不重写已经执行的 Migration；
5. 保持 `no_reward` 与系统 error 可区分，保持 Lottery 与 Benefit 事实边界。

## 重新评估触发条件

出现以下任一证据时，新增 ADR 或修订后续适配决策：

- 第 18 节所选 MySQL 类型无法无损表示当前 `uint64` 范围；
- 第 20 节随机源无法在整个总权重范围生成无偏区间；
- 运营明确需要固定万分比、概率上下限、中奖率审批或总中奖率约束；
- 候选数量或查找频率使排序/线性查找成为可测瓶颈；
- Award 需要稳定展示顺序、分组、库存、有效期或条件规则；
- Reward 统一模型出现，需要 Lottery 保存稳定奖励引用或快照；
- Strategy 需要草稿/发布/版本生命周期，且并发编辑必须检测冲突；
- 多语言名称、Unicode normalization、搜索或唯一性成为真实产品需求；
- 结果持久化和幂等用例出现，需要实现并验证 INV-03；
- 跨服务/跨语言契约出现，Go 内部类型不再适合作为唯一 Specification。

## 验收证据

本决策由纯领域单元测试证明当前内存契约，包括：

- 有效 reward/no_reward、首尾空白规范化、名称 rune 上限；
- 零 ID、空名、非法 UTF-8、控制字符、超长名、零权重和未知 Outcome 拒绝；
- Strategy 至少一项、AwardID 唯一、总和溢出拒绝；
- 单候选、任意比例、同名候选、全 no_reward、最大总权重合法；
- 构造输入与 `Awards()` 返回 slice 都不能修改聚合集合；
- 不同输入排列得到相同 AwardID 规范顺序；
- 按 ID 查找存在与不存在候选。

这些测试只能证明纯内存对象和构造边界，不能证明 SQL 映射、随机分布、并发抽奖、HTTP 契约、真实页面、缓存、一致性或业务 SLO。完整执行记录见[第 17 节 QA](../qa/lessons/lesson-17.md)。
