# GrowthOS 面试问答文档

本目录把已经实现的课程内容整理成“能在面试中准确说明、能回到仓库验证”的问答。它不替代实现说明，也不替代测试验收。

## 与 `docs/qa` 的边界

| 目录 | 回答的问题 | 主要内容 | 不应承担的职责 |
| --- | --- | --- | --- |
| [`docs/qa`](../qa/README.md) | 这一节是否真的通过验证？ | 命令、环境、测试结果、失败记录、待办和验收结论 | 不负责包装成面试口述答案 |
| `docs/interview` | 为什么这样设计，面试中怎样准确回答？ | 60 秒自述、核心问题、追问、选型边界、项目证据和外部来源 | 不得把“设计合理”写成“已经实测通过” |

面试文档引用 QA 记录时，必须保留其中的“已通过、待验证、因环境跳过”等真实状态；不能用问答文档覆盖验收事实。

## 每章统一模板

每个 `lessons/lesson-NN.md` 至少包含以下部分：

1. **60 秒项目自述**：说明本节解决的问题、关键设计、验证方式和明确边界。
2. **来源说明**：解释面经、官方资料、社区讨论和项目证据各自能证明什么。
3. **12～18 道核心问题**：数量随主题复杂度调整。每题必须包含：
   - 问题；
   - 可直接口述的精准回答；
   - 至少一个追问及追问回答；
   - 可点击的项目代码或文档相对链接；
   - 技术选型边界，即何时当前答案不再成立；
   - 来源标记和可访问 URL。
4. **不能夸大的事实**：列出最容易把项目边界、测试状态或外部资料说过头的地方。
5. **复习清单**：用于口述、画图、代码定位和故障场景演练。

推荐的单题格式：

```markdown
### 问题

- **直接回答：** 可以在 30～90 秒内完整说出的答案。
- **追问：** 面试官可能继续问什么？
  - **追问回答：** 给出结论、原因和必要边界。
- **项目证据：** 使用相对路径链接到实现、测试、ADR、Runbook 或 QA。
- **选型边界：** 当前方案何时需要调整，不能只说优点。
- **来源：** `面经启发` / `官方事实` / `社区讨论` / `项目事实`。
```

## 来源可信度规则

### `项目事实`

当前仓库的实现、测试、ADR、Runbook 和 QA 记录。它只能证明当前提交里的行为；尚未运行的集成测试、未来章节计划和注释中的设想不能写成已完成事实。

### `官方事实`

语言、数据库、框架或库维护者的一手文档和源码，例如 Go、MySQL、PostgreSQL、Redis、sqlx、GORM、golang-migrate。技术结论优先由这一层校准，并尽量链接到具体功能页而不是官网首页。

### `面经启发`

牛客、掘金、知乎等平台的候选人自述复盘，只能证明“有人记录过这个题型或追问方向”。除非帖子正文明确写出，否则不得补写公司、部门、轮次或原题措辞；即使正文写出，也应表述为“作者自述”，不能宣称已被独立核验。

### `社区讨论`

教程、题库、博客和经验文章可用于发现盲点或组织追问，不能作为关键技术事实的唯一依据。若社区说法与官方资料冲突，以当前版本官方资料和项目实测为准。

所有来源都遵循以下规则：

- 不复制长段原文，只做短句概括；
- 区分事实、项目选择和工程推断；
- 涉及版本行为时写明版本或使用当前版本页面；
- 外链必须可访问，仓库链接必须使用相对路径；
- 同一道题可以没有面经来源，但不能没有项目证据和事实校准；
- 找不到可靠面经时直接说明“项目场景题”，不得虚构成某公司原题。

## 完成标准

一章面试文档只有同时满足以下条件才算完成：

- 60 秒自述能覆盖问题、方案、验证和边界；
- 题目数量在 12～18 道之间，且没有用同义题凑数；
- 每题均有直接回答、追问与回答、项目证据、选型边界和来源；
- 所有技术事实均能由官方资料或当前项目证据支持；
- 面经仅用于题型启发，没有虚构公司原题；
- 至少覆盖正常路径、失败路径、安全边界、可观测性和替代方案；
- 明确列出不能夸大的事实；
- 仓库相对链接和外部 URL 已检查；
- 与对应 [`docs/qa`](../qa/README.md) 记录对照，不把待验证项说成已通过；
- 内容可口述，不依赖背诵大段定义，也不会暴露凭据、内部拓扑或不安全操作细节。
